一句话架构

Tauri 2 壳（Rust）跑本地 SQLite/SQLCipher 与 SMTP/Excel/模板引擎；React + TypeScript 只负责 UI 与状态；所有敏感凭据走 macOS Keychain；打包为 Developer ID 签名并公证的 .dmg，官网直发，不进 App Store。

为什么不上 App Store：沙盒会限制任意 SMTP 直连、读写用户选择的 Excel 文件以及后台发信队列；而薪酬类应用的「数据不出本机」卖点在公证直发下更容易向用户证明。
02 / REQUIREMENTS

产品定位与需求映射

03 / TECH STACK

技术选型与开发语言

选型的三个硬约束：① 能产出可签名公证的原生 macOS .dmg；② 能可靠读写 Excel、跑 SMTP、做字段加密；③ 包体小、无需用户额外装运行时。

层选型语言理由 / 替代方案为何不选
应用外壳Tauri 2（WKWebView + Rust 运行时）Rust / 配置 TOML包体 2–10MB、原生 dmg、IPC 安全白名单；Electron 包体 80–150MB 且需自己管 Node 侧文件权限
后端 / 领域逻辑Rust（Tauri Commands）Rust 2021内存安全、Excel/SMTP/加密生态齐备、单二进制；SwiftUI 最原生但 Excel/模板/PDF 要自建大量轮子
前端 UIReact 18 + TypeScript 5 + ViteTypeScript / TSX表格与表单密集场景生态最成熟，类型安全降低字段模板出错率
样式CSS Modules + 自建 Design Token（本报告第 11 章）CSS不引入 Tailwind 运行时争议；深色/浅色双主题靠 CSS 变量切换
本地状态Zustand + TanStack Query（对 IPC 做缓存/失效）TypeScript轻量；查询层统一处理 loading / error / 重试
数据库SQLite + SQLCipher（AES-256）SQL单机零部署、整库加密；明文 SQLite 被否，明文 ini/json 存工资数据被否
凭据macOS Keychain（security-framework / keyring）RustSMTP 授权码、OAuth token、数据库密钥只进 Keychain，禁止落库
Excelcalamine（读） + rust_xlsxwriter（写）Rust纯 Rust、无需 Office、支持 xlsx 动态表头与样式；Python openpyxl 需捆绑解释器
邮件lettre（SMTP over SSL 465）+ 可选 oauth2 crateRust本项目使用飞书邮箱：smtp.feishu.cn:465 + 飞书桌面客户端生成的「专用密码」；OAuth2 仅为其他邮箱扩展保留。不用 SendGrid 等第三方 API（违背「通过自己邮箱发」）
模板minijinja（Jinja2 语法，UTF-8 中文）Rust / 模板文本变量、条件、过滤器齐备且可沙箱化，防止模板注入读本地文件
PDF（可选附件）WebView 打印 HTML→PDF，字体嵌入 PingFang SC / 思源黑体HTML/CSS中文不乱码；比 printpdf 手绘版式成本低

为什么不是其他方案

SwiftUI（原生）

优点：最原生、体积最小。代价：Excel 读写、Jinja 模板、SQLCipher 集成、跨平台表格组件都要自建或引 Swift 包，开发量约为 Tauri 方案的 1.6 倍。若团队是纯 Apple 技术栈且只做 macOS，可作为 v2 备选。

Electron

生态最成熟，但包体大、内存高，Node 侧可直接访问文件系统导致安全边界更宽；签名公证同样要做，没有额外收益。不选。

Python + PyInstaller / Tkinter

GitHub 上那批中文工资条工具就是这条路。做原型最快，但 GUI 观感差、dmg 签名公证繁琐、代码易反编译、SQLCipher 集成麻烦。仅适合验证脚本，不作正式产品。

Web 本地服务（UZonMail / frappe hrms 改造）

功能强但要用户装 Docker/MySQL，违背「dmg 双击安装 + 数据本地」这一核心约束。不选，但借鉴其模板变量与发件队列设计。

系统架构与工程结构

严格分层：UI 不碰数据库、不碰 SMTP；所有外部副作用都经 Rust Command 层，便于做权限白名单、审计和单元测试。

表现层 · React

LAYER 2

LAYER 3

状态机

月份账套 salary_periods.status

草稿 draft → 待发送 ready → 发送中 sending → 已发送 sent → 已归档 archived

发送中/已发送状态禁止编辑工资数值；如需纠错，走「解锁 → 生成修订记录 → 仅对未发送者补发」。

单封信件 send_jobs.status

queued → sending → success / failed → retrying（≤3 次）→ dead

每个 job 带 idempotency_key = hash(batch_id + member_id + period_id + content_checksum)，重复点发送不会产生第二封。

防错机制（本产品最重要的差异化，开源项目全部缺失）

① 身份一致

导入行的姓名+邮箱必须与成员表精确匹配；不匹配的行标红且不允许进入发送范围。

② 内容一致

每封信渲染前计算 checksum(收件人 + 工资条数据)，与预览时校验和比对，不一致即中止。

③ 变量完整

模板中所有变量必须能解析且非空；缺失字段直接拦截，绝不发出「{{实发工资}}」字面量。

辅助措施：默认先试发给自己；发送前显示「本次将向 N 人发送 M 封，请确认」二次弹窗；发送完成后提供「仅重试失败项」而不是整批重发；整套流程零抄送、零密送，从根上避免把 A 的工资发给 B。

09 / SECURITY & COMPLIANCE

安全与合规

薪酬是敏感度最高的一类个人数据。设计上把「本机、加密、最小留存、可举证」当作产品功能而非附加说明。

技术安全

  • 全库 SQLCipher 加密；密钥仅在 Keychain，应用不落盘
  • 管理员口令 Argon2id + 随机盐；5 次失败锁定；空闲 10 分钟自动锁定
  • Tauri Capabilities 白名单：前端不可任意读文件、不可发起任意网络请求
  • 模板引擎沙箱化，禁止文件读取 / 系统调用 / 访问环境变量
  • 导入文件只读打开，不复制；临时附件定时清理；日志与崩溃转储脱敏
  • 发送凭据在内存中使用后清零（zeroize），不进入错误堆栈

合规要点

  • 《工资支付暂行规定》第 6 条：发薪时应向劳动者提供个人工资清单，并书面记录支付数额、时间、领取者姓名，保存 2 年以上备查 → 对应「发送日志 + 归档导出」
  • 《个人信息保护法》：最小必要、目的限定、单独敏感信息保护 → 本地处理、不上传、不采集非必要字段
  • 电子工资条有效性依赖证据链：收件地址、发送时间、SMTP 成功回执、内容校验和、可导出的 CSV 凭证
  • 用户可随时导出全部个人数据 / 彻底清空数据（可携带权与删除权）
  • 首次启动展示「数据仅保存在本机」告知，设置页常驻「无遥测」标识
产品层面的红线：① 任何情况下不把多个收件人放进同一封邮件；② 不把工资数值写进日志/错误上报/备份文件名；③ 不提供「一键群发到全部组」而不经过二次确认的快捷入口；④ 失败重试只允许针对未成功的 job。

四、加密 PDF 与普通 PDF 的区别 / 附件策略

对比普通 PDF打开口令加密 PDF（用户口令 + AES-256）仅「权限口令」PDF
文件内容文本/流以明文存储，任何拿到文件的人直接打开内容整体加密，无口令无法读出任何文字内容仍是明文
保护的是什么只保护版式，不保护信息邮箱被盗、误转发、设备丢失、云盘泄露后的兜底只约束打印/复制/编辑（由阅读器自觉遵守）
强度无AES-256 本身很强，实际强度取决于口令；弱口令可被字典秒破可被多数工具一键忽略/剥离，不能当安全措施
口令分发不需要必须走另一条渠道（飞书消息/短信/口头），绝不能和附件放在同一封邮件里不需要
能否防转发不能不能：收件人打开后可另存无密码副本再转发不能
代价零员工忘口令、HR 要重置、移动端输入不便、需生成并安全销毁临时明文 PDF几乎无
结论与建议：① 邮件正文里的工资条表格本身是明文，再附一份普通 PDF 等于在员工收件箱多留一份可搜索、可下载、可转发的明文副本，反而扩大敏感数据面 —— v1 建议不做 PDF 附件，正文即工资条（需求 7 已满足）。② 若确需附件，只做「打开口令 + AES-256」，口令按可记忆规则生成（工号 + 证件后 6 位 + 年月）并通过飞书消息单独下发，附件发送成功后立即删除本地临时明文文件；不做无意义的「权限口令」。③ 注意三个加密层不是一回事：SQLCipher 保护本机数据库、SMTP SSL 465 只保护传输链路、PDF 口令 保护落地文件，前两者不能替代第三者，也不能替代「逐人独立发送 + 防错校验」。

五、团队使用与分发模式

A · 一台管理机，团队是收件人

当前 v1 设计完全满足：一名管理员在一台 Mac 上配置、导入、发送，42 位成员只是收件人。

B · 多台 Mac，各用各的本地库 按此实施

HR 团队每人装一份 dmg，各自维护加密本地数据；换机/交接用「导出加密备份 → 新机恢复」。需明确备份保管责任与离职交接流程。

C · 多人共用同一份数据

需要共享存储（NAS/云数据库）+ 多管理员与角色权限 + 并发锁，与「本地零上云」卖点冲突，属架构级变更，建议 v2 单独立项评估。

不上 App Store 的落地方式：Developer ID 签名 + 公证 + stapler 装订 → dmg 放内网下载页或飞书云盘 → 附 SHA-256 校验值与「系统设置 → 隐私与安全性」说明 → 有 MDM 的团队可静默分发。应用不进沙盒，SMTP、Excel 文件读写、后台发信队列全部可用。
