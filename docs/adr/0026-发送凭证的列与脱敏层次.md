# ADR-0026 · 发送凭证：CSV 的列、脱敏的层次与留存

日期：2026-11-12 · 状态：**accepted**（TC-403 验收通过，2026-11-12）

## 背景

设计文档把「留痕」写成合规要求：

**ch.9 合规要点**：

> 电子工资条有效性依赖证据链：**收件地址、发送时间、SMTP 成功回执、内容校验和、可导出的 CSV 凭证**

**ch.8 M8 日志与归档**：

> 批次记录、逐封状态、SMTP 返回码、失败原因、按年月归档导出；
> 留存 ≥2 年；日志脱敏（不记工资数值/正文）；支持导出 CSV 凭证

**《工资支付暂行规定》第 6 条**（ch.9 引用）：书面记录保存 2 年以上备查。

红线 2：「绝不把工资数值写进日志、错误上报、备份文件名」。

TC-400 建表时已经把脱敏做进了**结构**（`send_jobs` 无正文列、无 cc/bcc 列）；
本卡把「读回来 + 导出凭证」补上，并验证三个层次的脱敏都是真的。

有四件事要定。

### 洞一：CSV 凭证有哪些列？

凭证要能回答「**谁**、什么时候、发没发到、发的是什么**版本**的内容」：

- **姓名** + **收件地址**：这是「谁」。只有地址也能对上人（邮箱全局唯一），
  但 HR 对账时看名字快得多 —— 凭证是给人看的。
- **状态**（success/dead/…）与 **SMTP 回码**：这是「发没发到」——
  2xx 是成功回执（ch.9 证据链的「SMTP 成功回执」）。
- **发送时间**（`sent_at`）：「什么时候」。
- **checksum**：「哪个版本的内容」—— 与 `send_jobs.checksum` 同源，
  与工资记录的行内容可互相验证（内容一致的凭证侧）。

**没有工资数值**（红线 2）：凭证会被存档、转发、打印 ——
它证明「发了工资条」，不需要复述「发了多少钱」。
工资数值在加密库里（`salary_records`），证据链不需要第二份明文。

### 洞二：姓名进 CSV 是不是违反数据最小化？

TC-301 给「预填成员名单」定过逻辑：**用户主动导出的动作**才是名单出库的许可
（默认关、界面写明后果）。凭证导出同理：CSV 是用户点了「导出凭证」才生成的，
落在 `exports/`（用户自己拿走）—— 与「日志偷偷记下来」是两种性质。
⇒ 姓名进 CSV 合规；**日志（tracing / audit_log）里不进** —— 那是「记下来」。

### 洞三：脱敏的三个层次怎么各自验证？

「日志脱敏」不是一句空话，它分布在三处，**每处都要有测试钉住**：

1. **库层**（结构性）：`send_jobs` 无正文列 —— 表结构本身没有地方放工资数值
   （TC-400 已建，标准已验）。
2. **审计层**：`audit_log.detail_masked` 只写行数与动作
   （TC-302 的覆盖审计已验）。
3. **凭证层**（本卡）：CSV 里逐格扫不到任何金额。
4. **日志层**（tracing）：发送循环的日志只记批次/任务 id 与处置，
   不记 to_email 之外的个人信息、不记数值 —— 编排循环里已有 `tracing::info!`
   的调用点，本卡补一条「日志里搜不到数值」的静态验证
   （对测试生成的日志行断言）。

### 洞四：CSV 的格式细节

- **UTF-8 带 BOM**：Windows Excel 直接双击打开 BOM-less 的 UTF-8 CSV 会乱码 ——
  财务的机器大概率是 Windows + Excel。BOM 是给它们的兼容层。
- **逗号分隔、字段带引号**：姓名/地址可能含逗号（少见但不能炸）——
  全字段按 RFC 4180 转义（含引号就翻倍、字段整体包引号）。
- **文件名含年月**：`发送凭证_2026-10.csv`（归档习惯与 TC-301 一致；
  **不含**批次 id 之外任何业务数值 —— 批次 id 是序号不是工资数据）。
- **留存 ≥2 年**：`send_jobs` 没有删除入口（任何 Command 都不删 job）——
  「不删」就是最稳的留存；清空数据（TC-105）是唯一的终点，那是用户销毁权。

## 决策

1. **CSV 凭证的列**：姓名、收件地址、状态、SMTP 回码、发送时间、内容校验和。
   **没有工资数值**（红线 2）。
2. **姓名进 CSV、不进日志**：凭证是用户主动导出的（同 TC-301 预填名单的逻辑）。
3. **脱敏分四层各自验证**：库层（无正文列）、审计层（detail_masked 只记行数）、
   凭证层（逐格无数值）、日志层（编排日志只记 id 与处置）。
4. **CSV 用 UTF-8 BOM + RFC 4180 转义**；文件名 `发送凭证_<年月>.csv`，
   落 `exports/`（与 TC-301 同一目录）。
5. **send_jobs 没有删除入口**：≥2 年留存靠「不删」；TC-105 是唯一终点。

## 后果

**变简单的**：

- 凭证导出是纯读操作（不写库、不发信）—— 导出不影响批次状态。
- 四层脱敏各有测试 ⇒ 将来任何人往任何一层加「数值」，门禁当场红。

**要认的账**：

- **凭证不含失败原因的原文**：SMTP 错误文案可能带服务器回的细节
  （含收件人片段）—— 凭证只记回码与分类（transient/permanent/auth/network），
  原文在应用内看（发送历史屏），不进导出文件。
- **「留存 ≥2 年」靠不删**：v1 没有归档压缩/搬移 —— 数据量（42 人 × 12 月）
  远不到需要管理的规模。

**重新评估的触发条件**：

- 若凭证要给第三方审计 → 加导出时间、应用版本、批次 id 的签名/哈希链。
- 若数据量大到「不删」成为负担 → 归档搬移策略要单独设计（且先过合规口径）。

## 附：本 ADR 与其他 ADR 的关系

- **红线 2**：四层脱敏是它的逐层兑现。
- **ADR-0023**（send_jobs 结构）：无正文列、checksum 同源。
- **TC-301**（exports/ 目录）：凭证落同一目录，用户拿走。
- **TC-105**（清空数据）：留存的唯一终点是用户主动销毁。
