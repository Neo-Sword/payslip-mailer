# ADR-0016 · 成员名单：一个邮箱一个人、批量粘贴自动去重、只有停用没有删除

日期：2026-11-11 · 状态：accepted（TC-201 验收通过，评审记录见该 spec 文末）

## 背景

TC-201 做 S05「邮件组与成员」与 S06「成员新增 / 编辑」。设计文档 ch.6 给了三张表：

> `mail_groups | id, name, note, sort_order | TEXT NOT NULL | 组名唯一`
> `members | id, name, email, employee_no, active, note | email 格式校验 / UNIQUE | employee_no 可选，用于 Excel 精确匹配`
> `group_members | group_id, member_id | 复合主键 | 成员可属多组`

S05/S06 的原型把行为写得很细，但有三处需要实现前定口径。

### 洞一：「同组邮箱唯一」到底是全局唯一还是组内唯一？

S05 的页脚写「同组邮箱唯一，导入时自动去重」，但 ch.6 的表定义写 `email … UNIQUE`
（**全局**唯一，不是复合唯一）。

这两个说法不冲突，只要把「一个邮箱 = 一个人」这件事认下来：

- `members.email` 全局唯一 ⇒ 同一个邮箱在任何地方都是**同一个人**；
- 一个人可以属于多个组 ⇒ 那是 `group_members` 的多行，不是多个 member 行；
- 所以「同组邮箱唯一」是全局唯一的**推论**，而 `group_members` 的复合主键
  保证「同一个人在同一组里只出现一次」。

**若 email 只在组内唯一**，同一个人在不同组会是两条 member 行，
S03 的「三重核对」里的「身份一致」就没法按邮箱匹配（ADR-0011 之外的一处隐患）。

⇒ **全局唯一**。

### 洞二：批量粘贴遇到重复邮箱，是报错还是去重？

S05 的交互要点写「『批量粘贴』接受 TSV/CSV 两列（姓名 邮箱）并**预览去重结果**」，
页脚写「导入时**自动去重**」；而 S06 的交互要点写「邮箱格式 + 同组唯一**实时校验**；
错误字段**红描边**」。

两处口径不同，但不是矛盾 —— **批量粘贴与编辑表单是两种场合**：

- **批量粘贴是便利功能**：HR 从飞书/Excel 粘一坨，重复的邮箱多半是同一个人被粘了两遍。
  报错的话，整批都进不去，HR 还得回去找哪两行重了。⇒ **自动去重**（同邮箱合并成一个人），
  并在预览里**告诉使用者去掉了几个**。
- **编辑表单是精确操作**：那是在改一个**已经存在**的人，填一个别人占用的邮箱
  一定是填错了。⇒ **报错 + 红描边**。

### 洞三：「邮箱待确认」这个第三态归谁？

S05 的状态列有三种：**启用 / 停用 / 邮箱待确认**；S06 的表单写
「该邮箱格式可疑（**曾有一次 550 退信**），请确认后再启用」，
交互要点写「异常状态（550 退信历史）直接暴露给用户，避免再次发错」。

⇒ **这个状态是从发送历史算出来的**，不是 `members` 表的一列
（ch.6 的 `members` 只有 `active`，没有别的状态列）。

而 550 退信历史住在 `send_jobs`（P4 的表，TC-402/TC-403 才有）。

⇒ **TC-201 只实现两态**（启用 / 停用），第三态归 TC-403。
TC-201 的界面把「状态」这一列的位置留好（它现在显示启用/停用），
TC-403 落地时在同一列加上第三态。

### 附带：成员能删吗？

S05 的操作列只有「编辑」，S06 的表单有「移出全部组」但没有「删除成员」。
且 S06 写「**修改邮箱后，历史发送日志仍保留原收件地址，便于追溯**」——
这说明历史是以**地址**留痕的，删掉成员行并不会删掉历史，但会让
「这个人现在还在不在名单里」这件事少一条线索。

⇒ 与 TC-200 的字段同一口径：**只有停用，没有删除**（红线 8 的同族）。
HR 想让一个离职的人不再收到信 → 停用（停用的人不进入发送范围，S05 原话）。

## 决策

1. **三张表照设计文档**（`mail_groups` / `members` / `group_members`），
   `members.email` **全局 UNIQUE**、`members.active` 默认 1、`group_members` 复合主键。
2. **批量粘贴：同邮箱自动去重**，并在预览里报告「去掉了几条重复」与「哪几行有问题」。
   格式非法的行**整行跳过并报错**（不静默丢）。
3. **编辑表单：邮箱撞了别人 → 报错 + 红描边**（与批量粘贴的不同口径，见洞二）。
4. **成员只有停用没有删除**；**邮件组可以删**（删组只解除归属，成员本身不动）。
5. **「邮箱待确认」第三态归 TC-403**（它才有 550 退信历史）。
6. **批量粘贴的解析**：TSV（制表符）与 CSV（逗号）两种；
   **第一行如果第二列不是邮箱，就当表头跳过**（HR 从 Excel 连表头一起粘过来的常态）。
7. **`INVALID_EMAIL` 码用起来** —— TC-102 的文件头早就把它划给
   「TC-201 成员邮箱批量粘贴」了，本卡是它的正主。

## 后果

**变简单的**：

- 一个邮箱一个人 ⇒ S03 的「三重核对」里的「身份一致」按邮箱匹配就有唯一依据。
- 批量粘贴不会因为几行重复就整批卡住（HR 粘一坨是很常见的动作）。
- 成员名单与 TC-200 的字段表一样，**没有删除**这个不可逆操作。

**要认的账**：

- **全局唯一意味着两个不同的人不能用同一个邮箱**。现实中确实会有
  （共用邮箱、别名）。这类情况只能合并成一个人 —— 界面上的提示要写清。
- 批量粘贴的格式判断是**启发式**的（看有没有制表符/逗号、看第一行像不像表头）。
  判错了整批都进不去，所以**必须先给预览**（设计文档 S05 原话：「并预览去重结果」），
  用户看着预览确认了才真的写进去。

**重新评估的触发条件**：

- 若真实名单里确有共用邮箱的成员 ⇒ 需要一个「主邮箱 + 别名」的模型，
  那时 `members.email` 的唯一性口径要重写（ADR-0016 随之改）。
- 若 TC-403 的 550 退信统计做出来了 ⇒ 「邮箱待确认」第三态落地，
  `members` 表**仍然不加那一列**（它是派生态，不是存出来的）。

## 附：本 ADR 与其他 ADR 的关系

- **ADR-0004**（错误词表先行）：本卡用上 TC-102 早就划给它的 `INVALID_EMAIL` 码。
- **红线 3**（不提供「一键群发全部组」而不经二次确认的入口）：
  S05 的「私发选中成员」只是**跳到 S11**（预览与核对），发送的二次确认在那边。
- **红线 2**（工资数值不写进日志/错误）：名单是个人数据，
  批量粘贴的报错只说**第几行、哪个字段不对**，不回显整行内容。
