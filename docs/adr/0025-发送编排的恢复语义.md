# ADR-0025 · 发送编排的恢复语义：点发送、中断恢复与仅重试失败项

日期：2026-11-12 · 状态：**accepted**（TC-402 验收通过，2026-11-12）

## 背景

设计文档 **ch.7「可中断设计」**（「自研相对脚本类开源工具最大的工程价值」）：

> 队列每完成一封即持久化。用户强退或断电后重启，应用显示
> 「发现未完成的批次：已发 27/60，是否继续？」——靠幂等键保证已发的人不会收到第二封。

**ch.5**：

> 每个 job 带 idempotency_key = hash(batch_id + member_id + period_id + content_checksum)，
> 重复点发送不会产生第二封。

**产品红线**：

- 红线 3：「绝不提供『一键群发全部组』而不经过二次确认的入口」。
- 红线 4：「失败重试只允许针对**未成功的 job**，不提供整批重发」。

**辅助措施**（ch.5）：「发送前显示『本次将向 N 人发送 M 封，请确认』二次弹窗；
发送完成后提供『仅重试失败项』而不是整批重发」。

TC-400 已经把编排骨架做完（`drive_batch` + 注入 `Sender` + 每封即持久化 +
`send_jobs` 无 cc/bcc + 幂等键的 UNIQUE）；TC-401 已经把三重核对做完。
本卡是编排的**最后一公里**：点发送的入口、恢复的语义、补发的边界。

有四件事要定。

### 洞一：`sending` 状态在重启后算什么？

进程崩溃的那一刻，可能有一封 job 停在 `sending`（取出来正要发）——
**它可能已经发出去了（SMTP 已收），也可能还没发出**。恢复时两个选择：

- **回 queued 重发**：最坏情形 = 给本人发两封一样的工资条（尴尬、不泄密 ——
  还是发给本人的地址）；最好情形 = 不丢发。
- **判 dead 补发**：最坏情形 = 那个人这轮收不到（走「仅重试失败项」补）；
  最好情形 = 不重发。

⇒ **回 queued 重发**。理由：工资条发给**本人**，重复发送的代价是「本人收到两封」
—— 不构成隐私事故（红线 1 关心的是把 A 的发给 B）；而「少发一封」需要 HR
在日志里逐个排查再补发，代价更高。设计文档的「已发的人不会收到第二封」
指的是**已成功（success）的 job 不再进循环** —— 这由 `take_next` 只取
queued/到点的 retrying 保证（TC-400 已实现），不是指存疑的 sending。

### 洞二：恢复的入口是什么？

「应用显示『发现未完成的批次：已发 27/60，是否继续？』」—— 这是**进入工作台时**
的一次性提示。但用户可能选择「先不继续」（去改数据）⇒ 恢复必须是**可重复发起**的：

- `find_unfinished(db)`：最近一个 running/paused 批次 + 进度统计
  （总数、已成功、失败、待发）—— 工作台启动时查一次（显示提示条），
  编排屏常驻也能看。
- `resume`（TC-400 已有）：paused → running。**恢复时把 sending 回 queued**
  （洞一）。

「继续」之后发送循环接上（`drive_batch`）—— TC-500 之前没有真发送器，
`run_batch` Command 会报「发信设置还没配置」（这是事实不是假象）；
批次与任务的持久化、恢复、补发的**逻辑**在单测里用假发送器完整验证。

### 洞三：「仅重试失败项」的边界

红线 4：「失败重试只允许针对**未成功的 job**」。

⇒ `retry_failed(db, batch_id)`：把 `dead` 的 job 回 `queued`
（**attempts 保留** —— 死过一次的事实不清零，下一轮失败立即按退避表的
后续档位走）；`success` 的**碰都不碰**。error_code 清空（重试是新的一次判定）。

**什么情况下不该提供重试**：批次被 `aborted`（认证失败）—— 凭据是坏的，
重试只会再失败；恢复入口引导去 SMTP 设置（TC-500）。`finished` 的批次
里如果有 dead（永久失败退信），重试合法 —— 那正是「仅重试失败项」的主场景。

### 洞四：点发送的入口与二次确认

红线 3 要求二次确认。编排屏的流程：

1. 选月份 + 范围（v1 全部启用成员，同 S11）→ **先核对**（TC-401 的
   `verify_send_scope`）→ `ok=false` 时**禁止进入发送**（按钮禁用 + 理由列出）。
2. 核对通过 → 点「发送」→ **确认对话框**：「本次将向 N 人发送 M 封（2026-10）。
   每封一个收件人，绝不抄送。」→ 确认 → `start_batch`。
3. `start_batch` Command 内部**再核一遍**（核对结果可能已过期 ——
   数据在确认对话框停留期间被改）：不过则拒绝并说清谁被拦。

**「再次核对」要不要做？** 要。前端核对通过到用户点确认之间可以隔很久
（先核对 → 去改了个数据 → 回来确认）—— Command 层是唯一关卡（红线 5 的同族）。

## 决策

1. **sending 存疑在恢复时回 queued**（洞一）：发给本人的重复无害，
   丢发难查；已成功（success）的绝不重发。
2. **恢复是可重复发起的**：`find_unfinished` 随时可查（工作台提示条 +
   编排屏常驻）；`resume` 把 sending 回 queued 后批次回 running。
3. **仅重试失败项**：`dead → queued`，attempts 保留、error_code 清空；
   success 不动；`aborted` 批次不提供重试（引导去 SMTP 设置）。
4. **点发送的入口带两层核对**：前端先核对（体验），`start_batch` Command
   再核一遍（关卡 —— 数据可能在确认期间被改）。
5. **真发送器在 TC-500 接线**：TC-402 的 `run_batch` Command 在 SMTP 凭据
   未配置时报「发信设置还没配置」—— 事实陈述，不是假成功。编排的持久化、
   恢复、补发逻辑在单测里用假发送器完整验证。
6. **发送历史的进度从库算**：批次的 success/failed/total 是逐封持久化时
   累加的（TC-400）—— 「已发 27/60」读库即得，不另存进度快照。

## 后果

**变简单的**：

- 恢复就是「查一次 + 续跑」，没有特殊的恢复模式 —— 批次状态机自己表达一切。
- 补发与首发走同一条循环（queued → sending → …）—— 没有第二套发送代码。

**要认的账**：

- **存疑 sending 回 queued 可能重发**：发给本人的两封重复 —— 接受（洞一）。
- **TC-402 结案时点发送会报「SMTP 未配置」**：真发送在 TC-500。
  编排屏在此之前能看到批次被创建、任务排队、（测试中的）恢复与补发。
- **aborted 批次不可重试**：凭据坏时重试没有意义 —— 用户要先修设置。

**重新评估的触发条件**：

- 若 SMTP 层能拿到「服务器是否已收」的回执 → 存疑 sending 可以精确判定，
  回 queued 的重发可以避免。
- 若要支持「发送窗口」（只在某时段发）→ 编排循环加时间条件，恢复语义不变。
