# ADR-0012 · 首启与解锁的界面口径：数据目录跟 bundle id 走 + SMTP 步骤后置 + 邮箱与单位名称的存放 + 迁移漂移专属码 + 只读态常驻横幅 + 锁定走事件推送 + `unlocked` 字段 + 「记住本机 10 分钟」的定义 + Keychain 丢失两条分支 + 忘记密码不给假按钮

日期：2026-11-11 · 状态：proposed（随 TC-103 发出，验收通过后转 accepted）

## 背景

TC-100 / 101 / 102 把 P1 的 Rust 层做完了：加密库、Keychain、口令哈希、失败锁定、空闲与唤醒锁定，
外加六个已注册的 Command。**但没有一个界面调用过它们**——`src/App.tsx` 至今是 P0 的骨架冒烟屏，
数据是写死的 `BATCHES` 数组，前端唯一一次碰 `@tauri-apps/api` 是 `AppShell.tsx:2` 的 `isTauri()`。
TC-103 是第一次真的把界面接到这些 Command 上。

设计文档对 S01 / S02 的**视觉与文案**写得很细（逐字可抄），但对「实现要决定的事」留了十个洞。
每一个洞不堵，写代码时就会随手填一个，而随手填的东西以后要么改不动（数据目录），
要么骗人（「记住本机 10 分钟」），要么静默失败（只读态）。逐条列在设计文档里查不到的部分：

1. **数据目录**：文档写 `~/Library/Application Support/PayslipMailer/`，而 Tauri 的
   `app_data_dir()` 按 bundle id 推出的是另一个目录名。两个名字只能有一个是真的。
2. **S01 第 2 步**：文档要求「填 SMTP 并『测试连接』成功后才允许完成」。真实发件账号
   是外部阻塞项（TC-500 至今 blocked），使用者已定「先 mock SMTP 开发，真实账号后置」。
3. **单位名称**：S01 表单里有这一栏，说它是「邮件模板默认值」，但 `admins` 表没有这一列，
   文档也没说它存哪。
4. **邮箱格式**：S01 要求「邮箱格式实时校验」，但 `create_admin` 现在不校验格式，
   而 `INVALID_EMAIL` 这个码在 TC-102 的文件头里被明确划给了 TC-201 的成员批量粘贴。
5. **迁移 checksum 漂移**：TC-100 结案时留了一行「要不要给迁移漂移一个专属错误码待定」。
6. **只读态**：文档 ch.6 只有一句「失败则回滚并保持只读」。用户界面怎么表达「只读」，
   文档里连「横幅」这个词都没出现过。
7. **锁定怎么进界面**：`LockWatch` 的锁定回调在观察线程上跑，它只能 `close()` 库；
   前端不知道库关了，界面会停在「已解锁」的样子继续让人点。
8. **`admin_status` 缺一个字段**：`db.rs` 的注释里提到「`admin_status` 的 `unlocked`」，
   但 `AdminState` 里没有这个字段。
9. **「记住本机 10 分钟」**：S02 上有这个开关，默认开着。它到底改什么、改完存不存、
   重启还在不在——文档一个字没写。
10. **Keychain 条目丢失 / 忘记密码**：`KEYCHAIN_MISSING` 与「无法远程找回」都在 Rust 层就位了，
    引导界面长什么样、给哪几个动作，文档没画。

## 决策

以下每条后面跟**实测输出**（源码位置、命令输出、或既有测试的断言），不是文档转述。
源码引用一律给 `crate-version/文件:行`，因为 Tauri 的行号会随版本漂。

### 1. 数据目录 = Tauri `app_data_dir()`，即 `~/Library/Application Support/cn.payslipmailer.desktop/`；设计文档写的 `PayslipMailer/` 作废

源码链条（三段，都在本机 `~/.cargo/registry` 里读到的，不是记忆）：

- `dirs-6.0.0/src/mac.rs:7` —— `fn app_support_dir() -> Option<PathBuf> { home_dir().map(|h| h.join("Library/Application Support")) }`
- `tauri-2.12.5/src/path/desktop.rs:75-77` + 同文件 73 行的文档注释 —— macOS 的 `data_dir()` 解析到 `$HOME/Library/Application Support`
- `tauri-2.12.5/src/path/desktop.rs:251-257` —— `app_data_dir()` = `data_dir().join(&config().identifier)`

`tauri.conf.json` 里 `identifier = "cn.payslipmailer.desktop"`，所以真实目录是
`~/Library/Application Support/cn.payslipmailer.desktop/`。

实测这个目录**现在还不存在**：

```
$ ls -d ~/Library/Application\ Support/*ayslip* ~/Library/Application\ Support/cn.payslip*
zsh: no matches found: /Users/swordsharp/Library/Application Support/*ayslip*
```

即：应用至今没有真的开过一次生产库（TC-000 起 app 只跑过冒烟界面，没调过 `app_data_dir()`）。
所以本卡是第一次真的创建它——**现在定口径的成本是零，以后改的成本是「搬家」**。

为什么不反过来把目录名硬掰成文档写的 `PayslipMailer/`：

- 要么在 `tauri.conf.json` 里配 `app.directories.data` 覆盖，要么在 Rust 里手写路径。
  手写路径等于和 Tauri 的 resolver 分叉，`identifier` 一改就静默分裂成两个库目录，
  而且第二个库是空的——用户看到的是「工资条全没了」，不是「目录变了」。
- 界面（S14 与 S01 的「数据仅保存在本机」卡片）必须显示**真实存在**的那个路径。
  显示一个不存在的路径，等于让用户照着它去备份，然后备份不到东西。
- 文档那条的价值在「数据在用户的 Library 下、不出本机、不进 iCloud」，不在目录名的字面。
  前一条由 `dirs` 的解析结果保证（macOS 的 `Application Support` 不在 iCloud Drive 同步范围内）。

顺带一条：`infra/db.rs` 测试里的 `dirs_hint()` 目前硬编码的是文档那个路径
（`~/Library/Application Support/PayslipMailer`），本卡把它改成同一口径，
免得测试里的字符串变成第二个「真相源」。

**实现期追加（TC-103 验收，2026-11-11）**：这个目录**由应用自己创建**。
验收时发现：真机首启时 `open_with` 直接拿目录去连库，而生产代码里没有任何地方
`create_dir_all` 那个目录（只有测试基座里有，所以几百条测试一条都没碰到它）。
全新机器上 SQLite 直接报「unable to open database file」，首启的 `admin_status`
失败，界面是「没能读到本机状态」而不是 S01 向导。
修法是 `open_with` 自己 `create_dir_all`（**只建目录，不建库文件**——
`load_or_create_key` 的守卫靠 `db_path.exists()` 判断「库在不在」，
建目录不影响它）。已由 `db_creates_the_data_directory_on_first_open` 与
`db_creating_the_directory_does_not_break_the_keychain_guard` 两条单测钉住。
这条同时把本节的「现在定口径的成本是零」变成了事实：
目录名仍由 `identifier` 决定，而目录本身由应用负责建出来。

### 2. S01 的第 2 步（SMTP + 测试连接）走「稍后设置」，真实连接后置到 TC-500

设计文档 S01 的交互要点原文是「第 2 步填 SMTP 并『测试连接』成功后才允许完成」。
本卡不实现这条，理由与实测：

- 使用者 2026-11-11 的决定是「先 mock SMTP 开发，真实账号后置」；
- TASKBOARD 上 TC-500（飞书 SMTP 实连）状态是 **blocked**，缺的是发件账号与专用密码，
  不是代码；
- `src-tauri/src/commands/` 里至今没有任何 SMTP 相关 Command（`app.rs` 只有 `app_info`，
  `auth.rs` 只有那六个），「测试连接」现在按下去只能连一个假地址，测了也不作数。

所以 S01 保留三步的**形状**（文档画的是三步，就画三步），第 2 步给一个「发件邮箱稍后在设置页配置」
的说明卡片 + 一个真的能点的「稍后设置」，点它就直接完成初始化进工作台。
**不做**的是「测试连接成功后才允许完成」这个门槛，spec 的范围里写明。

### 3. 邮箱：前端实时校验 + 后端 `create_admin` 用 `VALIDATION_ERROR` 兜底；单位名称：存 `app_meta` 的 `org_name` 键

实测的既有事实：

- `migrations/0002_admins.sql` 全文里 `admins` 只有 `id / email / pwd_hash / created_at /
  last_login / failed_attempts / locked_until` 七列，**没有单位名称**；
- `migrations/0001_baseline.sql:21` 建的是 `app_meta`——通用 KV，`idle_lock_minutes` 已经住在里面；
- `error.rs` 的 `INVALID_EMAIL` 在 TC-102 的文件头注释里被明确划给 TC-201 的批量粘贴场景，
  `admins.rs` 里也写了「别混用」；
- `create_admin` 现在**不校验**邮箱格式（`infra/admins.rs` 的注释记着这件事）。

决定：

- 邮箱格式**前端实时校验**（文档要求「实时」，只有前端能做），
  后端 `create_admin` 也校验一次，失败返回已有的 `VALIDATION_ERROR`——
  **不挪用 `INVALID_EMAIL`，也不新加码**。前端的「实时」是体验，后端的这次校验是底线：
  直接喂 Command 一个没有 `@` 的邮箱必须被拒，且库里不留行。
- 单位名称存 `app_meta` 的新键 `org_name`，不给 `admins` 加列。
  加列要走一次迁移，而 `org_name` 是「一次性事实的 KV」，正是 `app_meta` 的口径
  （`idle_lock_minutes` 同例）。文档说它是「邮件模板默认值」——TC-202 的模板引擎读它，
  读的是 `app_meta`，不是 `admins`。

### 4. 迁移 checksum 漂移给专属码 `MIGRATION_DRIFT`

TC-100 结案时这条写的是「待定」。现在定：**加**。

区分的依据是「谁知道原因」：

- 驱动报 `file is not a database` 是**歧义**的——ADR-0010 §4 实测过三种原因（密钥不对、
  文件损坏、根本不是 SQLite 文件）驱动报同一个错，所以那种情况只能给通用 `DATABASE`；
- 我们自己的 checksum 比对（`infra/db.rs` 的 `Migration::checksum` 与 `schema_migrations`
  里记录的 `checksum`）**知道原因**：某一版迁移的 SQL 与应用时记录的不一致。
  既有测试 `db_editing_an_applied_migration_fails_with_a_checksum_message` 钉的就是这件事。

按 ADR-0004 的「词表先行」：先加 `error.rs` 的码与 `user_message()` 文案，再让界面去显示。
文案要能点出**哪一版**（`version` 在 `MigrationFailure` 里拿得到），
细节（两个校验和各是什么）留在 `Display`/日志里，不进文案——
按红线 2 的同族口径，UI 文案不堆技术细节。

### 5. 只读态用**常驻横幅**，不用 toast

实测：`src/components/ui/overlay.tsx` 的 `useToast` 成功提示 3 秒自动消失，
失败可以 `sticky` 但**可手动关**；`DbState::is_read_only()` 存在；
`DbState::write` 在只读时拒绝并返回「数据库处于只读状态（迁移未完成），本次修改未写入」。

只读是**整个会话的持续状态**，不是一次事件。可关掉的提示会在用户下一次尝试写入之前消失，
于是那次写入的失败看起来像凭空冒出来的——这正是 TC-100 结案遗留里那句
「文案与状态不符」的界面版。所以：横幅由 `admin_status` 返回的 `read_only` 驱动，
常驻、不可关，文案给三要素（发生了什么 / 影响范围 / 下一步），
且解锁之后仍在（只读与锁定是两个维度：只读 = 能读不能写，锁定 = 什么都读不到）。

**实现期追加（TC-103 后端①，2026-11-11）**：写被拒不再复用 `DATABASE`，加专属码
`READ_ONLY`——同样按 ADR-0004 词表先行，先加码与文案再接线。实测的矛盾：旧实现下
写被拒的错误经 `user_message()` 变成「本机加密数据打不开」，与「已解锁、能读、只差写入」
的实际状态正好相反——这是本节要治的「文案与状态不符」在**错误通道**上的另一半
（横幅治的是显示通道）。现在的形态：`DbState::read_only_message()` 是横幅文案与写拒绝
文案的**唯一来源**，`write` 被拒时返回 `ReadOnly(同一句话)`，`AdminState.read_only_message`
把同一句带给前端，`UnlockOutcome`/`UnlockResult` 顺带 `unlocked`——
「与横幅说的是同一件事」在逐字层面成立，并有单元测试钉住
（`db_read_only_write_rejection_carries_the_banner_message` +
`probe_and_unlock_stay_usable_in_a_read_only_session`）。
只读但**不漂移**的情况（待跑迁移执行失败，TC-100 标准 6 的那条路）不知道具体原因，
文案就不带版本号——不知道原因就不假装知道，同样有断言钉住（`!msg.contains("版")`）。

### 6. 锁定怎么进界面：`.setup()` 捕获 `AppHandle` → 锁定回调里 `emit` 事件；不用轮询

现状实测：`src-tauri/src/lib.rs` 里**没有** `.setup()` 钩子，也没有任何 `emit` 调用——
这条是新增接线，不是已有能力。`LockWatch::start` 的回调边界是
`impl Fn() + Send + Sync + 'static`（`src/infra/wake.rs:243`），
所以现在这个闭包只捕获了 `Arc<DbState>`。

能不能捕获 `AppHandle`，读源码而不是猜：

- `tauri-2.12.5/src/app.rs:387-391` —— `AppHandle<R> { runtime_handle: R::Handle, manager: Arc<AppManager<R>>, event_loop: Arc<Mutex<EventLoop>> }`
- `tauri-runtime-wry-2.12.3/src/lib.rs:2526-2532` —— `pub struct WryHandle<T> { context: Context<T> }` 之后紧跟
  `// SAFETY: this is safe since the Context usage is guarded by Context::send_user_message.`
  与 `unsafe impl<T: UserEvent> Sync for WryHandle<T> {}`——**显式给了 Sync**
- `tauri-2.12.5/src/lib.rs:974` —— `Emitter::emit<S: Serialize + Clone>(&self, event, payload)`，
  只借 `&self`，转手交给 `manager().emit(...)`，签名里没有任何主线程要求

`Arc<AppManager<R>>` 与 `Arc<Mutex<EventLoop>>` 都是 Send+Sync，所以 `AppHandle` 应当
自动是 Send+Sync。但 auto-trait 是编译器算的，不是我能从字段推死的，
所以**编译期断言本身列为验收标准**（`lib.rs` 里一条 `assert_send_sync::<tauri::AppHandle>()`
式的 const 断言）。退路也定好：万一不是 Sync，用 `Mutex<AppHandle>` 包一层
（`Mutex<T>: Sync` 只需 `T: Send`），不改整体设计。

为什么不用轮询（前端每秒调 `admin_status` 看库关没关）：

- 锁定态下库是**关**的，`probe` 要读 `admins` 行才能报状态，轮询要么逼着后端反复开库
  （每次开库要从 Keychain 取密钥），要么在锁定态下读不到东西；
- 1 秒一次的 IPC 换不来「立刻」：合盖唤醒的那一瞬间，用户看到的仍是旧界面。

事件名与载荷由实现定，但验收钉的是**可观察结果**：空闲到点后界面自己变锁屏，
不需要用户点一下或刷新一次。

### 7. `AdminState` 加 `unlocked` 字段，并把两个「锁」的语义分开写进注释

实测的不一致：`infra/db.rs:548` 附近的注释提到「`admin_status` 的 `unlocked`」，
而 `infra/admins.rs` 的 `AdminState` 实际字段是
`initialized / email / locked / seconds_left / remaining_attempts / read_only`——**没有 `unlocked`**。

语义也必须分开，否则迟早有人把两个「锁」当一个：

- `locked` = **口令失败锁定**（`locked_until` 非空且未到点），来自 5 次输错；
- `unlocked` = **库是开着的**，取 `db.is_open()`。

两者独立：口令锁定期间库一定是关的（TC-102 的失败分支立刻 `close()`），
但库关着不等于口令锁定——空闲锁定、⌘L、唤醒锁定都关库而不锁口令。
前端要判的是 `unlocked`，要显示倒计时的是 `locked`。

**`probe` 里这个字段有个坑，写在这里免得实现时踩**：`probe` 为了读 `admins` 行会
**自己临时开库**再关回去（`infra/admins.rs:302-337` 的 `ensure_open` + `close_if_we_opened`，
注释原文「自己开的库读完就关回去：`probe` 只是『看一眼』，不该顺手把人解锁」）。
所以 `unlocked` 在 `probe` 里**不能**照 `db.is_open()` 取——那样它恒为 `true`
（库是 `probe` 自己开的），锁屏就永远进不去，而且「锁定态下库是关的」这条不变量
会被一个只读操作悄悄破坏。正确取法是「**进来时就已经开着**」，即 `!opened_by_us`。
`unlock` 那条路上库是我们主动开的，取 `db.is_open()` 才对——两个入口口径不同，
这是本条要钉的重点。

### 8. 「记住本机 10 分钟」= 本次解锁的空闲阈值取 `max(库里阈值, 10 分钟)`，不写库、重启失效

设计文档 S02 只有那个开关的字面（默认 ON），语义一个字没写。
不定义就只能猜，而猜出来的实现大概率是「存进 `app_meta`」——那会让一个
看起来只作用于本次的开关，永久改掉全局设置。

定义（本卡钉死）：

- 勾选后，**本次解锁会话**的空闲阈值 = `max(app_meta.idle_lock_minutes, 10 分钟)`；
- **不写库**：`app_meta` 里那个键的值在解锁前后一字不变；
- **重启失效**：下次解锁回到库里的阈值；
- 唤醒锁定与 ⌘L **不受影响**：它们是事件驱动，不是空闲计时，
  「记住本机」不该让人合盖后不锁屏——那正是这条红线要防的场景。

实现落在已有的 `LockWatch::set_idle_secs(secs)`（`src/infra/wake.rs:295`）上，
解锁成功后按上面的规则调一次，不改 `LockWatch` 本身。

必须诚实写进界面文案的一点：**库里阈值是默认 10 分钟时，这条是恒等操作**
（`max(10, 10) = 10`）。所以开关在默认配置下不改变任何行为，
文案不能暗示它总在起作用。它真正起作用的是「阈值被设成 5 分钟 + 我今天想偷懒」这一格。

### 9. `KEYCHAIN_MISSING` 给两条分支：「重试」与「重新初始化」

守卫的实测：`infra/db.rs:219-234` 的 `load_or_create_key`——钥匙串里没有密钥**且库文件不存在**
才生成新密钥；库文件在而密钥没了，原样返回 `KeychainMissing`。
这个守卫防的是「新密钥盖出一个空库压在老数据上，工资没了而应用一声不响」。
`KEYCHAIN_MISSING` 与 `KEYCHAIN` 是两个码，`error.rs` 的测试断言了它们不等。

界面据此给两条：

- **重试**：覆盖 ADR-0002 记的正常升级场景——未签名产物升级后 ACL 重置，
  用户在「密码与密钥」里重新授权或系统弹窗点了「允许」之后，点一下就能接上。
  重试走的是同一次 `admin_status`，**不新建空库**（守卫保证）。
- **重新初始化**：走 S01 重新建档。文案必须明说旧的 `data.db` 仍在原目录、
  只是当前打不开，且重新初始化不会删它（删与恢复归 TC-104 的备份/恢复）。

两条都不能只有文案没有动作——文档 ch.11 的通用规则是「空状态必须带一个明确主操作」。

### 10. 「忘记密码」只给诚实引导，不给假的「重置密码」按钮

实测：设计文档 ch.14 风险条写的是「忘记管理员密码 → …明确告知『无法远程找回』」，
S02 的交互要点写的是「『忘记密码』引导到备份恢复流程，明确告知无法明文找回」。
而备份恢复是 TC-104，还没做。

所以本卡点「忘记密码？」弹一个说明：口令只做哈希、无法明文找回；
唯一的出路是从加密备份恢复；恢复入口在设置页，**由 TC-104 落地**。
不放一个「重置密码」按钮——本地应用没有服务器可以重置，放了就是让用户白点一次，
然后在 TC-104 做完之后变成两个入口。

## 后果

**变简单的**：

- 数据目录只有一个真相源（`app_data_dir()`），S14 显示的路径、备份要找的路径、
  `db.rs` 测试里的提示字符串，三处同一个来源。
- 前端只需要一个状态判断（`unlocked`）就能决定渲染 S02 还是工作台，
  不必自己推断「库是不是开着的」。
- 只读、Keychain 丢失、口令锁定三件事各自有专属表达，不再共用一句通用 `DATABASE` 文案。

**变复杂的 / 要认的账**：

- 目录名与设计文档字面不一致。以后写安装说明、给用户指路，都得说
  `cn.payslipmailer.desktop` 这个名字（它不如 `PayslipMailer` 好认）。
- S01 的三步里有一步是「稍后设置」，与文档「测试连接成功后才允许完成」不符。
  TC-500 做完之后要回头补这个门槛，届时 S01 的第 2 步才算完整。
- 「记住本机 10 分钟」在默认配置下是恒等操作，界面上要老实说明，
  否则用户会以为它做了比实际更多的事。
- 事件推送新增了一条 Rust → 前端的通道（`.setup()` + `emit` + 前端 `listen`）。
  它不在门禁的覆盖范围内，只能靠验收里那条「空闲到点界面自己变锁屏」的真人观察兜住。
- `MIGRATION_DRIFT` 是一个新错误码，词表（ADR-0004）要同步加一行，
  否则门禁的「敏感数据未进 git」不拦它，但下一个人加码时会找不到先例。

**重新评估的触发条件**：

- 若 `tauri::AppHandle` 在某次升级后不再 `Sync`（编译期断言会当场红），
  退路是 `Mutex<AppHandle>`；若连 `emit` 也开始要求主线程，
  就改成 `run_on_main_thread` 投递，届时本条 §6 追加一节实测。
- 若真实发件账号到位（TC-500 解除 blocked），S01 第 2 步的「测试连接」门槛要补回来，
  本 ADR §2 随之追加。
- 若以后要支持多管理员或把单位名称做成可编辑设置，`app_meta.org_name` 这条要重看
  （单键 KV 撑不起「每个管理员一个单位」）。
- 若 TC-104 做完后备份恢复能一键跑通，S02 的「忘记密码」弹窗应从纯说明升级成
  带「从备份恢复…」主操作的引导，届时追加一节，不改本节。
