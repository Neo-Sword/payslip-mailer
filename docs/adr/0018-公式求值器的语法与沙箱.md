# ADR-0018 · 公式求值器：自己写递归下降解析器，不用模板引擎；求值用原始数值，格式化在求值之后

日期：2026-11-11 · 状态：accepted（TC-203 验收通过，评审记录见该 spec 文末）

## 背景

TC-203 做工资条项目的**公式求值器**。设计文档 ch.8「模板、Excel 与变量体系」把规格写死了：

> **formula** | 公式 | 表达式 | 只读计算列（如 实发 = 应发 − 扣款合计）
> **公式仅允许引用本行字段与 + - * / ( )，由 Rust 侧表达式求值器执行，禁止任意代码执行。**

以及「未知变量、空值、类型错误 → 渲染失败并拦截发送」。

S04 的原型里，「实发工资」这一行的公式写的就是 **「应发合计 + 扣款合计」** —— 注意
它引用的**不是某个字段的 key**，而是两个**汇总变量**。

于是有三件事必须定。

### 洞一：用什么求值？

TC-202 已经引入了 minijinja（沙箱模板引擎）。用它的表达式求值器不是不行，但：

- minijinja 的表达式语法**比设计文档宽得多**：过滤器（`|`）、测试、内建函数、
  属性访问、字符串操作……设计文档写的是「**仅允许**引用本行字段与 + - * / ( )」。
- 「禁止任意代码执行」这条红线，用 minijinja 是**靠约定**（先校验再用），
  用一个**语法就只有那几样**的求值器是**结构性**的 —— 它根本没有调用函数、
  访问属性、读环境变量、读文件的能力。

⇒ **自己写一个递归下降的算术表达式求值器**：语法只有

```
expr    := term (('+' | '-') term)*
term    := factor (('*' | '/') factor)*
factor  := '-' factor | primary
primary := 数字 | 标识符 | '(' expr ')'
```

零依赖（不引任何 crate）、零 I/O 面、零函数调用面。**「禁止任意代码执行」是结构性的。**

（顺带：TC-200 的 `domain/field.rs::check_formula` 那套手写的「括号配平 + 字符集 +
引用的 key 存在」检查，就是这个解析器的雏形。本卡把**语法判定的唯一权威**换成解析器 ——
两份语法规则并存，早晚漂移。）

### 洞二：求值用「格式好的字符串」还是「原始数值」？

TC-202 的模板渲染里，金额是**已经格式化过**的（`18,000.00`，带千分位）。
若把这种串喂给算术表达式，`18,000.00 + 3,200.00` 会直接解析失败。

⇒ **求值用原始数值（f64），格式化在求值之后**。

分工因此是清楚的：

```
原始数值（Excel 里读进来的 / 用户填的）
    → 公式求值（f64）
    → 按分四舍五入（2 位小数）
    → 格式化（千分位、¥、右对齐）← TC-202 的 format_amount 在这一层
    → 渲染进邮件 / 显示在表格
```

**精度**：内部用 `f64`，输出按分四舍五入。这是取舍 ——
严格的做法是用「分」为单位的整数，但公式里常出现系数（如 ×0.15），
整数分表达不了；引入十进制类型又要多一条供应链。
`f64` 在这个场景的误差远小于一分钱，**输出按分四舍五入**把误差挡在外面。

### 洞三：「汇总变量」在公式里是什么意思？

S04 的原型写「实发工资 = 应发合计 + 扣款合计」。这两个不是字段 key，是**汇总**：

- **应发合计** = 该行**正数**金额字段之和
- **扣款合计** = 该行**负数**金额字段之和（设计文档：扣款项「填负数，如 -2100」）
- **实发工资** = 应发合计 + 扣款合计

注意「**该行**」—— 是**这个成员这一行**的合计，不是整张表的合计
（整表合计是 S07 表格底部的「本页合计」，那是另一回事）。

⇒ 公式里可引用的标识符有两类：**字段 key** 与**汇总变量**（应发合计 / 扣款合计 / 实发工资）。

### 附带：TC-202 的内置变量漏了三个

设计文档 ch.8 的内置变量表是：

> 内置 {{姓名}} {{工号}} **{{邮箱}}** {{年月}} **{{年份}}** **{{月份}}** {{组名}} {{公司名称}}

TC-202 落了姓名/工号/年月/公司名称/组名，**漏了邮箱、年份、月份**（另加了两个
设计文档 ch.10 模板示例里用到的 回信邮箱 与 工资条表格）。

⇒ 本卡补齐这三个。TC-202 的评审记录里补一句说明。

## 决策

1. **自己写递归下降的算术表达式求值器**（`domain/formula.rs`）——
   语法只有数字、标识符、`+ - * / ( )` 与一元负号；
   **没有函数、没有属性访问、没有字符串、没有 I/O** ⇒「禁止任意代码执行」是结构性的。
2. **公式可引用的标识符** = 字段 key + 汇总变量（应发合计 / 扣款合计 / 实发工资）。
   未知标识符 → 错误（不是 0）。
3. **除以零 → 错误**（不是 Infinity、也不是 0）。
4. **求值用原始数值（f64）**；**格式化在求值之后**（TC-202 的 `format_amount` 在那一层）。
   输出按分四舍五入（2 位小数）。
5. **循环引用 → 错误**：A 的公式引用 B、B 引用 A（含 A 引用自己）。
   求值时带一个「正在算」的集合。
6. **引用非数值字段 → 错误**（文本字段不能参与算术）。
7. **TC-200 的 `check_formula` 改为委托给解析器** —— 语法判定的唯一权威是解析器，
   不留两份规则。
8. **补齐三个内置变量**：邮箱、年份、月份（设计文档 ch.8）。
9. **未知变量、空值、类型错误 → 失败并拦截**（设计文档 ch.8 原文）——
   与 TC-202 的「未解析变量不能设为默认」同一条防线的延续。

## 后果

**变简单的**：

- 公式语言小到能一口气讲完：**「一个数字、一个字段名、加减乘除和括号」**。
- 沙箱不需要论证 —— 求值器里根本没有能读文件/调函数的语法。
- 语法判定与求值是**同一份代码**：能求值的一定能解析，不能解析的一定报同一个错。

**要认的账**：

- **不支持条件**（`if`、比较、逻辑）。设计文档没要求，
  将来要支持时得重新审一遍沙箱口径（ADR-0017 后果段已记）。
- **f64 的精度**：内部计算可能有 1e-12 量级的误差，靠「输出按分四舍五入」兜住。
  若将来出现「必须精确到分」的合规要求，要换成整数分或十进制类型。
- **汇总变量的语义是「该行」**：同一张表里不同成员的应发合计不同 ——
  这正是公式列的用途（每人一行，各自算各自的实发）。

**重新评估的触发条件**：

- 若公式语言要支持条件或跨行引用（引用另一个成员的字段）——
  那就不是「本行字段 + 四则运算」了，沙箱与循环引用的边界都要重写。
- 若合规要求金额必须精确到分（不能靠四舍五入）→ 换数值类型。

## 附：本 ADR 与其他 ADR 的关系

- **红线 4**（模板引擎沙箱化）：本卡是它在公式求值上的对应实现，
  且比模板那侧更严（模板引擎有 I/O 面，公式求值器连函数调用都没有）。
- **ADR-0017**：两卡共用「先校验、后渲染」的次序；TC-202 的「变量白名单」
  在这里对应「公式可引用的标识符集合」。
- **ADR-0015**（字段是用户数据）：公式是用户自己写的，
  所以求值器必须**假设输入是恶意的**。
