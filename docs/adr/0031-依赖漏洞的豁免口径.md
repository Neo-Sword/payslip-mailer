# ADR-0031 · 依赖漏洞的处理口径：不可达即记录，不为看不见的漏洞升级存储引擎

日期：2026-11-12 · 状态：accepted

## 背景

TC-602 第一次真的把 `cargo audit` 跑起来（设计文档 ch.13 的发布门槛写着「无高危依赖漏洞」，
但此前**从未执行过**）。结果：

```
RUSTSEC-2026-0459  libsqlite3-sys 0.35.0  CVE-2026-119375  medium 6.8
    SQLite < 3.54.0：库文件旁边有一个 page size 不同的 -wal 文件时，
    查询会把进程内存里未初始化的页缓存字节返回出来（本地攻击者，需受害者打开这些文件）。
```

我们用的是 **`rusqlite` 的 `bundled-sqlcipher`**（ADR-0010：SQLCipher 源码内置，不链系统 SQLite），
所以问题不是「链了一个有洞的系统库」，而是「自己把 SQLite 编进来了」。

**升级能不能修掉？不能。** 公告自己写得很清楚：

> The `bundled-sqlcipher` feature builds SQLCipher instead of SQLite; in `0.39.0` and `0.39.1`
> it depends on `sqlcipher-src =419.0.6`, which bundles SQLite `3.53.4` **and is affected**.

也就是说：**连最新的 `libsqlite3-sys`（0.39.x）配 SQLCipher 也还是中招**，
真正的修复要等 `sqlcipher-src` 把 SQLite 提到 3.54.0 以上 —— 那不在我们手里。

那么「升级 rusqlite 0.37 → 0.41」买到什么？
SQLCipher 版本从旧号升到 419.0.6（SQLite 3.53.4），**这条 CVE 依旧在**。
代价却是实打实的：rusqlite 跨 4 个小版本（API 有破坏性变更）、
要求 Rust 1.89、SQLCipher 版本跳变要重验三百多条测试。
**为一个没修掉的漏洞付这个代价，不值。**

## 但它在我们的配置里到底能不能被触发

公告的触发条件是三个一起成立：

1. 受害者打开一个库文件；
2. 它的旁边有一个**兄弟 `-wal` 文件**；
3. 那个 `-wal` 的 page size 与库**不同**。

**第 2 条在我们这里不成立**：这个项目**从不开 WAL**，
`journal_mode` 一直是 `delete`（[ADR-0010](0010-SQLCipher用rusqlite-bundled走CommonCrypto.md) 第 5 条，
理由是「设计文档称 data.db 是唯一持久数据，WAL 的旁文件会打破这句话」，
而且 TC-104 的备份就是靠「整文件复制 data.db」成立的）。
`journal_mode = delete` 时 SQLite **根本不会创建 `-wal` 文件** ——
没有兄弟文件，攻击者就没有投放的载体。

这个前提不是「我们记得关掉它」，而是**一条可跑的断言**：
Rust 单测 `db_journal_mode_stays_delete` 每次门禁都跑，
它断言的就是 `PRAGMA journal_mode` 必须等于 `delete`。

## 决策

**一、`cargo audit` 进门禁与 CI，豁免只有一条，且写明理由。**

- 豁免写在仓库里的 `.cargo/audit.toml`（**可 grep、可评审**），不是命令行参数
  —— 命令行参数会被复制粘贴丢掉，配置文件不会。
- 豁免项：**只有 RUSTSEC-2026-0459 一条**，注释里写清「为什么不可达」与「依据是哪条测试」。
- 其余任何漏洞（含新出现的）一律**让门禁红**。

**二、不升级 rusqlite。**
理由如上：升级修不掉 SQLCipher 这一支的这条 CVE，却要付 API 破坏 + Rust 版本 + 三百多条测试重验的代价。
**等 `sqlcipher-src` 跟进 SQLite 3.54+ 时再升**（那时升级是有收益的）。

**三、豁免的依据必须是可跑的断言。**
「不可达」如果只是一句注释，它会在某次重构里悄悄失效 ——
比如有人为了并发把 `journal_mode` 改成 WAL（性能更好，备份会漏页，
但**测试会红**）。所以 `db_journal_mode_stays_delete` 留在单测里是这道豁免的**组成部分**，
不是可选项。

**四、另两条警告（unmaintained / unsound）不豁免，但也不拦门禁。**
`proc-macro-error`（unmaintained，无修复版本）与 `glib`（unsound，Linux GTK 链，
macOS 构建根本不编译它）默认只是警告 —— `cargo audit` 的退出码不受它们影响。
它们记在 TC-602 的评审记录里，等哪天 `glib` 那条影响到我们再单独处理。

## 后果

- 正面：发布门槛里那句「无高危依赖漏洞」从**没执行过**变成**每次门禁都执行**；
  豁免窄到一条、理由可 grep、依据有测试兜着。
- 负面：我们比「扫不到漏洞」多背一份责任：**豁免的判断是我做的**，
  判断错了就是真的漏了一个洞。所以依据必须是可跑的断言，而不是我的记忆。
- 记一笔事实：`cargo audit` 的 advisory 数据库在本机**拉不动**
  （github.com 的 git 协议与 codeload 在本网络都不通，SSH 正常），
  所以本地用手动克隆的 `~/.cargo/advisory-db` + `--no-fetch`，
  CI 里走正常拉取。`scripts/audit.sh` 会把这件事**明说**，不装作是最新的。

## 重新评估的触发条件

- `sqlcipher-src` 跟进 SQLite 3.54+ → 升级 rusqlite，**撤掉这条豁免**。
- 有人要开 WAL（为了并发）→ 本豁免的前提消失，**必须先解决备份的整文件复制问题**，
  或者把 WAL 文件纳入备份范围并重新评估。
- 出现另一条**可达**的漏洞 → 立刻处理，不进豁免表。
