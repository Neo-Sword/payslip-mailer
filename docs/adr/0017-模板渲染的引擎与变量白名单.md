# ADR-0017 · 模板渲染：minijinja（不开 loader）+ 变量白名单 + 字段变量用 key 不用显示名

日期：2026-11-11 · 状态：accepted（TC-202 验收通过，评审记录见该 spec 文末）

## 背景

TC-202 做 S10「中文邮件模板编辑器 + 变量白名单」。设计文档给了模板的样子：

> 变量随 S04 字段配置动态生成；未知变量或空值将在发送前被拦截。
> …渲染由 **minijinja 沙箱**执行。
> 变量面板：{{姓名}} {{工号}} {{年月}} {{公司名称}} {{组名}} {{字段.基本工资}}
> {{应发合计}} {{扣款合计}} {{实发工资}} {{工资条表格}}
> 交互要点：右预览默认用「第一位成员」渲染；变量面板点击即插入；
> **未解析变量高亮并阻止设为默认**。

另外 ch.10 的防错机制第三条：

> ③ 变量完整 — 模板中所有变量必须能解析且非空；缺失字段直接拦截，
> **绝不发出「{{实发工资}}」字面量**。

有四件事要在写代码前定。

### 洞一：minijinja 的哪个 feature 组合？

minijinja 3.1.0 的 feature 是逐个开关，每个开关对应一个能力面。红线要求
「模板引擎沙箱化，禁止文件读取 / 系统调用 / 访问环境变量」，所以：

| feature | 要不要 | 理由 |
|---|---|---|
| `loader` | **不要** | 它是「从文件加载模板」的能力。**不开它，「从磁盘读模板」这条路在结构上就不存在** —— 沙箱不是靠约定，是靠没开那个开关 |
| `unicode` | 要 | 变量名是中文的（`{{姓名}}`）。不开它 minijinja 的 lexer 只认 ASCII 标识符，中文变量名直接报 `syntax error: unexpected character`（实测） |
| `serde` | 要 | 要构造 `{{字段.xxx}}` 这种嵌套 map。serde 已经是项目依赖，**零新增 crate** |
| `builtins` | 要 | 内置过滤器与函数（金额格式化要用） |
| `debug` | 要 | 渲染错误的可读信息（给界面高亮用） |

实测结论（`examples/` 里跑过、跑完删掉）：
`{{姓名}}` → 「张三」✓；`{{字段.base_salary}}` → 「18000.00」✓；
`{{工资条表格}}`（用 `Value::from_safe_string` 放进去）→ 不被转义 ✓；
`{{不存在}}`（`UndefinedBehavior::Strict`）→ **报错** ✓。

依赖代价：**只多 `unicase` 一个纯 Rust crate**（`unicode-ident` 本来就在锁文件里）。

### 洞二：字段变量按显示名还是按 key？

设计文档的变量面板写 `{{字段.基本工资}}` —— 用的是**显示名**。

但 S04 允许改显示名（TC-200 的 `update_field`）。于是：

- 用显示名 → HR 改个名（「基本工资」→「底薪」），**所有老模板立刻全部失效**，
  而且失效信息是「未解析变量」，HR 根本不知道是自己改的名。
- 用 key（`base_salary`）→ 改显示名不影响模板；改 key 本来就禁止（TC-200 已钉住 key 不可改）。

⇒ **字段变量用 key：`{{字段.base_salary}}`**。

界面上给 HR 看的是**显示名**（「基本工资」），但模板里写的是 key，点一下插入。
显示名与 key 的对应关系由界面负责（插的是 key，显示的是名字）。

这是与设计文档的一处**字面偏离**，理由如上。写进 spec 的范围里。

### 洞三：「非空」怎么判？工号是可选的

防错机制说「所有变量必须能解析且非空」。但**工号在成员表里是可选的**
（ch.6：`employee_no 可选，用于 Excel 精确匹配`），而且 S06 的原型里工号也不是必填。

若照字面「非空」执行，一个没填工号的成员就永远收不到信 —— 而工号本来就不影响工资条。

⇒ **「非空」按「这个变量是否必填」判定**：

- **字段变量**：必填与否就是 TC-200 的 `required` 列 —— 同一份数据，不用另设一套；
- **内置变量**：姓名、年月、实发工资必填；工号、组名、回信邮箱允许空
  （组名允许空是因为「直接勾选成员私发」的场景没有组）。

「不可解析」（白名单里根本没有这个变量）与「解析出来是空」是**两件事**：

- 不可解析 → **模板级**拦截：不能保存为默认（S10 原话「未解析变量高亮并阻止设为默认」）；
- 值为空 → **发送前**拦截：拦下这一个成员，不发给他（而不是整批停下）。

### 洞四：试发给自己做不做？

S10 的界面有「试发给自己」，交互要点写「『试发给自己』不写入正式发送日志」。

但**试发要真的发一封邮件** ⇒ 要 SMTP ⇒ 真实发件账号（TC-500，现在 blocked）。

⇒ **TC-202 不做真发**：按钮位置留着，文案说清「需要先在设置里配置发件邮箱」。
「试发不写入正式发送日志」这条属于发送侧（TC-402/403 的 `send_jobs` 表），归那边。

## 决策

1. **渲染引擎：minijinja 3.1**，feature = `builtins, debug, serde, unicode`，
   **不开 `loader`**（红线：结构上没有读文件的路）。
2. **未知变量 → 渲染报错**（`UndefinedBehavior::Strict`），并**阻止设为默认**；
   错误信息里带变量名，界面高亮它。
3. **字段变量用 key**：`{{字段.base_salary}}`。显示名只是界面上的可读标签。
4. **变量白名单 = 两份**：
   - 「新建模板可选」= `fields::selectable_variables`（**未停用**的字段 + 全部内置变量）；
   - 「渲染历史模板要认」= `fields::all_keys`（**含已停用的**）+ 全部内置变量。
   （与 TC-201 / TC-200 的口径一致：这两份名单不是一回事。）
5. **空值按「是否必填」判定**：字段看 `required`；内置变量各自声明必填与否。
6. **试发不做**（要 SMTP → TC-500）；界面留位置并说明。
7. **text/plain 兜底自动生成**（表格转纯文本对齐）——
   设计文档的理由：「避免部分客户端把纯 HTML 邮件判为垃圾邮件」。
8. **HTML 内联 CSS + 中文字体栈** `PingFang SC, Microsoft YaHei, sans-serif`（设计文档原文）。
9. **预览用示例数据**（设计文档：「右预览默认用『第一位成员』渲染」；
   真实工资数据在 TC-303 才有，本卡用示例数据并在界面上标明）。
10. **初始化时写入默认模板**（设计文档 S10 的「标准中文模板」，
    正文取设计文档 ch.10 的「中文模板示例」原文）——
    那是**设计文档的原文**，不是我们编的文案；公司名与回信邮箱是模板里的变量，
    等业务方给了值就自动渲染出来。

## 后果

**变简单的**：

- 「变量面板点一下就插入」能保证插入的**一定是白名单里的**（界面的按钮直接来自白名单）。
- 未知变量在**保存/设为默认**时就被拦下，不会等到发出去才发现
  （防错机制③的核心：绝不发出「{{实发工资}}」字面量）。
- 沙箱的性质是**结构性的**：没开 loader 就没有读文件的能力，
  不依赖「我们记得别用它」。

**要认的账**：

- **minijinja 默认允许表达式求值**（实测 `{{ 1 + 1 }}` → 2）。
  红线管的是「文件读取 / 系统调用 / 环境变量」，这三条都满足；
  但模板里能写算术表达式这件事要在文档里说清楚。
- **字段变量用 key 而非显示名**，与设计文档的字面不同。
  代价是 HR 看模板源码时不直观（界面上的变量面板显示显示名，插的是 key）。
- 模板正文里的**公司名与回信邮箱是变量**，模板本身不含具体公司信息 ——
  这是好事（换公司不用改模板），但首启时预览里那两项是空的。

**重新评估的触发条件**：

- 若 TC-303 的真实数据到位后，预览要换成「第一位成员的真实数据」——
  那是替换示例数据源，不改渲染逻辑。
- 若将来要支持「模板里写条件判断」（如「扣款 > 0 才显示某段」），
  minijinja 的条件语法直接可用，但那时要重新审一遍沙箱口径。
