# ADR-0019 · 月份账套：快照在「进入 ready」时冻结、ready 仍可编辑、解锁回 draft 且留修订记录

日期：2026-11-12 · 状态：accepted（TC-300 验收通过，评审记录见该 spec 文末）

## 背景

TC-300 做 S07「月度工资数据」的账套本身：状态机、字段快照、只读保护。
设计文档 ch.5「状态机」写死了月份账套的状态迁移：

> 月份账套 `salary_periods.status`
> 草稿 draft → 待发送 ready → 发送中 sending → 已发送 sent → 已归档 archived
> **发送中/已发送状态禁止编辑工资数值**；如需纠错，走「**解锁 → 生成修订记录 → 仅对未发送者补发**」。

ch.6 的表定义：

> `salary_periods | id, year_month, status, field_snapshot, locked_at | UNIQUE(year_month) |
> field_snapshot 冻结当月字段定义，防止事后改字段导致历史错位`

`domain/period.rs` 是 TC-000 时代留下的状态机骨架，文件里写着
「状态机契约先行：要到 P3-01『月份账套状态机』才接进 Command 层」——
本卡就是那张卡，那两处 `#[allow(dead_code)]` 到此删掉。

有四件事要在写代码前定。

### 洞一：快照什么时候冻结？

设计文档只说「冻结当月字段定义」，没说**什么时候**冻结。

- **创建时就冻结**：HR 还在草稿阶段配字段（加一个「季度补贴」），快照却已经钉死了 →
  新字段进不了这个月的表。**不可接受**。
- **一直跟随，到 ready 才冻结** —— 草稿期间界面显示的是**当前**的字段配置；
  进入「待发送」（数据要发出去了）的那一刻，把当时的字段定义**写成快照**并钉住。

⇒ **冻结点在 draft → ready**。之后无论 S04 怎么改字段配置，这个月的表头与列都不动。

### 洞二：界面显示的列，从哪儿来？

既然草稿用当前配置、ready 起用快照，就得有个明确的规则，否则界面会「一会儿一套、一会儿另一套」：

- **状态是 draft → 用当前字段配置**（还没冻结）；
- **状态是 ready/sending/sent/archived → 用快照**（已冻结）。

冻结那一刻，快照里存的就是**当时**的字段配置 —— 于是 ready 与之后的显示，与冻结瞬间看到的完全一致。

### 洞三：ready 能不能编辑？

`domain/period.rs` 现在写的是「`is_editable` 只在 draft 为真」——
但设计文档的原话是「**发送中/已发送**状态禁止编辑工资数值」，**没提 ready**。

ready 的含义是「校验通过，等待发送」—— 还没发，事后再改一个数完全正常
（改完 S11 的校验会重跑）。把 ready 也禁掉，是 TC-000 时代凭感觉写的，
与设计文档的字面不符。

⇒ **`is_editable` = draft 或 ready**；只读的是 sending / sent / archived。
本卡修掉它，并改掉那条对应的旧测试。

### 洞四：「解锁」是什么，怎么留痕？

设计文档：「如需纠错，走『**解锁 → 生成修订记录 → 仅对未发送者补发**』」。

三步里，**第三步（仅对未发送者补发）是发送侧**（P4 的 TC-402，
它才有 `send_jobs` 能判断「谁已经收到了」）。本卡做前两步：

- **解锁**：已发送的账套回到 draft（可以再编辑）；
- **生成修订记录**：在 `audit_log` 里写一条（设计文档 ch.6 有这张表：
  「记录登录、改配置、导入、发送、**解锁**、导出」）。

解锁**必须**留下修订记录 —— 这是「可举证」的一部分（ch.9 合规要点：
「电子工资条有效性依赖证据链」）。没有记录的解锁等于偷偷改历史工资条。

## 决策

1. **冻结点 = draft → ready**（洞一）。冻结时把当时的字段配置写成快照。
2. **显示的列**：draft 用当前配置；ready 起用快照（洞二）。
3. **`is_editable` = draft | ready**；只读的是 sending / sent / archived（洞三）。
   —— 这修正了 TC-000 时代留下的旧口径。
4. **解锁 = sent → draft**，且**必定**在 `audit_log` 写一条修订记录（洞四）。
   第三步「仅对未发送者补发」归 TC-402。
5. **`year_month` 存 TEXT `'YYYY-MM'`**（如 `2026-10`）：可读、且按文本排序就是按时间排序。
   设计文档只说 `UNIQUE(year_month)`，没定格式。
6. **快照存 JSON 数组**，每个元素是这个字段的
   `key / label / data_type / formula / required / visible / sort_order`。
   JSON 是最自然的：字段定义没有独立的表（它就是 `salary_fields` 的行），
   而 `salary_records.values_json` 也是 JSON（同一套「键值袋」的做法）。
7. **`locked_at`** 记的是「进入 sending 的时刻」—— 那一刻开始，数据被锁住等发送结果。
8. **`audit_log` 表本卡建**（设计文档 ch.6 列了它，但之前没有卡碰过它）：
   `id / action / target / detail_masked / at`。

## 后果

**变简单的**：

- 字段配置改了，**历史月份不动** —— 这是「防止事后改字段导致历史错位」的实现。
- 一次快照 = 那个月「到底有哪些列、怎么算」的完整交代，不必回溯当时的配置。
- 解锁必留修订记录 ⇒ 纠错也是可举证的。

**要认的账**：

- **ready 之后字段配置与快照会不一致**（HR 改了字段，但历史月份用旧的）。
  这是**对的**（历史就该是历史的），但界面上要能看出来 ——
  S07 的月份视图里，ready 之后的月份显示的是快照里的列名。
- **`audit_log` 是全库增长最快的表**（每次解锁一条）。本卡不做清理策略；
  它增长得慢（解锁是罕见操作），真要清理是 TC-104 那类运维话题。
- 解锁只回到 draft，**不自动重新冻结** —— 重新冻结要再次进入 ready。

**重新评估的触发条件**：

- 若将来支持「一份模板多个语言版本」→ 快照的粒度要从「字段定义」扩到「模板 + 字段定义」。
- 若要支持「同一月份多个账套」（例如分批发薪）→ `UNIQUE(year_month)` 要放开，
  快照的键也要带上账套 id。

## 附：本 ADR 与其他 ADR 的关系

- **红线 8**（字段一旦被历史数据引用只能停用不能删除）：本卡是它在**月份**这一层的对应物 ——
  停用影响的是「以后」，快照固定的是「当时」。
- **ADR-0015**（字段是用户数据）：正因为字段是用户数据、随时会改，
  才需要快照把「当时」钉住。
- **ADR-0018**（公式求值器）：快照里存的是**公式源码**，不是算出来的值 ——
  值属于 `salary_records`（TC-303），公式属于字段定义。
