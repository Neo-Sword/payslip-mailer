# ADR-0004 · 错误词表先行，文案由 Rust 侧承载

日期：2026-11-11 · 状态：accepted

## 背景

设计文档 ch.12 S15 规定「错误码统一由 Rust `error.rs` 映射为中文文案」，并要求每条错误提示
给出**三要素：发生了什么 / 影响范围 / 下一步**。原型 S15 的示例文案就是这个格式：

> SMTP 535 认证失败 —— 授权码可能已过期。已中止本次发送，未产生重复邮件。请更新后仅重试失败项。

问题是**什么时候**把这些错误码定出来。P1–P4 每张卡都会撞上自己的失败分支，
最省事的做法是「用到再加」。

## 决策

1. **单一来源**：错误只在 Rust 侧定义（`src-tauri/src/error.rs`），前端不维护自己的错误码表，
   只做展示与「下一步」按钮的路由。
2. **词表先行**：一次性按设计文档把 P1–P5 会用到的错误码定齐（当前 15 个变体），
   不等各任务卡逐个发明。
3. **文案即 `Display`**：每个变体的 `#[error(...)]` 直接写成给用户看的中文三要素文案，
   不引入 i18n 表。本项目不做多语言，多一层映射只会让「日志里的码」和「屏幕上的话」对不上。

## 为什么先行，而不是用到再加

错误码是**对外契约**，不只是内部实现：

- 发送日志（TC-403）按错误码分类导出；
- 一页安装说明（TC-600）要写「看到 535 该怎么办」；
- 中断恢复（TC-402）要靠错误类别判断「哪些算未成功、可以补发」。

零散添加会让同类失败在不同卡里有不同码名，日志口径与安装说明都跟不上，
而这三样东西一旦发出去就不能改。

## 代价（必须记账）

1. **暂时构造不出来的变体**要靠 `#[allow(dead_code)]` 压住告警，
   代价是编译器不再替我们区分「将来要用」和「真的忘了接」。
   所以标注上写了 `TODO(P1–P4)`，并在 `error.rs` 顶部列明每个码由哪个阶段接线；
   **全部接线后必须移除该标注**，让死码重新变成编译告警。
2. 改一个错误文案要重编 Rust 侧。桌面应用每次本来就要重编，无实际损失。
3. 文案里的动态参数（如 `Locked(u64)` 的剩余秒数）只能是**非敏感**值。

## 与红线的关系

红线要求「工资数值不进日志与错误上报」。`Database(String)` / `Io(String)` / `Internal(String)`
这类携带上下文的变体，payload 只允许放**字段名、文件名、行号**，不允许放金额。
编译器管不了这件事，所以它必须作为可证伪的验收标准写进 TC-403（导出日志里 grep 金额应为 0 命中），
不能只靠 review 时留意。

## 重新评估的触发条件

- 若某阶段接线时发现词表里某个码永远构造不出来 → 删掉它，别留着当装饰。
- 若需要多语言 → 届时把文案从 `Display` 拆到码表，另写 ADR。
