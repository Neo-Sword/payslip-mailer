# ADR-0023 · 发送编排的速率与重试：令牌桶、指数退避与错误分类

日期：2026-11-12 · 状态：**accepted**（TC-400 验收通过，2026-11-12）

## 背景

TC-400 起 P4 发送链路。设计文档 **ch.7「邮件发送引擎」** 把发送的目标写得很直白：
「发送是最容易出事故也最容易被邮箱厂商限流的环节。设计目标：**逐人独立、可中断、可重试、可举证**」。
速率与重试的规定：

> 20–30 封 / 分钟（默认 30）—— 飞书邮箱保守值，可在设置页调整
> 3 —— 最大重试次数；指数退避 30s / 2min / 10min
> 每封一个收件人 —— 禁止 CC/BCC，物理隔离工资数据

**错误码处置**（ch.7）：

> 临时失败 421/451/452/4xx 限流 → 退避重试，自动降速 50%，UI「邮箱服务器繁忙，已自动降速」
> 永久失败 550/553/收件人不存在 → 标记 dead 不重试，UI「请核对该成员邮箱后单独补发」
> 认证失败 535/534 → 立即中止整批不重发，跳转 SMTP 设置
> 网络中断 连接超时/DNS → 暂停队列保留现场可「继续」

**发送编排六步**（ch.7）：冻结快照 → 逐人渲染 → 三重核对 → 入队限速 → 结果落库 → 收尾。

本卡做什么、不做什么：**本卡是编排的骨架（限速、重试、错误分类、批次与任务的持久化），
不含真实 SMTP** —— 发信的 socket 是 TC-500 的事（那时才引 lettre）。
这样切的理由：限速与重试是**纯策略**，可以在没有网络的情况下完整测试
（时钟注入）；等 TC-500 接上 lettre，策略层一行不用改。

有五件事要定。

### 洞一：令牌桶怎么计时？

令牌桶的教科书实现按**墙上时钟**算补充速率。但测试不能真等 2 秒、
生产也不该在每次发信前 `sleep`（那会把 UI 卡住）。

⇒ **令牌桶只做「判定」，不做「等待」**：`try_acquire(now)` 返回
「现在能不能发 + 下一封要等到什么时候」。**谁sleep、睡多久由调用方决定**
（编排器在 batch 的发送循环里 sleep；UI 层永远不阻塞）。
时钟由调用方传入（`now_millis`）—— 测试注入假时钟，生产传真时钟。

**速率的存储**：设置页可调（ch.7「可在设置页调整」）。
v1 存在 `app_meta`（TC-102 建的键值表，空闲阈值就在那里），
键 `rate_per_min`，默认 30。单独的设置界面是 TC-500（SMTP 设置页）的事，
本卡只保证「读出来的速率真的被令牌桶用了」。

### 洞二：降速 50% 是什么意思？

「临时失败 → 退避重试，**自动降速 50%**」。两种解释：

- **批次级降速**：这个批次的令牌桶速率减半（30 → 15 封/分），
  后续的批次恢复默认。
- **全局降速**：改 `rate_per_min` 本身（30 → 15），下次发信也慢。

⇒ **批次级降速**。理由：临时失败是**这一次**的拥塞信号
（「邮箱服务器繁忙」），不是这台邮箱永久变慢了；
把用户配置改掉等于让一次拥塞永久改变行为 —— 那是用户该做的决定，不是系统的。
批次结束速率作废；连续临时失败时**不叠加**（已是 50% 就不再减 ——
减到 0 就永远发不完）。

### 洞三：错误分类的边界

SMTP 码 → 处置的映射（ch.7 给了四类）。落成**一个纯函数**
`classify(smtp_code: Option<u16>, kind: ErrorKind)`：

- **认证失败**（535/534）→ `Abort`：立即中止整批，不重发。它是凭据坏了，
  重试只会被服务器继续拒，还会累计失败计数触发邮箱风控。
- **临时失败**（421/451/452、其它 4xx）→ `Retry`：退避重试。
- **永久失败**（550/553/541/5xx 除 535/534 外）→ `Dead`：不重试。
  「收件人不存在」重试一万次也不存在。
- **网络中断**（连接层错误，没有 SMTP 码）→ `Pause`：暂停队列保留现场，
  用户可「继续」。
- 其余未知的 5xx → **保守归 `Dead` 还是 `Retry`？** 未知 5xx 归 **`Dead`**
  —— 5xx 是服务器**拒绝**（4xx 才是「稍后再试」）；拒绝的原因多半不会自己好。
  未知 4xx 归 `Retry`。

**2xx → 成功**。3xx 是中间态（继续输入），SMTP 客户端不该把它交给应用层；
真收到了归 `Retry`（保守）。

### 洞四：重试状态机放哪一层？

设计文档 ch.5 的 `send_jobs.status`：
`queued → sending → success / failed → retrying(≤3) → dead`。

这里有个含糊：`failed` 与 `retrying` 与 `dead` 的关系。
**状态要能回答「这一封现在怎么样、下一步是什么」**：

- `queued`：排队中，还没轮到。
- `sending`：正在发（进程拿着它在发，崩溃后恢复时它是「存疑」——见 TC-402）。
- `success`：发成功了（终态，记录 SMTP 码与时间）。
- `retrying`：失败了，**排定**了下一次重试时间（`next_attempt_at`）。
- `dead`：重试次数用完或永久失败（终态）。

⇒ `failed` 不作为**存储状态**（它是事件不是状态 —— 失败的那一刻立即变成
`retrying` 或 `dead`，中间不存在「失败了但还没决定怎么办」的记录）。
状态机：`queued → sending → success | retrying | dead`；`retrying → sending`（到点重试）。
`retrying` 次数 ≤ 3，第 3 次失败进 `dead`。

### 洞五：批次与任务的表结构

ch.6 已定 `send_batches`（批次）与 `send_jobs`（逐封）。本卡建表（迁移 0008），
字段照设计文档：

- `send_batches`: id, period_id, template_id, scope_json, total, success, failed,
  started_at, finished_at + **status**（ch.5 的批次也要能暂停/中止）+
  **rate_per_min**（批次开始时的速率 —— 降速是这个批次自己的事）。
- `send_jobs`: id, batch_id, member_id, to_email, subject, checksum, status,
  attempts, smtp_code, error_code, idempotency_key, sent_at + **next_attempt_at**
  （`retrying` 的排定时间）。
- **`send_jobs` 不存正文**（ch.6 明写「不存渲染后的正文（脱敏），仅存摘要与结果」）。
  `subject` 是模板渲染后的主题 —— 主题含「2026-10 工资条」这类不算工资数值，
  但为稳妥起见 v1 存**模板名**而不是渲染后的主题？⇒ 渲染归 TC-401/402，
  本卡的 `subject` 字段先空着不用（建列是为了不必再迁移一次）。

**scope_json 记范围**（组/成员 id 列表）—— 它含成员 id，不含姓名邮箱数值，
可以存。

## 决策

1. **令牌桶只判定不等待**：`try_acquire(now_millis) → TryAcquire { allowed, retry_after_ms }`。
   时钟由调用方注入；速率读 `app_meta.rate_per_min`（默认 30）。
2. **降速是批次级的**：临时失败把本批次的桶速率减半，不叠加、不写回配置、批次结束作废。
3. **错误分类是一个纯函数**：`classify(smtp_code, kind) → Abort | Retry | Dead | Pause`。
   映射：535/534 → Abort；421/451/452/其它 4xx → Retry；550/553/其它 5xx → Dead；
   无码的连接层错误 → Pause；2xx → 成功；未知 3xx → Retry（保守）。
4. **job 状态机**：`queued → sending → success | retrying | dead`；`retrying → sending`。
   **没有 `failed` 存储态**（失败即刻变成 retrying 或 dead）。
   重试 ≤ 3 次，退避 30s / 2min / 10min（第 n 次失败后等 `BACKOFF[n-1]`）。
5. **迁移 0008 建 `send_batches` 与 `send_jobs`**（字段照 ch.6，加 status、
   rate_per_min、next_attempt_at）；`send_jobs` 不存正文，`UNIQUE(idempotency_key)`
   现在就建（TC-402 用它）。
6. **每封完成即持久化**（ch.7 可中断设计的基础）：发送循环每结束一封
   （无论成败）立即写库，不是批次结束才写。
7. **批次状态机**：`running → paused | aborted | finished`；`paused → running`。
   网络中断 → `paused`（保留现场）；认证失败 → `aborted`；全部处理完 → `finished`。

## 后果

**变简单的**：

- 限速与重试是纯策略 + 注入时钟 ⇒ 完整测试不需要网络、不需要 sleep。
- 错误分类是一个函数 ⇒ TC-500 接 SMTP 时只需把 lettre 的错误映射成
  `Option<u16> + kind`，处置逻辑一行不改。
- 每封即持久化 ⇒ TC-402 的中断恢复有了现成的基础（恢复 = 从库里读未完成的 job）。

**要认的账**：

- **本卡发不出真邮件**：编排骨架跑在「假发送器」上（测试注入）。
  TC-500 接 lettre 后才第一次发出真的。
- **降速不写回配置**：用户看到批次慢了但设置页的数字没变 —— 那是本来的设计
  （一次拥塞不该永久改配置）。UI 要能显示「本批次已降速」。
- **`subject` 列先空着**：渲染后的主题归 TC-401/402 落。建列只为避免再迁移。

**重新评估的触发条件**：

- 若要支持并发发送（同时开多条 SMTP 连接）→ 令牌桶要按连接数发牌，
  重试的排定也要按连接分开。
- 若要支持「重试次数可配」→ BACKOFF 表要进设置。

## 附：本 ADR 与其他 ADR 的关系

- **红线 3**（无二次确认不群发）：批次创建的入口在 TC-402（发送编排带确认），
  本卡只提供「批次如何被限速与重试」的机制。
- **红线 4**（失败重试只针对未成功的 job）：`retrying` 状态本身就是「未成功」的清单；
  「仅重试失败项」= 把 dead 且可重试原因的 job 重新入队（TC-402）。
- **ADR-0022**（checksum）：`send_jobs.checksum` 就是 TC-303 存的行级 checksum ——
  TC-401 的内容一致核对拿它比对。
