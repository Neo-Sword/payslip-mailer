# ADR-0022 · 工资记录的逐格编辑：单格保存、公式重算与校验列

日期：2026-11-12 · 状态：**accepted**（TC-303 验收通过，2026-11-12）

## 背景

TC-303 做 S07「月度工资数据」的记录本体。设计文档对这一屏的规定散在三处：

**ch.12 S07 原型**：

> 共 42 条记录 · 校验通过 41 · 待处理 1
> 金额列等宽右对齐；金额可双击编辑并自动重算公式列；有校验警告时「前往预览核对」仍可点，
> 但 S11 会拦截该成员进入发送范围
> 公式列由系统计算，不可直接编辑
> 本页合计　应发 ¥ 93,300.00　扣款 ¥ -13,690.00　实发 ¥ 79,610.00
> 赵六那行「个税」是「—」，「实发工资」照样算出 13,100.00（校验列标「个税缺失」）
> 自动保存于 09:31

**ch.6 核心表**：

> salary_records | id, period_id, member_id, values_json, checksum, source |
> UNIQUE(period_id, member_id) | values_json 存键值；checksum 用于防错校验

**ch.5 状态机**：

> 发送中/已发送状态禁止编辑工资数值；如需纠错，走「解锁 → 生成修订记录 → 仅对未发送者补发」

TC-300 已定 `is_editable = draft | ready`（设计文档只禁 sending/sent）；
TC-302 已建 `salary_records` 表并定下「空 = 没有这一项」「行求值唯一权威在
`domain/record.rs`」。本卡是这套口径的**第一个逐格编辑消费者**。

有四件事要定。

### 洞一：一次编辑保存多少？

S07 说「自动保存于 09:31」—— 这暗示逐格保存（改一格存一格），
不是「整表提交」。逐格保存对 HR 的意义：改完一格就知道这一格有没有问题
（必填缺失、公式重算失败），不用攒到最后一次性爆出一堆错。

⇒ **单格保存**：前端每改一格 → 一个 Command 调用 → 更新那一格 →
后端**整行重算公式列** → 返回这一行的新状态（含重算后的公式列值与校验结果）。

「整行重算」是因为公式列可能引用任意字段 —— 改了 `base_salary`，
`net_pay` 就得跟着变；公式套公式（net_pay 引用另一个公式字段）也要级联。
`domain::record::evaluate_row` 本来就是按整行算的，正合适。

**自动保存与显式保存**：v1 只做**显式保存**（单元格失焦或回车时保存），
不做防抖自动保存。理由：自动保存需要处理「连续快速改多格」的竞态
（两次保存的顺序、失败后的回滚提示），而单格保存本身已经是小粒度，
显式触发的心智负担最低。S07 的「自动保存于 09:31」在本卡落地为
**保存成功后的提示**（「已保存」），不是后台定时器。

### 洞二：校验列显示什么？

S07 的校验列有「通过」与「个税缺失」两种。赵六行没有个税但实发照样算出 13,100
—— 所以「个税缺失」**不是错误**（没有拦住这一行），是**提醒**。

校验列的规则（与 TC-302 的三档对齐，但语义是「这一行能不能进发送范围」）：

- **必填字段缺失**（`required = true` 且该行没有这个键）→ 警告，显示「<显示名>缺失」。
  数值型公式列（如 `net_pay`）由系统算，**永远有值**，不参与必填检查
  —— 「实发工资缺失」这种话没有意义。
- **公式重算失败** → 错误（这一行的钱算不出来，绝不能发）。
- 其余 → 「通过」。

**「待处理」的判定**：校验列不是「通过」的行数。S07 头部的
「校验通过 41 · 待处理 1」就是按这个数出来的。

**必填缺失不拦编辑**（能保存），只拦**发送**（TC-401 的范围过滤）。
这和 TC-302 的「警告不拦入库、拦发送」是同一条道理：HR 在编辑阶段
经常是「先录入，最后统一补」，中途拦保存只会逼人乱填一个 0。

### 洞三：合计行算的是什么？

S07 表底写「**本页**合计」。但分页在 v1 没做（42 人一屏放得下，
设计文档的数据表格规范支持横向滚动而非分页）⇒ v1 的「本页」= **整月**。

三个合计的口径与 TC-203 的行级汇总**不同层**：

- 行级（TC-203）：应发合计 = **该行**正数金额之和。
- 表级（本卡）：应发 = 所有行的正数金额字段之和；扣款 = 所有行的负数金额之和；
  实发 = 应发 + 扣款。
- **公式列不进表级合计**（否则实发会被算两遍 —— 行级公式列已经是和了）。

⇒ 表级合计从**非公式数值字段**直接累加。实发 = 应发 + 扣款（与行级的
`NET_PAY` 口径一致：正数之和 + 负数之和）。

### 洞四：编辑权与留痕

TC-300 已把 `editable` 放进 `Period`（draft | ready 可编辑）。
本卡加两条：

- **写入时再查一次状态**（不能只靠前端禁用 —— Command 层是唯一关卡）。
  `sending` / `sent` / `archived` 状态下 `update_cell` 直接拒绝（READ_ONLY 口径的
  业务版，用 ValidationError 而不是 ReadOnly —— 库本身没坏，是这个月的账被锁了）。
- **解锁后的编辑不再逐次留痕**：ADR-0019 已经在 `sent → draft` 时写了一条
  修订记录（audit_log）。之后的逐格编辑是修订的**执行过程**，
  每格都写一条 audit 会把审计日志淹没（改 42 行 × 10 列 = 420 条）。
  ⇒ 逐格编辑**不写 audit_log**；审计的粒度是「导入」（TC-302）、
  「解锁」（ADR-0019）、「导出」「发送」这些**成批动作**。

**checksum 什么时候算**：每次单格保存后整行重算 checksum
（`record::checksum(邮箱 + values_json)`）。它是 TC-401「内容一致」核对的基础
—— 保存时算好存着，发送前比对。

**source 的语义**：`manual`（逐格编辑）与 `import`（TC-302）。
单格保存把已有记录的 source **保持不变**还是改成 `manual`？
⇒ **保持不变**。source 记的是「这一行最初怎么来的」，一行内某格被手改
不改变「这行是导进来的」这个事实；真要追「哪格被手改过」，那是修订记录的事（v2）。

## 决策

1. **单格保存**：改一格 → 一个 Command → 更新该格 → 整行重算公式列 →
   返回这一行的新状态。显式保存（失焦/回车触发），不做后台自动保存。
2. **行求值走 `domain/record::evaluate_row`**（唯一权威）；
   保存失败（公式算不出来）→ 拒绝保存并报错，**旧值保留**。
3. **校验列**：必填字段缺失（非公式列）→ 警告「<显示名>缺失」；
   其余「通过」。表头统计「校验通过 N · 待处理 M」按它算。
   必填缺失**不拦保存**，只拦发送（TC-401）。
4. **表级合计 = 整月**（v1 无分页）：应发 = 非公式数值字段的正数和、
   扣款 = 负数和、实发 = 应发 + 扣款。公式列不进表级合计。
5. **编辑权在 Command 层再查一次**：`sending/sent/archived` 拒绝写入。
6. **逐格编辑不写 audit_log**（粒度是成批动作，见洞四）。
7. **单格保存后整行重算 checksum**；已有记录的 `source` 保持不变。
8. **整行删除不做**：删一行 = 这个成员这个月没有记录（`values_json` 空对象
   也不留 —— 直接 DELETE）。这是「给错了人要撤掉」的场景。
   删除也在 editable 状态下才允许。

## 后果

**变简单的**：

- 单格保存的返回就是这一行的新状态 ⇒ 前端不用整表刷新，
  TC-401 的「预览核对」读到的永远是已保存的最新值。
- 校验列与 TC-302 的警告共用「必填缺失」的判定 ⇒ 两处看到的问题一致。

**要认的账**：

- **不做自动保存**：「自动保存于 09:31」落地为保存成功的提示。
  改完没点保存就关窗 → 那一格没存上。表格的编辑框要在失焦时保存来兜住大多数场景。
- **逐格编辑不留痕**：审计粒度是成批动作。哪一格被谁改过，v1 查不到。
- **「本页合计」= 整月合计**：将来做分页时要改成真正的「本页」。

**重新评估的触发条件**：

- 若要做自动保存 → 竞态处理（连续快速改多格）要重新设计。
- 若要做修订级的格间留痕 → values_json 的历史版本要另存（或走 audit_log 的 detail）。

## 附：本 ADR 与其他 ADR 的关系

- **ADR-0019**（快照冻结）：编辑权沿用 `is_editable`；解锁留痕在账套级（不在格级）。
- **ADR-0021**（导入）：「空 = 没有这一项」「必填缺失拦发送不拦保存」沿用它的口径。
- **ADR-0018**（公式沙箱）：重算走唯一权威 `domain/record::evaluate_row`。
