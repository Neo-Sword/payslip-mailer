# ADR-0014 · 清空数据：先删库再删钥匙串条目，连备份一起删，日志留着

日期：2026-11-11 · 状态：accepted（TC-105 验收通过，评审记录见该 spec 文末）

## 背景

TC-105 做「清空数据」（设计文档 ch.6 的「备份 / 恢复 / 销毁」三段里的第三段）。
设计文档给的是一句原文：

> **清空数据**：二次确认 + 输入管理员密码，安全删除 data.db 与 Keychain 条目

加上 ch.10 合规要点那一句：

> 用户可随时导出全部个人数据 / **彻底清空数据（可携带权与删除权）**

以及 S14 / S15 的两处界面文案：

> 清空数据需输入管理员密码并二次确认，不可撤销。
>
> **确认清空全部本地数据？** 将永久删除 42 位成员、24 个批次日志与全部工资数据，操作不可撤销。
> 请输入管理员密码以继续：〔取消〕〔确认清空〕

TC-103 把「恢复」做完之后，有四件事是设计文档没写、但实现前必须定的：

1. **删除的顺序**。设计文档只说「删除 data.db 与 Keychain 条目」，没说先删哪个。
   这两个删一半的后果完全不对称。
2. **备份删不删**。备份里是同一批工资数据；留着它，「彻底清空」就不彻底。
3. **日志删不删**。日志是脱敏的，但也在数据目录里。
4. **「安全删除」在 macOS 上到底能做到什么**。设计文档写「安全删除」，
   而 APFS + SSD 上覆写擦除并不可靠。

本 ADR 定这四件。

## 决策

### 1. 删除顺序：**先删 data.db，后删钥匙串条目**

两个半成品状态的代价完全不对称：

| 崩在 | 留下的状态 | 后果 |
|---|---|---|
| 钥匙串条目已删、data.db 还在 | 库文件在、密钥没了 | 下次启动 → `KEYCHAIN_MISSING` → 引导页循环，**用户出不来**（TC-103 标准 15 那个界面） |
| data.db 已删、钥匙串条目还在 | 库文件没了、密钥还在 | 下次启动 → 首启向导（`load_or_create_key` 的守卫：条目有就用它，没有库就建一个空库）→ **干净回到 S01** ✓ |

⇒ **先删库**。崩在中间也停在「可恢复」的那一侧。

这个顺序不是洁癖：它把「不可撤销的操作」的最坏情况，从「用户被锁在门外」变成「用户回到首启向导」。

### 2. 备份**一起删**，并在确认框里点名

「彻底清空」如果留着 `exports/` 里的备份，就不彻底 —— 那些 zip 里是同一批工资数据
（虽然是用备份口令加密的，但它们仍在这台机器上）。留着它还会有合规问题：
「我清空了，怎么备份还在」。

⇒ 连 `exports/` 一起删。**但确认框必须逐项列出来**，并明确提醒：
备份文件也一起没了，**要留的话请先移到这台电脑之外**。

（备份的口令应用不掌握，所以留着它对「恢复权」有意义、对「删除权」是障碍。删除权优先。）

### 3. 日志**留着**，并在确认框里说明

`logs/` 是脱敏的滚动日志（设计文档 ch.6：「日志与崩溃转储过滤工资数值、邮箱正文、授权码」），
它记的是「谁、何时、发给谁、SMTP 结果」，**不含个人数据**。
留着它的理由是排障：用户清空数据之后如果遇到「历史记录怎么没了」这类问题，日志能查。

⇒ 不删 `logs/`，但**在确认框里写明「日志会保留（已脱敏）」** —— 不说清楚就是隐瞒。

### 4. 「安全删除」的真实含义：**删掉密钥，密文就再也解不开**

设计文档写「安全删除」。在 APFS + SSD 上，「覆写文件再删」并不可靠：
写时复制 + 磨损均衡让物理块不可寻址，覆写不保证落到原来的块。

所以真正的安全性质不是「数据被抹掉」，而是：

> **钥匙串里的那把 DB key 被删了 ⇒ 那份密文永远解不开。**

这也正是设计文档把「删 data.db **与** Keychain 条目」并列写的原因：
**单删库文件不够**（密文还在磁盘上，只是解不开 —— 其实解不开就够了），
**单删条目也不够**（新条目 + 旧密文 = 数据还在）。两个一起删，
两个条件同时成立，「不可恢复」才是真的。

⇒ 实现上不做任何覆写尝试（那只会给人虚假的安全感，且在 SSD 上纯属无用功），
而是**删文件 + 删密钥**，并把这句理由写进界面与文档。

### 5. 口令验证**没有副作用**，且发生在解锁态

管理员口令的哈希在加密库里（TC-102），所以验证口令必须库是开着的 ——
销毁流程因此只在**解锁态**可达（S14 的设置页）。

口令不对时**一个字节都不删**：验证与删除分成两步，验证失败直接返回。

验证**不计入**那 5 次失败锁定：那是给锁屏上的登录用的，而销毁入口本来就在解锁态，
用户已经拿着全部数据了 —— 计数只会让「手滑输错一次 → 之后 5 分钟不敢再试」。

### 6. 销毁后应用回到 S01 首启向导

data.db 与钥匙串条目都没了 → 下次 `admin_status` → `probe` → 开库 → 钥匙串没条目、
库文件也没有 → `load_or_create_key` 的守卫放行（生成一把**新**密钥）→ 建一个空库 →
`initialized == false` → 前端切到 S01。

⇒ 销毁完不用重启应用，前端重新读一次状态就回到首启向导。

## 后果

**变简单的**：

- 崩在中间也停在可恢复的那一侧（决策 1）。
- 「彻底清空」名副其实：库、备份、密钥三样都不留（决策 2）。
- 不用做覆写擦除这种在 APFS 上做不到的事，也不假装做到了（决策 4）。

**要认的账**：

- **删掉的备份找不回来**。所以确认框必须写明「备份文件也一起删除」，
  并且**在删除之前**再给一次「要留请先移走」的提醒。
  （这是不可撤销操作的固有代价 —— 与「重装应用」同级。）
- **日志留着**，所以严格说这台机器上还有「谁在什么时候给谁发了信」的记录。
  它不含工资数值与邮箱正文（脱敏），但它是「发送记录」的一部分，
  而合规要求里「保存 2 年以上备查」指的是这个。**留着是合规要求，不是疏忽** ——
  这条要在确认框里说清楚。
- 销毁后想找回数据，只能靠**事先导出到别处**的备份。

**重新评估的触发条件**：

- 若将来支持「多机共享同一份数据」（设计文档 ch.10 说要另行评估），
  「删除权」会变成「只删本机的副本还是全局删」的问题，本 ADR 的口径要重写。
- 若 macOS 将来提供真正的安全擦除原语（`NSFileManager` 的 secure erase 之类），
  决策 4 可以加上「物理擦除」这一层。

## 附：本 ADR 与其他 ADR 的关系

- **ADR-0013** §9：本卡是从那里拆出来的（不可撤销的操作不与「备份能救回来」同卡）。
  决策 2 直接接它的口径：备份是用户的可携带副本，删除权优先于可携带权。
- **ADR-0009**：钥匙串条目的删除走既有的 `KeychainStore::delete`，不新开一条路。
- **ADR-0011** §5：口令验证复用既有的 Argon2id 校验，不新造一套。
