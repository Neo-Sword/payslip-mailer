# ADR-0024 · 三重核对：身份一致、内容一致与变量完整的落点

日期：2026-11-12 · 状态：**accepted**（TC-401 验收通过，2026-11-12）

## 背景

设计文档 **ch.5「防错机制」**（「本产品最重要的差异化，开源项目全部缺失」）：

> ① 身份一致：导入行的姓名+邮箱必须与成员表精确匹配；不匹配的行标红且**不允许进入发送范围**。
> ② 内容一致：每封信渲染前计算 checksum(收件人 + 工资条数据)，与预览时校验和比对，**不一致即中止**。
> ③ 变量完整：模板中所有变量必须能解析且非空；缺失字段直接拦截，**绝不发出「{{实发工资}}」字面量**。

TC-302 已经做了 ①的**导入半**（Excel 姓名与成员表不一致 → 警告 + `identity_unverified` 标记）；
TC-400 已经把 `send_jobs.checksum` 落进表（②的存储侧）；TC-202/203 已经把
「未知变量渲染失败」做进引擎（③的语法侧）。本卡把三件事**接到发送链路上**。

验收准备时发现一个 TC-302 的**真缺口**：`identity_unverified` 标记**没有持久化** ——
`commit` 只写了 `values_json`，Excel 姓名与成员表不一致的那个事实在入库那一刻就丢了。
TC-401 想拦也无从拦起。本卡顺带修掉（迁移 0009）。

有三件事要定。

### 洞一：身份一致的「发送半」拦什么？

导入半拦的是「Excel 姓名与成员表不一致」。发送半要拦的还有两类
—— 它们在导入时不一定存在：

- **成员被停用**（导入后、发送前，HR 把人停了）。
- **成员被删了邮箱**（v1 没有删成员，但邮箱可以被改）—— 发送范围里的 job
  还是旧地址，人已经不在了。

⇒ **发送范围的核对**（创建批次时与发送前各跑一遍）：

1. `salary_records.identity_verified = 0` 的行 → **拦**（导入时身份存疑）。
2. 成员 `active = 0` → **拦**（已停用，S05 的口径「停用成员不进入发送范围」）。
3. 校验列有问题的行（TC-303 的 `has_problem`：必填缺失）→ **拦**
   （S07 原型：「有校验警告时『前往预览核对』仍可点，但 S11 会拦截该成员进入发送范围」）。

三类的处理不是「报错」而是**「从发送范围里排除 + 在核对报告里列出来让人看得见」**
—— 设计文档说「不匹配的行标红」，标红的前提是它出现在核对屏上。

### 洞二：内容一致核对「什么时候的什么与什么」？

「渲染前计算 checksum(收件人 + 工资条数据)，与预览时校验和比对」。

- 「预览时校验和」= **创建批次那一刻**的行 checksum（TC-400 的
  `send_jobs.checksum`，来源 `record::checksum(邮箱, values_json)`）。
- 「渲染前」= **这一封真的要发出去之前**。

中间隔着的这段时间里，库可能被改（解锁账套 → 逐格编辑）。
核对就是在发之前确认「我要发的还是我给用户看过的那份」。

⇒ 核对函数：`row_checksum(db, period_id, member_id)` 现算，
与 `send_jobs.checksum` 比对。不一致 → **中止该封**（`dead`，error_code=checksum_mismatch）
并暂停批次 —— 让人决定：改回数据重发，还是作废批次重来
（「不一致即中止」，不是「用新值继续发」—— 用户没确认过的值不能发）。

### 洞三：变量完整的「非空」判在哪个变量上？

TC-202 的语法核对（unknown）已经有了。③还要求**非空**：
「缺失字段直接拦截」。

但不是所有变量空了都该拦 —— TC-202 的 `BUILTINS` 表里每个变量带了
`required` 标记（姓名/年月/公司名称/应发合计/扣款合计/实发工资/工资条表格 =
required；工号/邮箱/组名/回信邮箱 = 可选 —— 工号可以没填、组名可以不属于任何组、
回信邮箱 TC-500 才有）。

⇒ **空值核对按 BUILTINS 的 required 标记 + 字段的 required 标记**：

- required 的内置变量渲染后是空 → 拦（列出变量名）。
- required 的字段在该行的 values 里没有 → 拦（TC-303 校验列的「必填缺失」在发送半的回响）。
- 可选变量空 → 放行（渲染成空串 —— 「组名」空着不构成发错工资）。

另外**渲染本身失败**（StrictUndefined 抛 unknown）→ 拦 ——
这是「绝不发出字面量」的引擎级兜底，TC-202 已有，本卡把它算进核对报告。

## 决策

1. **迁移 0009**：`salary_records` 加 `identity_verified INTEGER NOT NULL DEFAULT 1`
   （修 TC-302 的持久化缺口；已导入的历史行按「已验证」处理 ——
   修正之前的行没有标记，默认放行，等下次导入覆盖）。
2. **TC-302 的 commit 修正**：`ParsedRow.identity_unverified` → 写 0。
3. **发送范围核对**（`verify_scope`）拦三类：身份未验证、成员停用、
   校验列有问题；结果**从范围排除**并列进报告（不是报错）。
4. **内容一致**：发送前 `row_checksum` 现算与 `send_jobs.checksum` 比对；
   不一致 → 该封判死 + 批次暂停（执行在 TC-402 的编排循环，本卡提供函数与判定）。
5. **变量完整**：required 内置变量空 → 拦；required 字段缺 → 拦；
   渲染失败 → 拦；可选变量空 → 放行。核对**逐人**跑（每人的数据不同）。
6. **核对报告**是一等结果：`ScopeVerification { ok, blocked: Vec<BlockedMember>,
   variable_problems: Vec<MemberProblem>, previewable: 每人可预览 }`。
   S11 屏渲染它；`ok=false` 时创建批次的前端入口禁用。

## 后果

**变简单的**：

- 核对是**发送前的独立一步**（不藏在批次创建里）⇒ HR 能在发送前看清「谁被拦了、为什么」。
- 逐人渲染上下文（`context_for`）同时服务预览与核对 ⇒ 「核对看到的」与「发出去的」同一份。

**要认的账**：

- **identity_verified 默认 1**：修正前导入的行没有标记，一律放行 ——
  它们的身份问题只能靠 TC-303 的校验列与人工。
- **回信邮箱变量在 TC-500 前恒为空**：可选变量不拦，但模板里写了
  `{{回信邮箱}}` 的段落会空着 —— S11 的核对报告要能显示这一点。
- **内容一致的全量核对在本卡只做「范围核对时」**：真正的逐封核对（发送前）
  在 TC-402 的编排循环里跑（本卡提供函数）。

**重新评估的触发条件**：

- 若多管理员（ch.15 的远期）→ 身份一致的「成员表」可能与「发送范围」分属不同人维护。
- 若模板支持条件块（ADR-0018 留的口子）→ 空值核对要理解条件的分支。
