# ADR-0013 · 备份的密钥来源与恢复流程：用户口令派生的密钥 + SQLCipher 换密钥导出 + 先校验后替换

日期：2026-11-11 · 状态：accepted（TC-104 验收通过，评审记录见该 spec 文末）

## 背景

TC-104 要做「加密备份导出 / 恢复」。设计文档给了三句原文，都在 ch.6「加密与生命周期」：

> **备份**：导出 `payslip-YYYYMMDD.zip`（AES-256 加密，用户设口令），含 data.db + 模板 + 校验和
> **恢复**：先自动备份当前库 → 校验版本 → 事务内替换 → 重启应用
> **清空数据**：二次确认 + 输入管理员密码，安全删除 data.db 与 Keychain 条目

而 ch.10「打包、签名、公证与分发」里还有一句，决定了本卡的全部形状：

> 多机使用时每台 Mac 各自维护一份加密本地库，**交接靠「导出加密备份 → 新机恢复」**

再加上 ch.10「合规要点」里的：

> 用户可随时导出全部个人数据 / 彻底清空数据（可携带权与删除权）

三句话合起来，备份这件事有三个互相拉扯的要求：

1. **备份要能在一台没有本机钥匙串的机器上恢复**（ch.10 的多机交接）。
2. **备份自己得是加密的**（红线：不把工资数据明文落在磁盘上）。
3. **恢复不能把现有数据搞坏**（ch.6 的「先自动备份当前库」就是为这条写的）。

第 1 条与「用 DB key 加密备份」直接矛盾：DB key 在钥匙串里，
换台机器它就不在了（或者钥匙串授权被重置了 —— ADR-0002 记的那件事，
TC-103 验收时在开发机上亲眼见过）。**用 DB key 加密的备份，在最需要它的时候打不开。**

本 ADR 定的是「备份的密钥从哪来」与「恢复按什么顺序做」。

## 决策

### 1. 备份的密钥 = 用户口令经 Argon2id 派生，**与 DB key 无关**

派生参数沿用管理员口令那一套（`argon2 0.6`，`m=19456,t=2,p=1`，纯 Rust，ADR-0011 §1），
派生结果取 32 字节当对称密钥。

**为什么不是 DB key**：见背景。ch.10 的多机交接场景里，新机没有旧机的钥匙串条目，
用 DB key 加密的备份在新机上永远解不开 —— 那样的备份等于没有。

**为什么 Argon2id 而不是别的**：备份口令是**用户自己设的**、强度不可控，
而且备份文件会被拷到 U 盘 / 网盘 / 邮件附件里 → **攻击者可以离线爆破**。
弱 KDF 在这个场景下是实打实的风险。项目里已经有 argon2 这一条依赖与一套参数
（ADR-0011 §1 实测过的），复用它的好处是「全项目的口令只有一套 KDF 口径」。

**KDF 参数写进备份的 manifest**（版本号 + m/t/p + 盐）：将来调强参数时，
旧备份仍然能按它自己记的参数解开 —— 参数跟着备份走，而不是跟着应用走。

### 2. 加密层用 SQLCipher 自己的 AES-256，**不在 zip 容器上再叠一层**

备份文件仍然叫 `payslip-YYYYMMDD.zip`（设计文档的字面），但**加密发生在库这一层**：
用 SQLCipher 的 `ATTACH … KEY` + `sqlcipher_export` 把整库导出到一份
**用备份口令派生的 key 加密**的新库里。zip 只是外壳，装三样东西：

```
manifest.json      备份元信息（应用版本、schema 版本、创建时刻、KDF 参数、条目清单）
data.db            整库副本，已用「备份口令派生的 key」加密
checksum.sha256    data.db 的 SHA-256
```

**为什么不加密 zip 容器**（`zip` crate 的 `aes-crypto` 特性）：

- **口令错时必须在解密层就失败**。SQLCipher 打开时做 HMAC 校验，
  口令错 → 解不开 → 我们**在这一步就停下**，压根走不到「替换 live 库」。
  容器加密也能做到这点，但代价是引入第二套加密实现。
- **zip crate 的 AES 走 PBKDF2-HMAC-SHA1**，参数受限，且与本项目的 Argon2id
  口径不一致 —— 两套 KDF 并存是以后调参数时的坑。
- **代价要说清**：zip 容器本身不加密，所以 `unzip -l` 能看见三个文件名。
  补救：manifest 里**不放任何敏感信息**（只有版本号、时刻、KDF 参数、条目名）。
  真正的内容（data.db）仍然是 AES-256 加密的密文。

**「含模板」这一项**：设计文档写备份含「data.db + 模板 + 校验和」。
本项目的模板是**数据库表**（`email_templates`），模板文件在 `data.db` 里，
所以备份不需要单独的模板文件 —— manifest 里列出来是为了让人看得见。

### 3. 导出用「写到新文件」，**不用 `PRAGMA rekey` 就地重写**

SQLCipher 有两条换密钥的路：

| 做法 | 失败时 | 采用 |
|---|---|---|
| `PRAGMA rekey`（就地重写整个库） | **中途失败 = 源库直接损坏** | ✗ |
| `ATTACH … KEY` + `sqlcipher_export`（导到新文件） | 失败只影响那个新文件 | ✓ |

导出因此是**只增不改**的操作：live 库全程只读，输出写到临时文件。

### 4. 恢复的顺序：六步，**每一步都在碰 live 库之前**

```
① 校验备份文件自身：zip 能解开、checksum 对得上
② 用备份口令派生 key 打开备份里的 data.db     ← 口令错在这里失败
③ 校验版本：备份的 schema 版本 vs 应用支持的版本
④ 自动备份当前 live 库到 exports/            ← 设计文档 ch.6 的「先自动备份当前库」
⑤ 事务内把备份内容写回 live 库（live 用 DB key 加密）
⑥ 重启应用
```

第 ② 步与第 ④ 步的顺序是关键：**先确认「备份打得开」，再动 live 库**。
第 ④ 步在第 ③ 步之后，所以版本不对时连当前库都不用备份（没有破坏面）。

第 ⑤ 步用同样的 `ATTACH + sqlcipher_export` 反向做：打开备份库（备份 key）、
挂上 live 库（DB key）、把内容导进 live。live 库始终由 DB key 加密，
**DB key 的归属不变** —— 备份不接管主库的密钥。

### 5. 备份口令的策略：≥10 位，**但不做在线失败锁定**

- 长度策略直接复用 `domain::admin::check_password_policy`（≥10 位），
  界面给强度条，口令强度不足不许导出。
- **不做「错 5 次锁 60 秒」那一套**：那是给**在线**的口令登录用的
  （防的是不停试）。备份口令保护的是一个**离线文件**，锁定机制在这里
  给不了任何保护 —— 攻击者拿到文件后在别的机器上慢慢试就行。
  给用户一个「已锁定」的假安全感，比不锁更糟。

### 6. 备份的位置与文件名

- 落在 `exports/`（设计文档 ch.6 的磁盘布局）。
- 文件名 `payslip-YYYYMMDD.zip`（设计文档字面）：**只有日期**。
  红线 ② 要求「不把工资数值写进备份文件名」；这里连**姓名、组名、金额、人数**
  都不放 —— 日期是唯一的信息量。
- 同一天导出两次 → 加序号（`payslip-YYYYMMDD-2.zip`），不覆盖旧的。

### 7. 备份里**不含**附件与日志

设计文档的磁盘布局里有 `attachments/`（临时 PDF 工资条）与 `logs/`（脱敏滚动日志）。
两者都**不进备份**：附件是发送用的临时文件（用户已定「不做 PDF 附件」），
日志是脱敏的但也不属于「个人数据可携带」的范畴。备份只含数据库。

### 8. 依赖：只加两个，都是纯 Rust

| crate | 用途 | 为什么不选别的 |
|---|---|---|
| `zip` | 容器（**不开** `aes-crypto` 特性） | 纯 Rust；AES 层我们自己走 SQLCipher（决策 2） |
| `sha2` | 备份的 SHA-256 校验和 | 纯 Rust；`sha2` 已在 Cargo.lock 里（argon2 的传递依赖），提成直接依赖不新增闭包 |

**不引 `age` / `openssl` / 云备份 SDK**：前者会把第三方加密栈带进来
（ADR-0010 的取向是「加密走 Apple 的 CommonCrypto，零 libcrypto/libssl」），
后者与「数据不出本机」的红线直接冲突。门禁的「加密栈链接」一项会复查这一点。

### 9. 销毁（清空数据）**不并进本卡**

设计文档把「备份 / 恢复 / 销毁」写在一起，但本卡**只做导出与恢复**，
销毁另开 TC-105。理由不是嫌它小，而是**风险等级不同**：

- 恢复的每一步都先备份当前库，出错是可回退的；
- 销毁**不可撤销**，且要同时删 `data.db` 与钥匙串条目（ADR-0002 的授权重置场景下，
  「钥匙串条目还在、库没了」会留下一个打不开的条目）；
- 把不可撤销的操作和「备份能救回来」放在同一张卡里，
  一张卡做一半时最容易停在「删了一半」的状态。

## 后果

**变简单的**：

- 备份能在一台**没有本机钥匙串**的机器上恢复 —— 这正是 ch.10 说的多机交接。
- 钥匙串授权被重置（ADR-0002）时，备份仍然可用。
- 口令错**不可能**损坏 live 库：它在解密那一步就停了。
- 没有第二套 KDF：全项目两处口令（管理员、备份）同一套 Argon2id 参数口径。

**要认的账**：

- zip 容器不加密 → `unzip -l` 看得见三个文件名（内容仍是密文）。
- 备份口令强度不可控 → 靠界面强制 ≥10 位 + 强度条，用户自己记不住就会忘。
  忘了只能重新初始化（备份没导出过就没得救）。
- SQLCipher 的 `sqlcipher_export` 是 SQLCipher 专有函数，
  **不是**标准 SQLite —— 意味着这个库文件脱离 SQLCipher 打不开（本来就是）。
- 备份口令**不设在线锁定**（决策 5）—— 这是有意的取舍，不是遗漏。

**重新评估的触发条件**：

- 想要「忘记备份口令也能恢复」→ 只能靠把备份口令也存进钥匙串，
  但那样备份又绑回本机（与决策 1 冲突），得不偿失。
- 备份文件要发给不熟悉加密的人 → 需要换一种容器设计（当前形态对 IT 部门更友好）。
- 买了 Developer ID 证书 → 钥匙串授权重置这一项会缓解，
  但**备份仍然不该用 DB key**（多机交接的理由不变）。

## 附：本 ADR 与其他 ADR 的关系

- **ADR-0002**（未签名分发与 Keychain 后果）：本卡的第 1 条正是它那条后果的应对方式 ——
  钥匙串的钥匙会丢，备份不能跟着一起丢。
- **ADR-0010**（SQLCipher 走 CommonCrypto）：本卡不引第二个加密栈，理由同源。
- **ADR-0011**（Argon2id 口令哈希）：备份口令复用同一套 KDF 参数。
- **ADR-0012** §10（忘记密码只给诚实引导）：本卡兑现那条引导里承诺的「从加密备份恢复」。

## 实现期追加（TC-104 实现，2026-11-11）

实现过程中有三条口径与本 ADR 原文不同（或原文没写到），**追加**在此，原文不改。

### A. 引入 `tauri-plugin-dialog`（第 10 条：例外只有一个）

本 ADR 原话说「只加 `zip` 与 `sha2` 两个依赖」。实现时多了一个插件，理由与代价：

- **为什么需要**：恢复的核心场景是「从这台机器**之外**取回文件」（U 盘、网盘下载目录）。
  Tauri v2 的 drag & drop 虽然能拿到路径，但要求用户「把文件拖到窗口里」——
  对一个「可携带权」的功能，discoverability 太差。
- **权限面**：只加**一条** `dialog:allow-open`（`capabilities/default.json`）。
  插件返回的是**路径**，不是文件内容 —— 备份的字节不进渲染进程（红线 5 的同族口径）。
- **代价**：Cargo.lock 多 32 个条目，其中绝大多数是 `windows_*`（本项目 macOS-only，
  它们**不会**被编译进产物）；实际编进 macOS 产物的是 `rfd` + `objc2` 那一族。
- **与「不注册任何 Tauri 插件」的旧口径的关系**：那条说的是「脚手架自带的 opener 前端
  从未调用，摘掉它可缩小权限白名单」——针对**没人用的**插件。
  这个插件我们**真的用**，所以例外是合理的，但要在 capability 文件里看得见。

### B. zip 用 `Stored`（不压缩）

ADR 第 2 条说了「加密层走 SQLCipher 自己的 AES-256，容器不叠加密」。
补充一条实现细节：**压缩也一并省掉**。

理由是算得出来的：备份里的 `data.db` 已经是 SQLCipher 加密的密文，
熵接近随机 —— **deflate 在它上面压不动**（压了也是白费 CPU）。
于是 zip 只用 `Stored`，省掉 `flate2` + `miniz_oxide` 两个 crate。

### C. 恢复的第 ⑤ 步改成「暂存文件 + 原子改名」

ADR 第 4 条写的是「事务内把备份内容写回 live 库」。实现时发现**直接往 live 库上导会失败**：

```
sqlite> SELECT sqlcipher_export('live');
Error: table schema_migrations already exists
```

`sqlcipher_export` 走的是 `CREATE TABLE`，**目标库里表已存在就会报错**。
所以第 ⑤ 步的实际做法是：

```
备份库（备份密钥）──ATTACH──> 暂存文件（DB key）──sqlcipher_export──> 校验能打开 ──改名──> live
```

「暂存文件 + 校验 + 原子改名」比「直接写 live」多两步，换来三件事：

- **原子**：中途失败时 live 库要么是完整的旧内容、要么是完整的新内容，
  不会停在「删了还没写上」的状态（spec 标准 11）。
- **可验证**：改名前先验一遍「暂存库能被 DB key 打开」——
  不会出现「改完名才发现打不开」。
- **旧内容有退路**：第 ④ 步的自动保险备份已经把它保住了。

另外：**临时目录名必须每次唯一**。最初用「人可读的 stamp」做目录名，
于是同一秒内两次恢复会撞同一个目录，后一次把前一次解出来的库副本删掉
（真机上表现为「打不开备份里的库文件」）。已改成 `stamp + 进程号 + 纳秒`。

### D. `sqlcipher_export` 的附加库要显式设加密参数

导出时挂上去的附加库必须显式设 `cipher_page_size` 与 `kdf_iter`，
否则它用的是 SQLCipher 默认值，将来按生产参数打开会报
「file is not a database」（ADR-0010 第 4 条那类歧义：驱动只给一句笼统的错）。
