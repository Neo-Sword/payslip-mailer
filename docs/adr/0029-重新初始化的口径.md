# ADR-0029 · 重新初始化：把读不出来的旧库**改名移走**，不是删

日期：2026-11-12 · 状态：accepted

## 背景

钥匙串里的密钥与本机那份 `data.db` 对不上时，`admin_status` 以 `DATABASE` 失败，
使用者被卡在「没能读到本机状态」那一屏。而那屏的文案写着：

> 本机加密数据打不开：可能是钥匙串里的密钥与这份数据不匹配……**请先从备份恢复或重新完成初始化**，
> 再重试本次操作。

**两条路都没有按钮** —— 屏上只有一个「重试」，而重试永远不会成功
（密钥对不上这件事不会因为再点一次而改变）。2026-11-12 的发布版真机验收撞到了它：
开发构建与发布构建共用同一个 `data.db` 却各用各的钥匙串，第一次从开发切到发布就必然撞上。

同样的死路还有一条：钥匙串缺授权时（`KEYCHAIN_MISSING`），
引导页的「重新初始化」只是把人送回首启向导，而旧库还在原地 ——
向导提交时照样打不开那个库，于是又回到原地。TC-103 当时的口径是
「请把旧文件改名或移走，再继续下面的步骤」，也就是**让使用者自己去 Finder 里搬文件**。

## 决策

**一、错误页给出三条真能点的路。**
`重试` / `从备份恢复` / `重新初始化`。文案里承诺的每一条，都必须有一个按钮顶着。

**二、「重新初始化」= 把旧库改名移走，然后重新建档。**

- 旧库被改名为 `data.db.bak-<时间戳>`，**留在同一个目录里，一个字节都没删**；
  它仍然是加密的（打不开也读不出内容），要找回就把文件名改回去。
- 移走之后 `data.db` 这个名字空出来了，下一次建档会建一套全新的库。
- 旁挂文件（WAL / SHM）跟着走 —— 留着它们等于留着一个指向已移走文件的尾巴。

**三、不碰钥匙串条目。**
下一次建档会用**同一个条目名**写入新密钥（覆盖写），库与密钥自然配对。
这里主动删条目反而会造出「库没了、条目还在」的半成品状态 ——
那是 [ADR-0014](0014-清空数据的删除顺序与边界.md) 明确要避免的那一侧：
条目没了库还在会把人**锁在门外**。

**四、不碰备份。**
导出的加密备份在 `exports/` 里，与本步无关 —— 它们本来就是「从备份恢复」那条路的输入。

**五、动之前先讲清。**
确认框里必须说清三件事：会发生什么（改名移走，不是删）、影响范围（备份与钥匙串不动）、
下一步（重新建档；想救旧数据先走「从备份恢复」）。

## 为什么不是「直接删掉旧库」

- **可逆性**：改名移走与删除的差别，在这一屏上就是「以后能不能救回来」。
  这里旧库本来就读不出来，但「读不出来」不等于「永远不需要」——
  比如有人正想拿它去比对另一次事故。
- **与 ADR-0014 的分工**：「清空数据」是**用户明确要求销毁**（要口令、要确认），
  本步是「库坏了走不下去」的兜路。两者刻意不同：**要销毁的路径必须更狠**，
  走不动的路径必须更怂。
- **删了库却留下坏条目**就是 ADR-0014 里那个「锁在门外」的半成品状态。

## 后果

- 正面：使用者从「死路」变成「两条路 + 一条兜路」；旧数据仍在磁盘上，可逆。
- 负面：数据目录里会留下 `data.db.bak-*` 文件 —— 这是**有意的**，
  界面与日志里都会点名它的路径（`infra::reinit::ArchiveReport`）。
  它们是加密的占位文件，不占多少空间。

## 重新评估的触发条件

- 有人要求「重新初始化时把旧库也一并删掉」→ 那属于「清空数据」的语义，
  应走 `infra::wipe`（要口令、要确认清单），不在本步里加开关。
