# ADR-0030 · 开发构建与发布构建用**两个**数据目录

日期：2026-11-12 · 状态：accepted

## 背景

两边的钥匙串本来就不一样：

| 构建 | 库密钥存在哪 | 为什么 |
| --- | --- | --- |
| 开发构建 | **专用钥匙串文件**（`~/Library/Keychains/xinyou-dev.keychain-db`） | 未签名程序的钥匙串 ACL 记的是二进制的 **cdhash**，每重编译一次就变 → 每次启动都要重新授权（[ADR-0009](0009-Keychain用security-framework的item层.md)）。开发钥匙串的口令是脚本里的常量，所以能自动授权 |
| 发布构建 | **登录钥匙串** | 发布版就是普通用户的应用，用登录钥匙串才对 |

但两边的**数据目录是同一个**：`~/Library/Application Support/cn.payslipmailer.desktop/`
（[ADR-0012](0012-首启与解锁的界面口径.md) §1 定的口径）。

于是：

1. 开发构建建档 → `data.db` 用**开发钥匙串的密钥**加密；
2. 切到发布构建 → 它去登录钥匙串找密钥 → **找到的是另一把**（或找不到）
   → 库打不开 → 「钥匙串里的密钥与这份数据不匹配」；
3. 反过来也一样。

后果是：**在一台既跑开发版、又装了发布版的机器上（也就是开发者自己的机器），
两个构建永远不能共存**。症状是「昨天还好好的，今天一开就报数据库打不开」，
而原因藏在「昨天我跑的是另一个构建」这件事里 —— 极难自查。

2026-11-12 的发布版真机验收就是这么撞上的：发布版一启动就死在错误屏上，
而那台机器上的 `data.db` 是当天早上开发构建建的。

## 决策

**开发构建用另一个数据目录：`cn.payslipmailer.desktop-dev/`。**

- 目录名只有一个真相源（[`src-tauri/src/paths.rs`](../payslip-mailer/src-tauri/src/paths.rs)），
  开发构建在**编译期**（`debug_assertions`）加 `-dev` 后缀，
  **发布二进制里根本没有 dev 路径** —— 不存在「发布版误写进 dev 目录」的可能。
- 两个构建各存各的数据：开发时随便删、随便重来，**发布的数据一点不受影响**。
- 生产目录的口径**不变**（ADR-0012 §1），安装说明与验收标准里的路径一个字都不用改。

## 为什么不是别的三条路

1. **让开发构建也用登录钥匙串** → 每次重编译都要人输登录密码，
   开发循环直接没法做（这正是当初引入专用钥匙串的原因，ADR-0009）。
2. **让两个构建共用一把密钥**（把开发密钥同步到登录钥匙串）→ 同一把密钥管两台「机」，
   一旦哪边的库被清空，另一边也一起废；而且未签名程序的 ACL 还是要重新授权。
3. **发布构建也用开发钥匙串** → 发布给别人的应用去读一台普通机器上不存在的钥匙串文件，
   直接不可用。

## 后果

- 正面：开发与发布彻底不打架；开发时清库只影响 dev 目录。
- 负面：**开发构建的既有数据换了个位置**（老数据留在 `cn.payslipmailer.desktop/`，
  dev 构建从此不再看它）。第一次跑新的 dev 构建会看到首启向导（它读的是空的 dev 目录）。
  这是**一次性的**，且换来了「两个构建互不干扰」。

## 重新评估的触发条件

- 将来要支持「多台机器共享一份数据」→ 分目录的口径要重新审一遍
  （那时冲突的就不再是构建，而是机器）。
