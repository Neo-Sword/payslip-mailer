# ADR-0028 · 未签名内部分发的口径

日期：2026-11-12 · 状态：accepted

## 背景

设计文档 **ch.10** 要求 v1 就把签名与公证做对，写得很直白：

> macOS 15 起，未签名未公证的应用普通用户几乎打不开。这一步必须在 v1 就做对，
> 而不是「先发个能跑的」。

它给出的发布链是完整的：Developer ID Application 签名（`--options runtime --timestamp`）→
`notarytool submit --wait` → `stapler staple` → `create-dmg` 定制布局 → 分发。
仓库里的 `scripts/sign.sh` 与 `scripts/notarize.sh` 就是照这条链写的。

但决策 **D8**（[ADR-0002](0002-未签名分发与Keychain后果.md)）已定：
**不购买 Apple Developer Program**（US$99/年），走**未签名内部分发**。

于是 ch.10 与实际形态之间留了一道缺口，而缺口正好落在**分发的人和使用者身上**：

- 读 ch.10 的人会以为 dmg 双击就能开；实际每台机器都要手动放行一次。
- 本机 `security find-identity -v -p codesigning` 的输出是「0 valid identities」（ch.15 实测），
  `sign.sh` 会在第一步就退出 —— 看起来像**构建失败**，其实只是没有证书。
- 更要命的是钥匙串：未签名二进制的条目 ACL 认的是 **cdhash**，每次重建都变
  （[ADR-0009](0009-Keychain用security-framework的item层.md)），
  所以「升级之后弹窗又来了」是**必然**而不是意外。不写清楚，使用者会连点「拒绝」，
  然后被锁在门外（下次启动进 `KEYCHAIN_MISSING` 引导页）。

这些不是「缺陷」，是**口径缺失**。不补一条 ADR，下一个人（和下一个使用者）会各自重新踩一遍。

## 决策

**一、v1 不签名、不公证。**
产物是未签名的 universal `.app` + `hdiutil` 产出的 dmg + SHA-256（[ADR-0008](0008-dmg由hdiutil产出.md)）。
`sign.sh` / `notarize.sh` 保留在仓库里但**默认不执行**（`release.sh --signed` 才走），
将来有证书时直接复用，不重写。

**二、分发方式由 quarantine 属性决定，不由介质名称决定。**
判据只有一条：**这份文件到达用户手上时带不带 `com.apple.quarantine`**。
U 盘拷贝、局域网共享拷贝**不带** → 双击直接开；浏览器下载、网盘下载**带** → 每台 Mac 首次手动放行。
所以首选 **U 盘 / 局域网共享**，网盘与内网下载页是次选。

**三、手动放行的确切位置写进安装说明。**
「系统设置 → 隐私与安全性 → 仍要打开」，或 Finder 里**右键 → 打开** → 确认。
说明里**原样给出** `spctl -a -vv` 的失败输出（不转述成「可能无法打开」）。

**四、钥匙串弹窗必须点「允许」。**
未签名构建的授权每次重建/升级都会重置，弹窗会再出现一次。
点「拒绝」→ 下次启动进 `KEYCHAIN_MISSING` 引导页（用户被锁在门外）；
点「允许」即可。安装说明里明确写「允许」，并说明「为什么又弹了一次」。

**五、`spctl -a -vv` 预期失败是事实，不是缺陷。**
它证明的是「这个包没签名」，不是「这个包坏了」。
只有 `--signed` 构建才要求它通过；未签名构建的失败**只记不判**。

**六、发布产物不入 git。**
`artifacts/` 由 `.gitignore` 挡住；dmg 只存在于本机与分发介质上。
产物由「发布记录 + SHA-256」定位，不靠版本库历史定位。

**七、升级流程单独一卡（TC-601）。**
「升级后 Keychain 授权重置」必须在**机器上已经装过旧版本、库里有数据**的状态下演练，
才能验出「数据完整 + 加密库可打开」。本卡造不出那个状态。

## 为什么不是「先买证书再做发布」

- ADR-0002 已经把账算清：US$99/年买的是「免手动放行 + 分发体验」。
  v1 的形态是**一台管理机 + 一个管理员**（D5），分发量极小，手动放行一次的成本可接受。
- 但要注意一个**反直觉的点**：证书真正解决的主要不是「双击能不能开」，
  而是**第四条** —— Developer ID 锚定的签名才能根治钥匙串授权重置。
  未签名构建每次重建都弹一次授权窗，这个才是真正烦人的那件事。
- 推迟购买不影响任何工程能力：发布链已就位，`--signed` 开关已留，
  签名与公证脚本照 ch.10 写好并随时可用。

## 为什么不是「让 dmg 免放行」

免放行只有两条路：**签名公证**，或**让使用者自己编译**。
后者等于把发布工作推给使用者，与「一台管理机出包」的形态相悖。

## 后果

- **正面**：v1 分发零成本、零等待；发布链完全脚本化，能在无 GUI 会话里跑完（ADR-0008）。
- **负面**（四条，逐条写明而不是留给使用者撞）：
  1. 网盘 / 浏览器分发的每台 Mac、每个新版本，都要手动放行一次；
  2. 每次重建或升级后钥匙串授权重置，需要再点一次「允许」；
  3. 用 `spctl` 或 `codesign -v` 检查的人会看到「未签名」；
  4. **v1 的分发对象是内部使用者** —— 交给外部客户时这套形态不成立。

## 重新评估的触发条件

- 要给**外部客户**分发 → 必须先买 Developer ID 并签名公证（否则对方装不上）。
- 使用者反馈「手动放行 / 重复授权」造成实际流失 → 提前买，别等事故。
- 决定做自动更新（ch.10 的 v2）→ 签名是前提（更新清单必须签名）。
- TC-601 的演练若发现「授权重置」造成数据不可恢复 → 立刻买，这属于事故级。
