# ADR-0021 · Excel 导入：表头映射规则、校验分级与冲突策略

日期：2026-11-12 · 状态：**accepted**（TC-302 验收通过，2026-11-12）

## 背景

TC-302 做 S08「Excel 导入向导」。设计文档把这一屏的规则写在两处：

**ch.8 · 导入校验规则（S08 第三步）**：

> 表头映射：
> 优先按字段 key 精确匹配，其次按显示名模糊匹配并让用户确认；新增字段可「跳过」或「创建为自定义字段」。
> 行级校验：
> 姓名/邮箱必填；邮箱格式；成员是否存在且启用；同一成员同月不可重复；金额可解析；公式列只读并忽略用户填写值。
> 冲突策略：
> 同月已有数据时提供「覆盖 / 仅补空 / 取消」三选一，覆盖前生成变更审计。
> 结果预览：
> 显示「成功 N 行 / 警告 M 行 / 错误 K 行」，错误行可下载明细 xlsx，K>0 时禁止进入待发送状态。

**ch.12 S08 原型**：

> 上传 → 表头映射 → 校验与入库（3 步）
> 导入策略：◉ 覆盖同月已有数据（生成变更审计）○ 仅补充空白单元格 ○ 取消导入
> 表头映射：自动匹配 9 / 10 列
> Excel 列名 → 映射到 → 识别（精确 / 模糊 / 未匹配）
> 未匹配列可「跳过」或「创建为新字段」
> 第 3 步显示「成功 N / 警告 M / 错误 K」，K>0 时禁止入库；冲突策略必须先选
> 原文件不会被复制进应用目录，仅在本机内存中解析
> 所有映射可保存为「本单位的模板」供下月复用

**ch.5 防错机制 ①身份一致**：

> 导入行的姓名+邮箱必须与成员表精确匹配；不匹配的行标红且不允许进入发送范围。

另外两条硬约束来自本项目自己的红线：

- **红线 2**：绝不把工资数值写进日志、错误上报、备份文件名。
- **ch.9 数据最小化**：导入用的 Excel 原文件不复制到应用目录，只读解析；解析完成后内存中数值立即写入加密库。

有五件事要定。

### 洞一：表头怎么认字段？

「优先按字段 key 精确匹配，其次按显示名模糊匹配」这句话有个歧义：**key** 是 ASCII 的（`base_salary`），
而 Excel 表头是中文显示名（「基本工资」）。TC-301 导出的表头写的是**显示名**，
所以按 key 精确匹配**永远命不中**自己导出的文件。

⇒ 这里必须分清两种「匹配」：

- **精确（exact）**：表头文字与目标列的**显示名**（或固定列名「姓名/邮箱/工号」）完全相等。
  这是**自己导出的文件导入自己的系统**的主路径 —— 必须命中，不许要求用户去确认。
- **模糊（fuzzy）**：表头文字**包含**目标显示名，或去掉空格/全角差异后相等。
  命中了要**让用户确认**（设计文档明写「并让用户确认」）。

那「按字段 key 精确匹配」这句怎么落？**key 是导入映射结果的稳定标识** ——
映射结果一律用 field key 表示（「基本工资」→ `base_salary`），
不是用显示名。这样「优先按 key」讲的是**映射结果用 key 存**，
「其次按显示名模糊匹配」讲的是**匹配算法的顺序**。两者不冲突。

**模糊匹配的边界**：表头包含显示名 → 模糊。「社保个人」包含「社保」？
若字段叫「社保」而表头是「社保个人」，那**前者包含后者**也算命中。
但反过来 —— 表头「个人社保」包含字段「社保」？也算。
所以规则是：**双向包含**，去空格后比较。

**固定列怎么处理？**「姓名 / 邮箱 / 工号」是三个**锚点**，
它们不是 `salary_fields` 的行（设计文档 ch.6：`members` 表与 `salary_fields` 表是分开的），
但导入要靠它们把人对上。所以表头映射的目标域有两类：
**固定列**（3 个）与**工资字段**（N 个）。固定列的 key 就是 `name`/`email`/`employee_no`。

**「未匹配」列怎么办？** 设计文档给了两个选项：「跳过」或「创建为新字段」。
**「创建为新字段」本卡不做** ——
它要动 `salary_fields`（全局配置，影响所有月份与所有模板），是 TC-200 领域的写操作，
且创建后当月快照（ADR-0019）已经冻结的话，新字段进不了这个月。
本卡只给「跳过」，并把「创建为新字段」明确标为**不做**（归属 TC-303）。

### 洞二：行级校验里，哪些是「错误」，哪些是「警告」？

设计文档给了三档结果（成功 N / 警告 M / 错误 K），但没逐条说每条规则落在哪一档。
这必须定死，否则「K>0 时禁止入库」的门槛就没有确定含义。

判据：**这条问题会不会让发出去的钱是错的？**

- **会算错钱 / 发错人 → 错误（K）**：
  姓名空、邮箱空、邮箱格式不对、**成员不存在**、**成员已停用**、
  同一成员同月出现两次、金额解析不出来、公式列有用户填的值（只读列被写入 = 数据不可信）。
- **只是提醒，但不阻止入库（警告 M）**：
  工号与成员表不一致（工号只是「用于 Excel 精确匹配」的辅助键，不是身份）、
  某列在表里但被映射成「跳过」。

**身份一致（防错机制 ①）落在哪一档？** 它说「不匹配的行标红且不允许进入发送范围」。
注意这句话是关于**发送范围**的，不是关于**导入能否进行**的。
如果把「姓名与成员表不一致」定成错误，那么 HR 只要在 Excel 里改了个错别字，整批就导不进去 ——
这是把「标红并排除出发送范围」实现成了「整批拒绝」，比设计文档说的更严。

⇒ **身份一致分两步**：

- **导入时**：按**邮箱**找成员（邮箱是全局唯一键，ADR-0016）。
  找不到 / 已停用 → **错误**（这两个人根本没有有效收件地址，导进来必然是错的）。
  找到但**姓名与成员表不一致** → **警告**：这一行入库，但带一个「身份待核对」的标记，
  **这一行不得进入发送范围**（TC-401 的身份核对会再挡一次）。
- **发送前（TC-401）**：三重核对里的「身份一致」再核一遍，
  不一致的成员拦在发送范围之外。

这样「不匹配的行标红且不允许进入发送范围」完整落地，
而「一个错别字毁掉整批导入」这种过度反应被避免。

**为什么用邮箱而不是工号找人？** ch.6 的 `members.email` 是**全局 UNIQUE**
（ADR-0016 洞一），而 `employee_no` 是**可选**的（ch.6：「employee_no 可选，用于 Excel 精确匹配」）。
拿可选键当身份主键，遇到没填工号的人就认不出来。
所以：**邮箱是身份主键，工号是辅助校验**。工号不一致 → 警告。

### 洞三：金额怎么算「可解析」？

Excel 里的金额单元格可能是：

- 数字 `18000` / `-2100`（calamine 读出来是 Float）
- 文本 `"18,000.00"`（带千分位，财务粘贴时很常见）
- 文本 `"¥18000"`（带货币符号）
- 文本 `"18000 元"`
- 空（表示「这个人没有这项」）

规则：**空 = 无此项**（不是错误，也不是 0）。
非空必须能解析成一个十进制数，**允许**去掉千分位逗号与货币符号后解析。
解析不出来 → **错误**。

**为什么空不是 0？** TC-301 的说明 Sheet 写着「留空表示没有这项，不要填 0（0 和「没有」不是一回事）」。
导入必须与导出说同一套话 —— 否则「填 0」与「留空」在库里长得一样，
实发工资就差一大截。

**百分比呢？** `percent` 类型的字段（0–100），导出时写 `12.50%`。
解析时 `%` 要去掉，值域 0–100，超出即错误。

### 洞四：公式列在导入时怎么办？

ch.8：「公式列只读并忽略用户填写值」。这很明确：
**Excel 里「实发工资」那一列填什么都不算数** —— 系统自己算。

但有一条容易被忽略：TC-301 导出的模板里，公式列写的是占位文字「公式自动计算」。
如果导入时把它当「用户填的值」去忽略，那**每一行都会报一条错误**，
正常文件反而导不进去。

⇒ **公式列的用户填写值分两种**：
- 内容是占位文字「公式自动计算」→ **不是错误**，静默忽略（这是我们自己导出的模板）。
- 内容是别的（用户自己填了数字）→ **错误**（只读列被写入，数据不可信），
  提示「这一列由系统计算，请清空该列」。

### 洞五：冲突策略与「覆盖前生成变更审计」

「同月已有数据时提供「覆盖 / 仅补空 / 取消」三选一，覆盖前生成变更审计」。

- **覆盖（overwrite）**：这个成员本月已有记录 → 用导入的行**替换**它。
- **仅补空（fill empty）**：这个成员本月已有记录 → **只填它没有的字段**，
  已有字段的值**保留原来的**。
- **取消（cancel）**：有冲突就整批不做。

「仅补空」这个策略有点微妙：它操作的是**字段**（values_json 里的 key），
不是整行。所以「补空」的判据是：**那个字段在这条已有记录里不存在**。
不存在 → 填；存在 → 保留旧值。

**「覆盖前生成变更审计」写在哪？** `audit_log` 表（TC-300 建的）——
设计文档 ch.6 的表清单里明确列了它（「记录登录、改配置、导入、发送、解锁、导出」）。
审计内容**只记行数与动作**，不记任何工资数值（红线 2 的同族）：
`{"action":"import","strategy":"overwrite","rows":42,"replaced":12}`。

**审计什么时候写？** 「覆盖前」—— 在写库**之前**写。
理由：覆盖是不可逆的（旧的工资数值没了），审计必须在动手前就留下痕迹。
若写库事务失败回滚，审计行也一起回滚（同一个事务）——
**没有真正覆盖成功就不该留下「已覆盖」的痕迹**。

### 洞六（补）：公式引用了一个「这一行没填」的字段，算什么？

这是验收时撞上的真问题，值得单独记。

`net_pay` 的默认公式是 `base_salary + performance + meal_allowance + social_insurance + housing_fund`
—— 引用的是**字段名**。而一行里某个字段**可以没值**（TC-301 的说明 Sheet：
「留空表示没有这一项，不要填 0」）。

⇒ 若把「这一行没填」当成「公式引用了不存在的字段」，
那么「绩效奖金」留空的一行**算不出实发工资** ——
一个没这项奖金的人反而拿不到工资条。这在验收时是真的发生了：
「仅补空」策略下已有记录只有 `base_salary`，导入时公式直接报「引用了不存在的字段」。

**正确的区分**是「配置里有没有」与「这一行填没填」两件事：

- **配置里有、这一行没填** → 该项在这一行**不存在** → 公式里按 **0** 算。
  设计文档 S07 的原型正是这么画的：赵六那行「个税」是「—」，
  而「实发工资」照样算出 13,100.00。
- **配置里根本没有这个名字** → 公式**写错了字段名** → **报错**
  （TC-203 标准 3：「把未知变量当 0 算出来的是错的钱，比报错糟得多」）。

⇒ 行求值因此要带**两份**字段清单：`field_values`（这一行的值）
与「这个月的字段配置」。前者决定取值，后者判「这个字段存在吗」。

**这条修正落在 `domain/record.rs`（行求值）而不是 `domain/formula.rs`（表达式求值）** ——
表达式求值器本身没有「字段配置」的概念，那是**行**的概念。
这样 TC-203 的沙箱边界不变（它仍然只做四则运算、仍然不碰 I/O）。

### 洞七（补）：K>0 时禁止入库，那 M>0 呢？

设计文档说「K>0 时禁止入库」，没说 M>0。
按设计文档的字面：**M>0 允许入库**（警告不拦人）。
但那条「身份待核对」的行（洞二）是个例外 —— 它入库了，但**不得进入发送范围**。
所以它不是「拦住导入」，而是「拦住发送」，由 TC-401 执行。

⇒ **M>0 允许入库**，但每条警告都要能定位到行与列（下载明细 xlsx）。

## 决策

1. **表头映射的目标域有两类**：固定列（`name`/`email`/`employee_no`）与工资字段（field key）。
   映射结果一律用 **key** 表示，不用显示名。
2. **匹配算法**：先精确（表头 == 固定列名或字段显示名），再模糊（双向包含 / 去空格后相等）。
   精确命中**直接采用**；模糊命中**标记为待确认**，由用户在界面上确认后才允许入库。
   两类目标都没命中 → **未匹配**，本卡只提供「跳过」（**不做**「创建为新字段」，见洞一）。
3. **姓名/邮箱/工号三列固定列必须能对上**：三个固定列各自映射到 Excel 的一列。
   对不上 → **错误**（整批不能导）—— 没有邮箱就找不到人，没有姓名就看不出是谁。
4. **校验分三档**：错误 K（阻断入库）、警告 M（入库但带标记）、成功 N。
   错误清单见洞二；身份一致按「邮箱找成员、姓名对不上记警告并标记不许进发送范围」处理。
5. **邮箱是身份主键**（全局唯一），**工号是辅助键**（可选，只用于校验）。
6. **空金额 = 没有这一项**（不是 0、不是错误）；非空金额必须可解析，否则错误。
   金额允许带千分位逗号与货币符号；百分号去掉后必须在 0–100。
7. **公式列**：填的是占位文字「公式自动计算」→ 静默忽略；
   填了别的内容 → 错误（只读列被写入）。
8. **冲突策略三选一**：覆盖 / 仅补空 / 取消。
   「仅补空」以**字段**为粒度：已有记录里**不存在**的字段才填。
   「覆盖」在写库前于**同一事务**内写一条 `audit_log`（只记行数与动作，不记数值）；
   事务回滚则审计一起回滚。
9. **K>0 时禁止入库**；M>0 允许入库。错误行可下载明细 xlsx（明细里**不含**工资数值本身，
   只有行号、列名与问题描述 —— 见「红线 2」那一节）。
10. **原文件只读打开、不复制**：路径由用户在文件对话框里选，解析在 Rust 侧一次性完成，
    解析结果直接进内存，随后写进加密库；原文件不进应用目录，解析后不留副本。
11. **行求值时「配置里有但这一行没填」的字段按 0 算**；
    **配置里没有的字段名仍然报错**（见洞六）。

## 后果

**变简单的**：

- 映射结果的 key 是稳定标识 ⇒ 显示名改了不影响已保存的映射。
- 校验分档有确定判据（「会不会算错钱」）⇒ 「K>0 禁止入库」的门槛有了确定含义。
- 审计与覆盖在同一个事务里 ⇒ 不会出现「审计说覆盖了、其实没覆盖」。

**要认的账**：

- **「创建为新字段」没做**：HR 的 Excel 里有本系统没有的列（比如「季度补贴」），
  只能跳过 —— 那列数据不会进库。这一条要**在界面上明说**，
  不能让人以为「多了一列系统会自己长出来」。
- **「映射存成本单位的模板供下月复用」没做**（设计文档 S08 交互要点里的一句）。
  它要一张新表 + 一套保存/加载界面，属于本卡的**范围外**（本卡只做「这一批怎么导」）。
  归 TC-303 或后续卡片。
- **姓名不一致只警告**：那一行会入库，但 TC-401 必须把它拦在发送范围外。
  这条跨卡依赖写在这里，TC-401 的 spec 里必须兑现。

**重新评估的触发条件**：

- 若要支持「导入时创建新字段」→ 表头映射的目标域就不只是「已有列」，
  且要处理「当月快照已冻结」的情形（ADR-0019）。
- 若要支持「映射模板」→ 映射结果要能存进库里（带 key + 目标 + 顺序）。

## 附：本 ADR 与其他 ADR 的关系

- **ADR-0016**（成员邮箱全局唯一）：洞二是「按邮箱找人」的前提。
- **ADR-0019**（快照冻结）：洞一的「创建为新字段」为什么被划到范围外。
- **ADR-0018**（公式沙箱）：洞四的公式列由 TC-203 的求值器算，本卡不自己写一套。
- **红线 2 / ch.9 数据最小化**：洞三的数值不进日志、洞七的错误明细不含数值、
  决策 10 的原文件不复制。
- **ADR-0018**（公式沙箱）：洞六的「按 0 算」只改了**行求值**的口径，
  表达式求值器本身没动（它仍然只做四则运算、仍然零 I/O）。
