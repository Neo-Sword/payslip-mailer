# TC-200 · 工资条项目配置（停用不删）

状态：accepted · 依赖：TC-100（SQLCipher 库）、TC-103（首启与解锁） · 最后更新：2026-11-11

设计依据：设计文档 **ch.6 数据设计与保存方式** 的核心表定义（`salary_fields` 九列、
`data_type ∈ text/number/money/percent/formula`、「停用不删；影响模板表头与变量白名单」）
与「备份 / 恢复 / 销毁」段的默认字段集；**ch.12 界面原型** 的 S04「工资条项目配置」
（单一事实源：决定 Excel 表头 / 表格列 / 模板变量；拖拽排序、自动保存、key 唯一校验；
预览表头直接展示下一份空模板会出现的列；「已被历史月份引用的字段不能删除，只能停用。
停用后不再出现在新导出的 Excel 模板中，历史数据保持原样」）；
**ch.9** 的错误提示三要素与空状态规则；**ch.4** 的红线 8（字段只能停用不能删除）。

> **引用口径**：本卡引用设计文档一律用**章号 + 屏号 / 章标题**，不写行号。

决策依据：ADR-0015（本卡七条口径：**停用 = `visible = 0`**、**只给停用没有删除**、
**默认字段集用设计文档 S04 原型的那一组**、key 唯一且格式受限、
公式只做轻量校验、类型枚举照设计文档、「预览表头」是导出表头的唯一真相源）；
ADR-0004（错误词表先行）；红线 8。

## 目标

做完之后使用者能干什么：

- **配出自己要发的工资条长什么样**：在 S04 里加自己的工资项（基本工资、绩效、补贴、扣款…），
  调顺序、起显示名、给变量键、标必填、停用不要的。
- **一份清单，三处生效**：改完这一张表，Excel 表头、工资条表格列、邮件模板变量
  全部跟着变（设计文档说的「单一事实源」）。
- **先看见再导**：「预览表头」直接显示下一份空模板会长什么样。
- **停用而不是删除**：不要的字段停用它，它不进新表头了；历史数据里的值还在，
  上个月的模板也照样渲染得出来。

## 范围

**做**：

1. 迁移 `0003_salary_fields.sql`：设计文档 ch.6 的九列。
2. `domain/field.rs`：字段的纯逻辑 —— 类型枚举、变量键的格式规则、
   公式的轻量校验（引用的 key 必须存在、括号配平、字符集合法）。
3. `infra/fields.rs`：字段的读写 —— 列出 / 新增 / 编辑 / 停用 / 启用 / 排序。
4. 初始化时写入**默认字段集**（设计文档 S04 原型的那七项），只在表为空时写。
5. Command：`list_fields` / `create_field` / `update_field` / `set_field_visible` /
   `reorder_fields` / `preview_header`。
6. **变量白名单**（给 TC-202 用）：新建模板可选的变量 = `visible` 的字段。
7. S14 之外的 S04 界面（设计文档 S04）：字段列表（拖拽排序 / 显示名称 / 变量键 /
   类型 / 必填 / 显示 / 公式说明 / 操作）+ 新增编辑表单 + 「预览表头」+ 顶部一句
   「这是设计文档的示例清单，请按贵司实际情况增删停用」。
8. `error.rs` 加字段相关的错误码（按 ADR-0004 词表先行）。

**不做**（范围膨胀是本项目最大的风险，逐条写清归属）：

- **删除字段** → 本卡**不给**这个操作（ADR-0015 决策 2）。要「让它消失」= 停用它。
  将来要做删除，判据（有没有被月份引用）在 TC-300 落地后才有。
- **公式求值**（算出一个字段的值）→ TC-203。本卡只做保存时的轻量校验。
- **Excel 表头导出 / 导入映射** → TC-301 / TC-302。
  本卡只提供「预览表头」这个**函数**，TC-301 直接复用它，不另算一遍。
- **月份账套与 `field_snapshot` 冻结** → TC-300。
- **成员 / 邮件组 / 模板编辑器** → TC-201 / TC-202。
- **字段的分组（应发 / 扣款）** → 不做。设计文档的示例里扣款项是**负数**
  （「填负数，如 -2100」），不需要分组概念。

## 验收标准

每条都要在验收时给出**实际观察到的输出**，不接受「已验证」。

**1. 首启后字段表里是设计文档 S04 原型的那一组。**
新建一个库 → `list_fields` 返回 7 项：基本工资 `base_salary`、绩效奖金 `performance`、
餐补 `meal_allowance`、社保个人 `social_insurance`、公积金 `housing_fund`、
实发工资 `net_pay`（公式）、备注 `remark`。
*为什么必须有这条*：设计文档 S01 明写「初始化成功后写入 admins、Keychain 与
**默认字段模板**」，TC-103 当时把它后置到本卡。写进去之后 S04 一打开就是个
能用的界面，而不是一堆空行。

**2. 变量键唯一，且格式受限。**
新增一个 key 叫 `base_salary` 的字段 → 被拒（唯一）；新增一个 key 叫 `基本工资`
或 `base salary` 的字段 → 被拒（只允许小写字母、数字、下划线）。
*为什么必须有这条*：key 会进 Excel 表头、也会进模板变量 `{{key}}`，
跨工具必须是安全的标识符。中文或带空格的 key 在 Excel 里就是灾难。

**3. 没有删除操作。**
`grep -n 'delete_field\|remove_field' src-tauri/src/` 命中 0 次；
S04 的操作列里也没有「删除」。
*为什么必须有这条*：红线 8。TC-200 阶段「有没有被历史引用」的判据还不存在
（月份账套是 TC-300），所以**这个时刻正是最容易误删的**。
要「让一个字段消失」= 停用它。

**4. 停用后：不在新表头里、不在新建模板的白名单里。**
把「餐补」停用 → `preview_header` 的列里没有它；
`list_selectable_variables`（新建模板可选的变量）里也没有它。
*为什么必须有这条*：设计文档 S14 原型写明「停用后不再出现在新导出的 Excel 模板中」，
而「影响模板表头与变量白名单」是 `salary_fields` 这一行说明里的原话。

**5. 停用不影响历史数据的可读性（机制层面）。**
停用一个字段后，该字段在库里的历史行**仍然读得到**（本卡没有历史表，
所以这条验的是「停用只是 `visible = 0`，没有动数据」）。
*为什么必须有这条*：红线 8 的另一半。如果停用顺手清了历史值，
那它就变成了事实上的删除 —— 上个月的工资条会缺项。

**6. 预览表头 = visible 字段按 sort_order 拼出来的列。**
调换两个字段的顺序 → 预览表头的列顺序跟着变；停用一个 → 列少一个。
*为什么必须有这条*：设计文档 S04 说「『预览表头』直接展示下一份空模板会出现的列」。
它也是 TC-301 导出表头的**唯一真相源** —— 两处各算一遍必然漂移。

**7. 排序真的落库。**
拖动排序 → `reorder_fields` → 重开库（`list_fields`）顺序不变。
*为什么必须有这条*：`sort_order` 存在库里但排序只在内存里做的话，
下次打开就乱序了。

**8. 公式引用了不存在的 key → 被拒。**
给「实发工资」写一个公式 `base_salary + nosuchfield` → 保存被拒并说清是哪个 key 不存在。
*为什么必须有这条*：拼错 key 是公式最常见的错，而且是**静默**的错
（求值时才发现，错误信息还很难懂）。在保存时拦住，成本最低。

**9. 公式的括号与字符集不合法 → 被拒。**
公式 `base_salary + (` → 被拒（括号不配平）；公式 `base_salary & foo` → 被拒（非法字符）。
*为什么必须有这条*：轻量校验的价值就在这里 —— 完整的语法解析是 TC-203 的事，
但「明显坏掉的公式」不该被存下来。

**10. 类型是 `formula` 的行才有公式，其它类型的公式字段必须为空。**
给「基本工资」（金额类型）填一个公式 → 被拒。
*为什么必须有这条*：设计文档的 `data_type` 枚举里 `formula` 是**一种类型**，
不是一个附加开关。类型与公式不一致会让下游（TC-203 求值、TC-301 导表头）无从判断。

**11. 默认字段集只在表为空时写。**
已经配过字段的库再走一遍初始化 → 字段表**不被覆盖**。
*为什么必须有这条*：「恢复当前库」「重新初始化」这些路径都会碰到初始化。
覆盖掉用户配好的字段是灾难。

**12. 门禁九项全绿。**
`FAST=0 bash scripts/gate.sh` → 「✓ 门禁全绿」。九项按名字：Rust 格式、
前端类型检查、设计 Token（色值只允许出现在 `tokens.css`）、Token 引用可解析、
敏感数据未进 git、Rust 静态检查（clippy `-D warnings`）、Rust 单测、
加密栈链接（`otool`：链 `Security.framework`、零 `libcrypto`/`libssl`）、前端构建。
*为什么必须有这条*：本卡第一次在**业务表**（不是 `app_meta`）上工作，
「敏感数据未进 git」与「加密栈链接」两项第一次真正被压测。

| 2 key 唯一且格式受限 | ✅ 通过 | `key_must_be_unique_and_well_formed`：重复的 `base_salary` → `Duplicate`；中文 key、带空格的 key → 被拒。`domain::field::key_format_is_enforced` 另钉了大小写、数字开头、空串 |
| 3 没有删除操作 | ✅ 通过 | `there_is_no_delete_operation`：扫**测试模块之前**的源码，`fn delete` / `fn remove` / `DELETE FROM salary_fields` 三者一个都不在。界面操作列也只有「编辑」 |
| 4 停用后不在新表头、不在新建模板白名单 | ✅ 通过 | `a_deactivated_field_leaves_the_header_and_the_whitelist`：停用「餐补」后 `preview_header` 里没有它、`selectable_variables` 里也没有它 |

**浏览器实测（S04 界面）**：侧栏「工资条项目」→ 表格列出 7 项，每行有序号手柄（↑↓）、显示名称、

### 二、实现期改掉的一个已结案 TC-100 的断言

加 `0003_salary_fields` 迁移后，TC-100 的 `db_migrations_are_replayable_and_not_rerun_on_reopen`
红了 —— 它把期望的迁移版本**写死**成 `vec![1, 2]`。

已改成**从 `MIGRATIONS` 推导**期望值（`vec![1, 2, 3]` 自动跟随）。
那条测试的本意是「生产迁移表里的每一条都被应用了，且重开不重跑」，
写成推导式后本意更强（加卡不会误报），而不是「版本号恰好是 1 和 2」。

- **12 / 12 条已过**，无豁免项，本卡结案：`状态` 转 accepted、ADR-0015 转 accepted、TASKBOARD 更新。
