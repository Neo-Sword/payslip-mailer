# TC-403 · 发送日志脱敏 + 凭证 CSV 导出

状态：**accepted** · 依赖：TC-400（send_jobs）、TC-402（批次编排） · 最后更新：2026-11-12

设计依据：设计文档 **ch.9**（「电子工资条有效性依赖证据链：收件地址、发送时间、
SMTP 成功回执、内容校验和、可导出的 CSV 凭证」；《工资支付暂行规定》第 6 条
「书面记录保存 2 年以上备查」）、**ch.8 M8**（「批次记录、逐封状态、SMTP 返回码、
失败原因、按年月归档导出；留存 ≥2 年；日志脱敏；支持导出 CSV 凭证」）、
**ch.12 S13**（发送历史屏）、**红线 2**（数值不进日志）。

> **引用口径**：本卡引用设计文档一律用**章号 + 屏号 / 章标题**，不写行号。

决策依据：ADR-0026（本卡五条口径：**CSV 列无工资数值**、**姓名进 CSV 不进日志**、
**脱敏四层各自验证**、**UTF-8 BOM + RFC 4180**、**send_jobs 没有删除入口**）。

## 目标

做完之后使用者能干什么：

- **看发送历史**：批次列表（状态、进度、时间）+ 逐封明细（谁、发到哪、回码、结果）。
- **导出合规凭证**：一份 CSV，证明「给这个人、这个时间、发了工资条、服务器收了」。
- **确定没有第二份数据**：凭证、日志、审计里都搜不到工资数值。

## 范围

**做**：

1. `infra/sendlog.rs`：发送历史的读 API（批次列表带进度、一个批次的逐封明细）、
   **CSV 凭证导出**（UTF-8 BOM + RFC 4180 转义，落 `exports/`）。
2. Command：`list_send_history`（批次 + 进度）、`get_send_batch`（已有）、
   `export_batch_voucher`。
3. S13 发送历史屏：批次列表 + 点开看逐封明细 + 导出凭证按钮。
4. 四层脱敏的验收测试。

**不做**（范围膨胀是本项目最大的风险，逐条写清归属）：

- **归档压缩 / 搬移** → 数据量远不到规模（ADR-0026 洞四）。
- **凭证签名 / 哈希链** → 第三方审计是远期（ADR-0026 重新评估条件）。
- **日志滚动文件**（tracing 的文件输出）→ 已有 `tracing_subscriber`，
  文件落盘与滚动策略归 TC-600（发布前的运维口径）。

## 验收标准

每条都要在验收时给出**实际观察到的输出**，不接受「已验证」。

**1. 发送历史可读：批次列表带进度。**
跑完一个批次 → `list_send_history` 返回它，带 status/total/success/failed 与
started_at/finished_at；多个批次按时间倒序。
*为什么必须有这条*：S13 的本体。

**2. 逐封明细可读。**
点开批次 → 每封 job 的姓名（按 member_id 关联）、to_email、status、
smtp_code、sent_at、error_code 可读。
*为什么必须有这条*：出问题时「看发送日志定位 SMTP 错误码」（ch.5 用户任务）。

**3. CSV 凭证的列正确且无工资数值。**
导出 → CSV 有表头（姓名/收件地址/状态/SMTP回码/发送时间/内容校验和）；
逐格扫「18000」「3200」「2100」等金额 **都不在**文件里。
*为什么必须有这条*：ch.9 证据链 + 红线 2。凭证会被存档转发打印 ——
它证明「发了工资条」，不需要复述「发了多少钱」。

**4. CSV 是 UTF-8 带 BOM。**
文件头三字节是 `EF BB BF`（Windows Excel 双击打开不乱码）。
*为什么必须有这条*：ADR-0026 决策 4 —— 财务的机器大概率 Windows + Excel。

**5. CSV 转义符合 RFC 4180。**
成员姓名含逗号或引号 → 字段被整体包引号、内部引号翻倍；
读回（按 RFC 4180 解析）与原值一致。
*为什么必须有这条*：转义炸了整行就废了，凭证就成了废纸。

**6. 文件名含年月、落 exports/。**
导出 → `<数据目录>/exports/发送凭证_2026-10.csv`。
*为什么必须有这条*：ch.8「按年月归档导出」+ TC-301 的目录口径。

**7. 库层脱敏（结构性）：send_jobs 无正文列。**
表结构里没有正文/cc/bcc 列 —— 工资数值在库的结构上就没有位置。
*为什么必须有这条*：ch.6「不存渲染后的正文（脱敏）」；
结构性的约束比约定硬（红线 1/2 的同族）。

**8. 审计层脱敏：audit_log 只记行数与动作。**
本卡跑的导入/发送动作 → audit_log 的 detail_masked 里搜不到任何金额。
*为什么必须有这条*：审计日志留存 ≥2 年 —— 它是「记下来」的那份，
数值进去了就是第二份明文。

**9. 凭证导出是纯读操作。**
导出前后批次的 status/进度**不变**、send_jobs 逐字节不变。
*为什么必须有这条*：导出凭证不该搅动发送状态 ——
它是「看」与「拿走」，不是「改」。

**10. send_jobs 没有删除入口。**
全部 Command 里没有删除 job 的调用（grep 验证）；
凭证导出 ≥2 年留存的唯一终点是 TC-105 的清空数据。
*为什么必须有这条*：ch.9《工资支付暂行规定》「保存 2 年以上备查」。

**11. 门禁九项全绿。**
`FAST=0 bash scripts/gate.sh` → 「✓ 门禁全绿」。九项按名字：Rust 格式、
前端类型检查、设计 Token、Token 引用可解析、敏感数据未进 git、
Rust 静态检查（clippy `-D warnings`）、Rust 单测、加密栈链接、前端构建。
*为什么必须有这条*：脱敏与合规是本卡的全部 —— 门禁与「敏感数据未进 git」
持续压测。

**验收中发现并当场修的问题（都在测试侧，实现无误）**

1. **表结构断言误伤注释**：`send_jobs` 的 `idempotency_key` 列注释里有
   `content_checksum` 公式 —— 按子串扫「content」会误报。改为只匹配
   「列定义形态」（`content text` 这样的 `列名+类型`）。
2. **敌意姓名的往返解析**：姓名里的换行会被「按行切分」的简易解析拆开 ——
   RFC 4180 的引号内换行不是行边界。改为在原始文本里查找转义后的字段整体。
3. **epoch 期望值算错**（1_784_121_600 ≠ 2026-11-12）：用 `date -j -u` 校准为
   1_794_441_600。`civil_from_days`（Howard Hinnant 算法）实现本身正确 ——
   闰年 2024-02-29 与一天结束的边界都过。

**实现口径的说明**

- **凭证文件名带批次 id**（`发送凭证_2026-10_000001.csv`）：同月多批次不互相覆盖；
  批次 id 是序号不是工资数据（红线 2 不拦）。
- **换算时间没有引 chrono**：`civil_from_days` 十四行搞定（ADR-0010 的同族取向 ——
  一个时间格式化不值得多一个依赖）；UI 层展示本地时间由前端格式化。
- **S13 发送历史屏已补上**（2026-11-12，TC-500 结案后）：批次列表（状态/进度/
  速率/起止时间）+ 逐封明细（姓名/地址/状态/尝试次数/回码/失败分类/时间）+
  「导出 CSV 凭证」按钮。脱敏口径不变：屏上与凭证里都没有工资数值。

**要认的账（本卡遗留的边界，不是缺陷）**

- **凭证不含失败原因原文**：只记回码与分类（ADR-0026 已写明 ——
  服务器错误文案可能带收件人片段，原文只在应用内看）。
- **「留存 ≥2 年」靠不删**：v1 没有归档搬移；数据量远不到规模。
