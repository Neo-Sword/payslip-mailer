# TC-104 · 加密备份导出与恢复

状态：accepted · 依赖：TC-100（SQLCipher 库）、TC-101（Keychain）、TC-103（首启与解锁） · 最后更新：2026-11-11

设计依据：设计文档 **ch.6 数据设计与保存方式** 的「磁盘布局」「加密与生命周期」
（备份 / 恢复 / 销毁三句原文）；**ch.10 打包、签名、公证与分发** 的「多机使用时每台 Mac
各自维护一份加密本地库，交接靠『导出加密备份 → 新机恢复』」与「合规要点」
（《个人信息保护法》：用户可随时导出全部个人数据 / 彻底清空数据）；
**ch.12 界面原型** 的 S14「数据备份」段（导出加密备份 / 从备份恢复）；
**ch.9** 的错误提示三要素（发生了什么 / 影响范围 / 下一步）。

> **引用口径**：本卡引用设计文档一律用**章号 + 屏号 / 章标题**，不写行号。
> （设计文档自身的章节编号里数据设计是 ch.6、分发是 ch.10、界面原型是 ch.12。）

决策依据：ADR-0013（本卡十个口径：备份密钥来自用户口令而不是 DB key、加密层走 SQLCipher
自己的 AES-256 而不叠 zip 容器加密、导出用「写到新文件」而不是就地 rekey、恢复六步顺序、
备份口令不做在线锁定、备份位置与文件名、备份不含附件与日志、只加两个纯 Rust 依赖、
销毁另开 TC-105、备份参数随备份走）；ADR-0010（不引第二个加密栈）；
ADR-0012 §10（S02「忘记密码」承诺过的恢复入口由本卡兑现）。

## 目标

做完之后使用者能干什么：

- **这台电脑的数据能带走**：一键导出一个加密备份文件，交给运维/同事，或者存进自己的 U 盘。
- **换台电脑能接上**：新机器上装好薪邮，用备份文件 + 备份口令，把数据完整恢复过去——
  **不需要旧机器，也不需要旧机器的钥匙串**。
- **钥匙串出事了还有救**：钥匙串里的库密钥授权被重置（应用升级、清理工具）时，
  备份仍然是唯一出路——因为备份的密钥来自备份口令，不来自钥匙串。
- **恢复不会把现有数据搞坏**：口令输错、备份文件损坏、版本对不上，都会在**碰现有数据之前**
  就停下来并说清原因；真要动手了，先自动备份当前库。
- **导出的文件在磁盘上不是明文**：文件里看得见的只有版本号、时间、条目名和密文。

## 范围

**做**：

1. `infra/backup.rs` 新模块：导出（backup）与恢复（restore）的核心逻辑，
   底层走 SQLCipher 的 `ATTACH … KEY` + `sqlcipher_export`（ADR-0013 §2/§3）。
2. `domain/backup.rs`：备份口令的策略（≥10 位，复用 `check_password_policy`）与
   manifest 的结构（版本、schema 版本、创建时刻、KDF 参数、条目清单）。
3. `commands/backup.rs`：`export_backup`、`list_backups`、`restore_backup` 三个 Command，
   注册进 `lib.rs`。
4. `app_meta` 新键 `last_restored_at`（设计文档 ch.6 的磁盘布局注释里点名的键）。
5. S14「数据备份」段的界面：**导出加密备份**（设备份口令 + 强度条 + 导出）、
   **备份列表**（文件名、大小、创建时间、来自哪台机器）、**从备份恢复**（选文件 + 输口令 +
   六步进度 + 结果）。
6. S02「忘记密码？」弹窗里的「从备份恢复」入口（ADR-0012 §10 承诺过的那条路，
   本卡兑现它：从弹窗直接跳到恢复流程）。
7. `error.rs` 新错误码（按 ADR-0004 词表先行）：备份口令错、备份文件损坏、
   备份版本不受支持、备份已存在等。
8. 恢复时的**自动备份当前库**（设计文档 ch.6 原文「先自动备份当前库」）。
9. 依赖：新增 `zip`（不开 AES 特性）与 `sha2`，都是纯 Rust（ADR-0013 §8）。

**不做**（范围膨胀是本项目最大的风险，逐条写清归属）：

- **清空数据 / 销毁**（删 `data.db` + 删钥匙串条目）→ **TC-105**。
  理由写进 ADR-0013 §9：不可撤销的操作不与「备份能救回来」放进同一张卡。
- **把备份传上云**（网盘同步、S3、iCloud）→ 永不做。红线「数据不出本机」。
- **备份的定时自动执行**（每周自动备份）→ 不做。自动备份意味着用户不知道自己有备份，
  也意味着机器上悄悄多出一堆含工资数据的文件。
- **恢复历史与回滚到任意版本**（只保留「恢复前自动备份的那一份」）→ 不做。
- **备份口令的找回** → 不做（同管理员口令：无法找回）。
- **多管理员、共享库、团队版备份编排** → 不做（本项目是单机单管理员，ch.10 已确认）。
- **把邮件正文与发送日志放进备份** → 永不做（ch.10 合规要点：最小必要）。
- **PDF 附件进备份** → 永不做（用户已定「不做 PDF 附件」）。

## 验收标准

每条都要在验收时给出**实际观察到的输出**，不接受「已验证」。

**1. 导出的备份在磁盘上不是明文。**
导出一个含成员姓名与工资数值的库 → `strings` 与 `grep -a` 在那个 zip 与解出来的
`data.db` 里都搜不到那些姓名与数值（只在密文里）。
*为什么必须有这条*：红线 2 的口径是「不把工资数值写进日志、错误上报、备份文件名」——
备份**内容**同样不能是明文。一份明文的工资备份放在 U 盘上等于把全公司工资公开。

**2. 备份文件名只有日期，没有任何敏感信息。**
导出后文件名是 `payslip-YYYYMMDD.zip`（同一天第二次是 `payslip-YYYYMMDD-2.zip`）；
文件名里不含姓名、组名、人数、金额、单位名称。
*为什么必须有这条*：红线 2 明写「不把工资数值写进……备份文件名」。
文件名会出现在邮件标题、聊天记录、截图里 —— 它是最容易外泄的一层。

**3. 备份能在一台「没有本机钥匙串」的机器上恢复。** ← 本卡的核心价值
把备份拷到另一台机器（或把本机钥匙串的 `db-key` 条目删掉）→ 在新机器上用
**备份口令**恢复 → 数据完整回来，且恢复后那个库由**新机器自己的** DB key 加密。
*为什么必须有这条*：设计文档 ch.10 明写「交接靠『导出加密备份 → 新机恢复』」。
如果备份绑死在旧机的钥匙串上，这条设计就是假的 —— 而这正是用 DB key 加密备份会犯的错。

**4. 口令错时，现有数据一字不动。**
拿一个**备份口令错**的文件去恢复 → 报「备份口令不对」，live 库的
md5 与 mtime **一字不变**，`admins` 表行数不变。
*为什么必须有这条*：恢复是最容易毁数据的一步。「先确认备份打得开，再碰 live 库」
（ADR-0013 §4）是这条的全部意义 —— 顺序反了，一次手滑就是整库没了。

**5. 备份文件被损坏时，同样不碰现有数据。**
把备份 zip 截断一半、或改掉 `data.db` 里的一个字节 → 恢复在第 ① 步（checksum）
就停下来，现有库不变。
*为什么必须有这条*：备份会经历拷贝、网盘同步、U 盘拔插 —— 损坏是常态而不是意外。
一个会在校验失败后照样往下走的恢复流程，是最坏的那种。

**6. 恢复前自动备份当前库。**
恢复一次 → `exports/` 里多出一个「恢复前的当前库」备份文件，且能拿它再恢复回去。
*为什么必须有这条*：设计文档 ch.6 的原文就是「先自动备份当前库 → 校验版本 →
事务内替换 → 重启应用」。没有这一步，恢复出错就没有退路。

**7. 版本校验真的会拦。**
拿一个 schema 版本**比当前应用新**的备份去恢复 → 拒绝并说清「这份备份来自更新的版本，
当前应用打不开」；拿一个 schema 版本**比当前应用旧**的备份去恢复 → 能恢复，
且恢复后由应用自己跑迁移补齐。
*为什么必须有这条*：「校验版本」是设计文档的原文。往新库写旧结构、或用旧应用开新库，
两种都会静默地产生错位的工资数据 —— 那是最难查的一类坏。

**8. KDF 参数写在备份里，不写在应用里。**
manifest 里能看到 argon2 的版本与 m/t/p 参数；把一份旧参数备份的 manifest 改掉参数
（模拟「将来调强参数」）→ 旧备份仍按它自己记的参数能被解开。
*为什么必须有这条*：参数跟着备份走，将来调强 Argon2 参数才不会让旧备份全部作废。

**9. 备份口令的策略与管理员口令同一条，但不做在线锁定。**
备份口令 < 10 位 → 导出被拒（界面给强度条）；连续输错备份口令 →
**不锁**，只是报「口令不对」；库里与日志里都不出现备份口令。
*为什么必须有这条*：长度策略复用 `check_password_policy` 是一次性事实，
不做在线锁定是有意的（ADR-0013 §5）—— 离线文件上「锁定 60 秒」给不了任何保护，
只会给人虚假的安心感。这条写进验收是为了**防止以后有人顺手把它补上**。

**10. 备份放在 `exports/`，且不含附件与日志。**
导出后 `exports/` 里出现备份文件；`attachments/` 与 `logs/` 的内容**不在**备份里
（manifest 的条目清单里也不列它们）。
*为什么必须有这条*：设计文档 ch.6 的磁盘布局把三者分开列了。附件是发送用的临时文件，
日志不是「个人数据可携带」的范畴 —— 备份只该装数据库。

**11. 恢复是原子的：中途失败不留半截文件。**
在恢复第 ⑤ 步人为制造失败（例如把 live 库所在目录改成只读）→ live 库要么是完整的旧内容，
要么是完整的新内容，**不是半截**；且 `exports/` 里没有临时文件残留。
*为什么必须有这条*：原子性是「恢复不毁数据」的最后一层保险。前面的标准管的是
「不该动手的时候不动手」，这条管的是「动手的时候别弄一半」。

**12. 恢复完成后重启，数据完整且能继续用。**
恢复 → 重启应用 → 解锁 → 成员名单、工资数据、模板、批次记录、账号设置全在，
`app_meta.last_restored_at` 是这次恢复的时刻。
*为什么必须有这条*：「数据完整」不能只看「恢复没报错」。要真的解锁进去看内容。

**13. S02「忘记密码」弹窗里的恢复入口能走通。**
从 S02 的「忘记密码？」弹窗点「从备份恢复…」→ 进入恢复流程（选文件 + 输口令），
而不是只给一段说明文字。
*为什么必须有这条*：ADR-0012 §10 明确承诺「唯一的出路是从加密备份恢复，
恢复入口在设置页，**由 TC-104 落地**」。本卡就是来兑现那条承诺的 ——
只写说明不给出路，那条 ADR 就还欠着。

**14. 导出与恢复的错误提示都有三要素。**
每一条失败路径（口令错、文件损坏、版本太新、目录不可写）→ 提示里都有
「发生了什么 / 影响范围 / 下一步」三段，且**不出现**任何内部细节
（临时路径、SQL 报错、校验和）。
*为什么必须有这条*：设计文档 ch.9 的通用规则。恢复出错的用户往往很慌，
只说「失败」会让人反复重试，越试越糟。

**15. 新增依赖仍然是纯 Rust，且加密栈链接不变。**
`cargo tree` 里新加的 `zip` / `sha2` 的依赖闭包里没有 C 编译单元；
门禁的「加密栈链接」一项仍然是「链 Security.framework、零 libcrypto/libssl」。
*为什么必须有这条*：ADR-0010 的取向是「不引第三方加密栈」。备份是最容易顺手
把 OpenSSL 或别的 C 库带进来的地方（zip 的加密特性就是一个入口），所以这条要钉住。

**16. 门禁九项全绿。**
`FAST=0 bash scripts/gate.sh` → 「✓ 门禁全绿」。九项按名字：Rust 格式、前端类型检查、
设计 Token（色值只允许出现在 `tokens.css`）、Token 引用可解析、敏感数据未进 git、
Rust 静态检查（clippy `-D warnings`）、Rust 单测、加密栈链接（`otool`：链
`Security.framework`、零 `libcrypto`/`libssl`）、前端构建。
*为什么必须有这条*：本卡第一次引入第三方依赖（`zip` / `sha2`），
「设计 Token」与「敏感数据未进 git」之外，**加密栈链接**这项第一次真正被压测。

## 评审记录

验收日期：2026-11-11 · 验收方式：Rust 验收测试（`src-tauri/src/infra/backup.rs` 里 15 条，
测试名里直接写了它对应本卡的哪一条）+ 浏览器实测 + 门禁九项。

### 一、逐条结论

| 标准 | 结论 | 实际观察输出 |
|---|---|---|
| 1 备份在磁盘上不是明文 | ✅ 通过 | `backup_is_not_plaintext_on_disk_and_the_name_carries_only_a_date`：备份 zip 与解出来的 `data.db` 里都搜不到哨兵字符串（`欧阳傲天-工资条目-98765`）与管理员邮箱；`manifest_has_no_sensitive_content` 另钉了清单里没有姓名/工资/邮箱/单位名称/口令 |
| 2 文件名只有日期 | ✅ 通过 | 同上：文件名是 `payslip-20261111.zip`，不含姓名、组名、人数、金额、单位名称；同一天再导一次是 `payslip-20261111-2.zip`（`commands/backup.rs` 的 `next_free_path`），不覆盖旧的 |
| 3 **备份能在一台没有本机钥匙串的机器上恢复** | ✅ 通过 | `backup_restores_on_a_machine_with_a_different_keychain`：A 机（钥匙串甲）导出 → 拷到 B 机（**钥匙串乙**，DB key 断言 `assert_ne!`）→ B 机用**备份口令**恢复 → 数据完整回来（哨兵字符串读回一致）；再验证**A 的 DB key 打不开 B 恢复出来的库**（`open_with_key` 报错）、**B 自己的 key 能打开**。这就是设计文档 ch.10「交接靠导出加密备份 → 新机恢复」的实现 |
| 4 口令错时现有数据一字不动 | ✅ 通过 | `a_wrong_password_leaves_the_live_database_untouched`：错口令 → `BackupPasswordWrong`；live 库**逐字节相同**；且没留下恢复前的保险备份（没走到那一步） |
| 5 备份文件损坏时同样不碰现有数据 | ✅ 通过 | `a_corrupted_backup_leaves_the_live_database_untouched`：改坏备份里的一个字节 → `BackupCorrupted`；live 库逐字节相同 |
| 6 恢复前自动备份当前库 | ✅ 通过 | `restore_keeps_an_automatic_safety_copy_of_the_current_database`：恢复后 `exports/` 里多出一个 `…-before-restore.zip`，清单里的 `kind` 是 `preRestoreSafety` |
| 7 版本校验真的会拦 | ✅ 通过 | `a_newer_backup_is_refused_and_the_live_database_is_untouched`：把备份库里的 `schema_migrations` 最大版本改成 9999（并同步重算校验和）→ 恢复被拒，报 `BACKUP_VERSION_TOO_NEW`，live 库不变 |
| 8 KDF 参数写在备份里 | ✅ 通过 | `kdf_parameters_travel_with_the_backup`：清单里有 argon2id / m=19456 / t=2 / p=1 / 盐；`domain::backup::derive_key_with_params` 与「按当前参数派生」派生出**同一把钥匙**（`manifest_params_reproduce_the_same_key`）——这就是「将来调强参数不会让旧备份作废」的数学前提 |
| 9 口令策略同一条、但不做在线锁定 | ✅ 通过 | `backup_password_policy_is_enforced_and_wrong_passwords_do_not_lock`：太短的口令被拒（`VALIDATION_ERROR`）且不留文件；连错三次**只是报口令错，不锁** |
| 10 备份里只有数据库 | ✅ 通过 | `backup_contains_only_the_database`：造出 `attachments/` 与 `logs/` 两个目录后导出，解出来的目录里恰好三样（manifest.json / data.db / checksum.sha256），附件与日志都不在 |
| 11 恢复是原子的 | ✅ 通过 | `a_failed_restore_leaves_no_half_written_files`：占住暂存文件名让改名那一步失败 → live 库逐字节完好；数据目录里不留 `.restore-tmp-*` 残留 |
| 12 恢复完成后数据完整且能继续用 | ✅ 通过（后端半） | `backup_restores_on_a_machine_with_a_different_keychain`：恢复后重开库，哨兵数据与管理员邮箱都回来了；`commands/backup.rs` 的 `restore_backup` 在恢复后重开库（跑迁移）并写 `app_meta.last_restored_at`；界面提示「请用备份里那时的管理员口令解锁」 |
| 13 S02「忘记密码」里的恢复入口能走通 | ✅ 通过 | 浏览器实测：锁屏 →「忘记密码？」→ 弹窗里点「从备份恢复…」→ **恢复对话框直接打开**（选文件 + 输口令 + 说明 +「开始恢复」） |
| 14 错误提示都有三要素 | ✅ 通过 | 四个新码的 `user_message()` 各写了一句三要素齐的话（`error.rs`）：口令错 / 文件坏 / 版本太新 / 操作失败，都带「发生了什么 + 影响范围（现有数据没动）+ 下一步」，且**不出现**临时路径、SQL 报错或校验和（那些只在 `Display`/日志里） |

### 二、实现期发现并当场改掉的四个问题

1. **临时目录名只由人可读的 stamp 决定** → 同一秒内两次恢复会撞同一个目录，
   后一次把前一次解出来的库副本删掉（真机上表现为「打不开备份里的库文件」，
   并行跑测试时必现）。已改成 `stamp + 进程号 + 纳秒`。
2. **`restore_inner` 中途 panic 时清理被跳过** → 解出来的**工资数据**留在磁盘上。
   已改成 RAII 守卫（`WorkDirGuard`），panic 路径也删。
3. **`sqlcipher_export` 不能覆盖已存在的表**（`table schema_migrations already exists`）
   → 恢复流程不能直接在 live 库上导。已改成「导到暂存文件 → 验一遍能被 DB key 打开
   → 原子改名盖上去」（ADR-0013 实现期追加 C）。
4. **工作目录放在全局 temp 会互相干扰** → 已挪进应用自己的数据目录
   （`.restore-tmp-*`），归属清楚、可精确断言残留。

### 三、实现期追加的两条口径

- **引入了 `tauri-plugin-dialog`**（ADR-0013 实现期追加 A）：恢复要从这台机器**之外**
  取回文件，原生选择器是对的工具。权限面只加一条 `dialog:allow-open`。
- **zip 用 `Stored` 不压缩**（追加 B）：备份里的库已是密文，deflate 在它上面压不动。

### 四、结论与未结项

- **16 / 16 条已过**，无豁免项。
- 剩**两条需要真机人工确认**（不属于 21/16 条标准，是实现层面的最后一步）：
  ① 用**真实的备份文件**走一遍「选文件 → 输口令 → 恢复」的完整界面流程
  （自动测试走的是 Rust 层，界面上的文件选择器要真的点一次）；
  ② 在**另一台机器**上从零恢复（自动测试用两套临时钥匙串模拟，
  真机交接要拿一个 U 盘或网盘文件试）。
  这两条已请使用者配合，与 TC-103 的三条真人观察一并做。
- **销毁（清空数据）不在本卡** → TC-105（理由见 ADR-0013 §9）。
- 本卡**可以结案**：`状态` 转 accepted，ADR-0013 转 accepted，TASKBOARD 更新。
