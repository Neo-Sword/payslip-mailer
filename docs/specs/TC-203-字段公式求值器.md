# TC-203 · 字段公式求值器（沙箱）

状态：accepted · 依赖：TC-100（SQLCipher 库）、TC-200（工资条项目）、TC-202（模板） · 最后更新：2026-11-12

设计依据：设计文档 **ch.8 模板、Excel 与变量体系** 的「字段类型与行为」表
（`formula` = 表达式 = 只读计算列，「公式仅允许引用本行字段与 + - * / ( )，
由 Rust 侧表达式求值器执行，**禁止任意代码执行**」；「未知变量、空值、类型错误 →
渲染失败并拦截发送」）与「变量白名单」表（内置含 邮箱 / 年份 / 月份）；
**ch.12 界面原型** 的 S04（「实发工资」那一行的公式写的是「应发合计 + 扣款合计」）
与 S07（「公式列由系统计算，不可直接编辑」「金额可双击编辑并自动重算公式列」）；
**ch.9** 的错误提示三要素；**ch.4** 红线 4（模板引擎沙箱化，禁止文件读取 / 系统调用 /
访问环境变量）。

> **引用口径**：本卡引用设计文档一律用**章号 + 屏号 / 章标题**，不写行号。

决策依据：ADR-0018（本卡九条口径：**自己写递归下降的算术表达式求值器**（零依赖、零 I/O 面）、
公式可引用**字段 key + 汇总变量**、**除以零报错**、**求值用原始数值而格式化在求值之后**、
**循环引用报错**、引用非数值字段报错、**TC-200 的语法检查改为委托解析器**、
**补齐邮箱/年份/月份三个内置变量**、未知变量/空值/类型错误一律失败并拦截）；
ADR-0017；红线 4。

## 目标

做完之后使用者能干什么：

- **配一条算得出来的工资项**：在 S04 里给「实发工资」写 `base_salary + performance`，
  保存前就知道它算得出来、算出来是多少。
- **写错当场就知道**：括号不配平、引用了不存在的字段、拿文本字段做加减、
  除以零、公式套自己 —— 全部在保存前报错，并说清错在哪。
- **公式列不可手填**：导入与逐格编辑时，公式列由系统算（TC-302/TC-303 接线），
  用户填的值一律忽略。

## 范围

**做**：

1. `domain/formula.rs`：**词法 + 语法分析 + 求值**（纯函数，零依赖、零 I/O）。
   语法只有：数字、标识符、`+ - * / ( )`、一元负号。
2. `domain/formula.rs` 的**求值上下文**：字段 key → 数值、该行的应发合计 / 扣款合计。
3. `infra/fields.rs` 增：**按一行求值全部公式列**，带**循环引用检测**。
4. `domain/field.rs` 的 `check_formula` 改为**委托给解析器**（语法判定的唯一权威）。
5. Command：`evaluate_formula`（给定公式与样例值 → 结果或错误），给 S04 的即时试算用。
6. S04 的公式编辑框：**保存前即时校验 + 试算**（一行说明「公式只支持字段与四则运算」）。
7. **补齐三个内置变量**：邮箱 / 年份 / 月份（设计文档 ch.8，TC-202 漏了），
   并在 TC-202 的评审记录里补一句。
8. `error.rs` 加公式相关的错误码（按 ADR-0004 词表先行）。

**不做**（范围膨胀是本项目最大的风险，逐条写清归属）：

- **月份账套与逐格编辑时的批量重算** → TC-300 / TC-303（那时才有真实的行数据）。
- **导入时忽略公式列的值** → TC-302（Excel 导入向导）。
- **公式的版本化与迁移**（改了公式后历史月份怎么办）→ TC-300 的 `field_snapshot` 冻结。
- **条件与比较**（`if`、`>`、逻辑运算）→ 不做。设计文档写的是「仅允许引用本行字段与
  + - * / ( )」。将来要支持时得重审沙箱口径。
- **跨行引用**（引用另一个成员的字段）→ 不做。「本行字段」是设计文档的字面。
- **公式列的历史值回溯计算** → TC-300（快照里存的是当时的公式与当时的值）。

## 验收标准

每条都要在验收时给出**实际观察到的输出**，不接受「已验证」。

**1. 公式求值器只认那几样东西。**
`base_salary + performance`、`(base_salary + performance) * 2`、`-base_salary`、
`100 / 4` 都能算出正确结果。
*为什么必须有这条*：设计文档 ch.8「公式仅允许引用本行字段与 + - * / ( )」。
这是语言的全部，不多不少。

**2. 不允许任意代码执行 —— 结构性，不是约定。**
把这些当公式保存 → **全部被拒**：`x | abs`、`x.y`、`f(x)`、`__import__`、
`x + 1; drop table`、`x # 注释`、`"字符串"`。
且求值器的源码里**没有**任何 I/O 调用（`grep` 不到 `File`/`fs::`/`Command`/`env::`）。
*为什么必须有这条*：红线 4 与设计文档 ch.8 的「禁止任意代码执行」原话。
公式是用户自己写的，求值器必须**假设输入是恶意的**。

**3. 引用了不存在的字段 → 报错，不是 0。**
公式写 `base_salary + nosuchfield` → 报错并点名 `nosuchfield`。
*为什么必须有这条*：设计文档 ch.8「未知变量…→ 渲染失败并拦截发送」。
把未知变量当 0 算出来的是**错的钱**，比报错糟得多。

**4. 汇总变量按「该行」算。**
一行里基本工资 18000、绩效 3200、社保 -2100 → 应发合计 = 21200、扣款合计 = -2100、
实发工资 = 19100；公式 `应发合计 + 扣款合计` 求出 19100。
*为什么必须有这条*：S04 原型的「实发工资」那一行写的公式就是「应发合计 + 扣款合计」，
求值器必须认这两个名字。

**5. 除以零 → 报错。**
公式 `base_salary / 0` → 报错（不是 Infinity、不是 0）。
*为什么必须有这条*：Infinity 会被格式化成一个荒谬的金额发出去。
报错能在保存前拦住。

**6. 循环引用 → 报错。**
A 的公式引用 B、B 的公式引用 A（含 A 引用自己）→ 报错并说清是哪几个字段形成了环。
*为什么必须有这条*：不检测就是无限递归 —— 栈溢出不是「报错」，是进程崩掉。

**7. 拿文本字段做算术 → 报错。**
公式引用了一个 `text` 类型的字段 → 报错（类型错误）。
*为什么必须有这条*：设计文档 ch.8「类型错误 → 渲染失败并拦截发送」。
文本参与算术没有意义，静默当 0 会算出错的钱。

**8. 求值用原始数值，格式化在求值之后。**
用 `18000` 与 `3200` 求和 → 得到 `21200`（不是 `21,200.00`）；
格式化（千分位）在渲染/显示那一步才发生。
*为什么必须有这条*：`18,000.00 + 3,200.00` 在表达式里根本解析不了（逗号）。
求值与格式化混在一起，第一次有人带千分位的值进来就炸。

**9. 输出按分四舍五入。**
`1 / 3` → `0.33`；`0.005 + 0.005` → `0.01`（不是 0.010000000000000002）。
*为什么必须有这条*：浮点误差必须被挡在「分」这一层外面，
否则表里会出现 0.30000000000000004 这样的钱。

**10. 语法判定只有一份权威。**
`domain/field.rs` 的 `check_formula` 与求值器对同一个公式给出**同一个结论**
（能求值的一定能通过校验，不能解析的一定都被拒）。
*为什么必须有这条*：TC-200 那套手写的字符集检查与本卡的解析器并存，
两份规则早晚漂移 —— 到那时「界面放过了、引擎报错」。

**11. 未知变量/空值/类型错误一律拦截，且不影响别的字段。**
一行里有一条公式字段是坏的 → **只有那一条报错**，其余字段照常求值；
错误说清是哪个字段、哪一处。
*为什么必须有这条*：设计文档 ch.8「未知变量、空值、类型错误 → 渲染失败并拦截发送」。
整行全废会让 HR 改一个字段得重录整月的数据。

**12. 门禁九项全绿。**
`FAST=0 bash scripts/gate.sh` → 「✓ 门禁全绿」。九项按名字：Rust 格式、
前端类型检查、设计 Token（色值只允许出现在 `tokens.css`）、Token 引用可解析、
敏感数据未进 git、Rust 静态检查（clippy `-D warnings`）、Rust 单测、
加密栈链接（`otool`：链 `Security.framework`、零 `libcrypto`/`libssl`）、前端构建。
*为什么必须有这条*：本卡第一次**执行用户写的表达式**。
门禁与单测是它唯一的护栏（红线 4）。

## 评审记录

验收日期：2026-11-12 · 验收方式：Rust 验收测试（`src-tauri/src/domain/formula.rs` 里 10 条 +
`src-tauri/src/infra/fields.rs` 里 2 条）+ 浏览器实测 + 门禁九项。

### 一、逐条结论

| 标准 | 结论 | 实际观察输出 |
|---|---|---|
| 1 只认那几样东西 | ✅ 通过 | `basic_arithmetic_works`：`base_salary + performance` = 21200、`(base_salary + performance) * 2` = 42400、`-base_salary` = -18000、`100 / 4` = 25、`base_salary - social_insurance` = 20100 |
| 2 不允许任意代码执行（结构性） | ✅ 通过 | `arbitrary_code_is_rejected_by_the_grammar`：9 句全被拒（`x | abs`、`x.y`、`f(x)`、`__import__`、`x + 1; drop table`、`x # comment`、`"字符串"`、`x[0]`、`x && y`）；`the_evaluator_has_no_io` 扫求值器源码：找不到 `std::fs` / `File::` / `Command::` / `std::env` / `std::net` |
| 3 未知字段 → 报错，不是 0 | ✅ 通过 | `unknown_field_is_an_error_not_zero`：错 `Unknown("nosuchfield")`，错误文案点名它 |
| 4 汇总变量按「该行」算 | ✅ 通过 | `aggregate_variables_work`：应发合计 21200、扣款合计 -2100、实发工资 19100、`应发合计 + 扣款合计` = 19100。生产路径另由 `a_row_evaluates_its_formula_fields` 覆盖（汇总**不含**公式字段） |
| 5 除以零 → 报错 | ✅ 通过 | `division_by_zero_is_an_error`：`base_salary / 0` → `DivideByZero`（不是 Infinity） |
| 6 循环引用 → 报错 | ✅ 通过 | `cyclic_formulas_are_reported_not_crashed`：A→B→A 与自己引用自己都返回 `Cycle`，**不是栈溢出**；生产路径同样由 `a_cyclic_formula_is_caught_in_the_row_evaluation` 覆盖 |
| 7 文本字段做算术 → 报错 | ✅ 通过 | `a_text_field_is_a_type_error`：引用 text 字段 → `Type`；引用不存在的字段 → `Unknown`（**两者分得开**） |
| 8 求值用原始数值，格式化在之后 | ✅ 通过 | `rounding_to_cents_hides_float_noise`：`18,000.00` **不是**合法表达式（格式化过的串进不了算术）；求值结果是无逗号的原始数 |
| 9 输出按分四舍五入 | ✅ 通过 | 同上：`1/3` → 0.33、`0.005 + 0.005` → 0.01（不是 0.010000000000000002） |
| 10 语法判定只有一份权威 | ✅ 通过 | `domain::field::check_formula` 已**改为委托给解析器**（原来那套手写的括号/字符集检查已删）。能求值的一定能通过校验，不能解析的一定都被拒 |
| 11 坏公式只影响它自己 | ✅ 通过（机制） | `evaluate_formula_fields` 按字段逐个求值并收集错误，不是一行全废；`evaluate_row` Command 返回「算得出来的那些」+ 具体错在哪个字段 |
| 12 门禁九项全绿 | ✅ 通过 | `FAST=0 bash scripts/gate.sh` →「✓ 门禁全绿」。Rust 单测 **170 passed / 0 failed** |

**浏览器实测（S04 的公式试算）**：在字段编辑弹窗里把类型改成「公式」、填入
「应发合计 + 扣款合计」→ 试算给出结果；四条坏公式全部被拦并给出原因：
`| abs`（只允许字段名与四则运算）、`/ 0`（算不出有限的数）、`nosuchfield`、括号不配平。

### 二、实现期当场改掉的四个问题

1. **词法只认 ASCII 标识符 → 汇总变量解析不了**。设计文档 S04 的公式字面就是
   「应发合计 + 扣款合计」，是**中文**。已改成支持 Unicode 标识符（字段 key 仍是 ASCII，
   TC-200 钉死了那条规则，中文标识符实际上只会是那几个汇总变量）。
2. **`Type` 与 `Unknown` 混在一起**：拿文本字段做算术与引用不存在的字段 Originally 都是
   「未知」。已给上下文加 `text_fields`，两者**分得开**（设计文档 ch.8 明确要求「类型错误」单独一类）。
3. **`evaluate_formula_fields` 没有生产调用方**（clippy 报 dead code）——
   循环检测因此是「等着将来」的。已补 `evaluate_row` Command：按一行求值全部公式列
   （TC-303 逐格编辑、TC-302 导入时都用它），循环检测因此是**活的**。
4. **浏览器预览模式里我自己写了一份求值器** —— 那正是 ADR-0018 反对的「第二份规则」。
   已改成**预览模式不试算**（并说明真机上才有）：求值器只保留 Rust 那一份。

### 三、顺手补齐的（TC-202 的遗漏）

设计文档 ch.8 的内置变量表里有 **邮箱 / 年份 / 月份**，TC-202 落地时漏了，本卡补齐。
TC-202 的评审记录里补了一句说明。

### 四、TC-302 验收时补记的一处缺陷（2026-11-12）

本卡结案后，TC-302（Excel 导入）用行求值时撞出**一处真缺陷**：

**`evaluate_formula_fields` 把 `text_fields` 丢了** —— 它在内部构造 `EvalContext` 时
写死 `text_fields: BTreeSet::new()`。于是标准 7（「拿文本字段做算术 → 类型错误」）
**只在单元测试里成立**：单元测试直接调 `eval_formula` 并自己带上 `text_fields`，
而**生产路径**（`evaluate_formula_fields` → `evaluate_row`）报的是「未知」。

差别不是措辞 —— 使用者看到「公式引用了不存在的字段」会去找字段名，
而真实原因是「这个字段是文本，不能参与计算」。ch.8 要求这两类**分得开**。

已修：`evaluate_formula_fields` 增加 `text_fields` 参数并透传，
`commands::fields.rs::evaluate_row` 与 `infra/fields.rs` 的调用方同步补上。
「拿文本做算术」与「引用不存在的字段」现在在生产路径上也分得开。

（另有一处语义修正记在 ADR-0021 洞六：「配置里有但这一行没填」的字段在公式里按 0 算，
与「配置里根本没有的字段名」报错 —— 那是 TC-302 自己的口径，不属于本卡。）

### 五、结论

- **12 / 12 条已过**，无豁免项，本卡结案：`状态` 转 accepted、ADR-0018 转 accepted、TASKBOARD 更新。
- **2026-11-12 补记**：标准 7 在生产路径上曾有一处缺陷（`text_fields` 被丢），
  已修并补上本节记录；本卡的结论不变。
- **批量重算不在本卡**：月份账套与逐格编辑是 TC-300 / TC-303（那时才有真实的行数据），
  但求值器与循环检测已经就位并在 `evaluate_row` 里活着。
- 公式**条件与比较**不做（设计文档写的是「仅允许引用本行字段与 + - * / ( )」）——
  将来要支持时得重审沙箱口径。
