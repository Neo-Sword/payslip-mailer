# TC-402 · 幂等键 + 中断恢复（只补未发）+ 发送编排屏

状态：**accepted** · 依赖：TC-400（编排骨架）、TC-401（三重核对）、TC-303（记录与 checksum） · 最后更新：2026-11-12

设计依据：设计文档 **ch.7「可中断设计」**（「队列每完成一封即持久化……
应用显示『发现未完成的批次：已发 27/60，是否继续？』——靠幂等键保证已发的人
不会收到第二封」）、**ch.5**（幂等键公式、辅助措施「发送前显示『本次将向 N 人
发送 M 封，请确认』二次弹窗；发送完成后提供『仅重试失败项』」）、
**红线 3**（二次确认）、**红线 4**（重试只针对未成功的 job）。

> **引用口径**：本卡引用设计文档一律用**章号 + 屏号 / 章标题**，不写行号。

决策依据：ADR-0025（本卡六条口径：**sending 存疑恢复时回 queued**、
**恢复可重复发起**、**仅重试失败项 attempts 保留**、**点发送两层核对**、
**真发送器归 TC-500**、**进度从库算**）。

## 目标

做完之后使用者能干什么：

- **点发送**：核对通过 → 确认「本次将向 N 人发送 M 封」→ 批次创建、任务排队。
- **断电不怕**：重启后看到「发现未完成的批次：已发 27/60，是否继续？」，
  继续后已成功的绝不重发。
- **补发有边界**：只补失败的（「仅重试失败项」），没有整批重发。

## 范围

**做**：

1. `infra/batch.rs` 增：`find_unfinished`（最近的 running/paused 批次 + 进度）、
   `recover_batch`（sending → queued + paused → running）、
   `retry_failed`（dead → queued，attempts 保留）。
2. `commands/batch.rs` 增：`start_batch`（**Command 层再核对一遍** → 创建批次）、
   `find_unfinished_batch`、`recover_and_run_batch`（恢复 + 驱动；SMTP 未配置时报
   「发信设置还没配置」）、`retry_failed_jobs`。
3. S11 → 发送编排：核对通过后的「发送」按钮 + 确认对话框
   （「本次将向 N 人发送 M 封……每封一个收件人，绝不抄送」）、
   批次创建后的任务队列视图（queued/sending/success/retrying/dead 计数）。
4. 工作台的「未完成批次」提示（有 running/paused 批次时显示 + 一键去编排屏）。

**不做**（范围膨胀是本项目最大的风险，逐条写清归属）：

- **真 SMTP 发送**（lettre、连接、TLS、真发送器）→ TC-500。
  `recover_and_run_batch` 在凭据未配置时报「发信设置还没配置」—— 事实陈述。
- **发送进度的实时推送**（事件驱动 UI）→ TC-500（发送循环跑起来后接
  `emit("send://progress")`；本卡的进度从库算，够用）。
- **发送历史的完整屏**（S13 批次列表 + 逐封明细）→ TC-403（与日志/凭证一起）。
- **PDF 附件** → v2。

## 验收标准

每条都要在验收时给出**实际观察到的输出**，不接受「已验证」。

**1. 点发送必须核对通过。**
核对 `ok=false`（有被拦的人）→ `start_batch` 返回错误并说清谁被拦；
`ok=true` → 批次创建成功。
*为什么必须有这条*：ADR-0025 决策 4 —— Command 层是唯一关卡，
前端核对通过后数据可能被改。

**2. 二次确认在界面上。**
确认对话框显示「本次将向 N 人发送 M 封」与「每封一个收件人，绝不抄送」；
不确认就没有批次。
*为什么必须有这条*：红线 3。

**3. 幂等键挡重复。**
同一个人同一份内容，同一批次里只有一条 job（UNIQUE 挡；
`idempotency_key` 按 `hash(batch_id:member_id:period_id:checksum)` 生成）。
*为什么必须有这条*：ch.5「重复点发送不会产生第二封」。

**4. 中断后能发现未完成的批次。**
跑到一半（2 success / 1 queued / 1 dead）不再驱动 →
`find_unfinished` 返回该批次与进度（total=4、success=2、failed=1）。
*为什么必须有这条*：ch.7「应用显示『发现未完成的批次：已发 27/60』」。

**5. 恢复后已成功的不重发，存疑的 sending 回队。**
恢复（`recover_batch`）→ sending 的 job 回 queued、批次回 running；
继续驱动 → **success 的没被再发**（假发送器调用次数不含它们），
queued 的发完。
*为什么必须有这条*：ADR-0025 决策 1、2 —— ch.7 的「已发的人不会收到第二封」。

**6. 仅重试失败项。**
`retry_failed` → dead 的回 queued（attempts **保留**、error_code 清空）、
success 的不动；继续驱动 → 只发重试的那几封。
*为什么必须有这条*：红线 4「失败重试只允许针对未成功的 job，不提供整批重发」。

**7. aborted 批次不提供重试。**
批次 aborted（认证失败）→ `retry_failed` 返回错误（引导去 SMTP 设置）。
*为什么必须有这条*：ADR-0025 决策 3 —— 凭据坏时重试没有意义。

**8. SMTP 未配置时点发送报明确错误。**
`recover_and_run_batch` / `run_batch` 在凭据未配置时返回
「发信设置还没配置」—— 不假装成功。
*为什么必须有这条*：ADR-0025 决策 5 —— 假成功是编排的大忌。

**9. 进度从库算。**
批次的 success/failed/total 与逐封的 status **一致**
（逐封持久化时累加，没有第二份进度快照）。
*为什么必须有这条*：ADR-0025 决策 6 —— 「已发 27/60」读库即得。

**10. 门禁九项全绿。**
`FAST=0 bash scripts/gate.sh` → 「✓ 门禁全绿」。九项按名字：Rust 格式、
前端类型检查、设计 Token、Token 引用可解析、敏感数据未进 git、
Rust 静态检查（clippy `-D warnings`）、Rust 单测、加密栈链接、前端构建。
*为什么必须有这条*：发送编排是红线 3/4 的兑现处，门禁是底线。

**验收中发现并当场修的问题**

1. **`retry_failed` 的返回值统计错**：先写成了「queued 且 attempts>0 的数量」——
   把恢复时从 sending 回队的那封也算进去（它没死过，不算「重试」）。
   改为在 `dead → queued` 的 UPDATE 后立即取 `changes()`（回队多少记多少）。

**实现口径的说明**

- **存疑 sending 回 queued**（ADR-0025 决策 1）：发给**本人**的重复无害，
  丢发难查 —— 界面上明说「继续前存疑的任务会回到队列」。
- **两层核对**（ADR-0025 决策 4）：S11 先核（体验）→ 确认对话框 →
  `start_batch` 再核（关卡）。核对不过的错误**点名**被拦的人与原因。
- **aborted 批次恢复后可以补发吗？** 不可以（决策 3）：凭据坏时重试没有意义；
  `retry_failed` 直接拒绝并引导去 SMTP 设置。
- **编排屏的位置**：发送编排接在 S11「预览与核对」屏内（核对通过才能点发送 ——
  两个红线（3/4）的动作在同一个屏上闭环），不是独立屏；范围 v1 = 全部启用成员
  （与 TC-401 一致，范围选择归后续卡）。

**要认的账（本卡遗留的边界，不是缺陷）**

- **TC-402 结案时点发送会停在「SMTP 未配置」**：批次与任务已落库、恢复与补发
  的语义已完整实现并被单测验证；真发送循环的最后一格（`Sender` 的 lettre 实现）
  是 TC-500 的事，接线点已在 `recover_and_run_batch` 里注明 —— 到时代码一行不改。
- **发送进度靠刷新**（`get_batch_progress`），事件推送（`emit("send://progress")`）
  归 TC-500（发送循环跑起来才有事件可推）。
