## 目标

做完之后使用者能干什么：

- 第一次打开应用，看到的是「欢迎使用薪邮」的三步向导，填管理员邮箱 + 口令 + 单位名称就能把这台机器初始化成发件机；初始化完直接进工作台，不用碰命令行。
- 此后每次启动、每次合盖唤醒、每次空闲到点，看到的都是同一张锁屏：显示本机管理员邮箱、输口令、回车进工作台；输错看得见「还剩几次」，连续错 5 次会看到 60 秒倒计时。
- 按 ⌘L 立刻锁上；放着不动到点自己锁上——**界面自己变锁屏，不用点一下也不用刷新**。
- 在设置页把空闲锁定改成 5 / 10 / 30 分钟，**改完这一分钟就生效**，不用重启。
- 出问题时知道发生了什么：钥匙串条目没了有两条路可走（重试 / 重新初始化），迁移漂移了会点出是哪一版，数据库只读时顶部有一条常驻横幅说明「只能查看、改动不会写入」。

这张卡是 **P1 的收口卡**：TC-100 / 101 / 102 交付的 Rust 层（加密库、Keychain、口令、锁定）
到这里第一次被界面接上；前三张卡攒下的六行「落到 TC-103」的遗留全部在这里清掉。

## 验收标准

每条都要在验收时给出**实际观察到的输出**，不接受「已验证」。
标 🙋 的两条（11、19）必须由使用者本人在真机上做，机器跑不出来。

**1. 空数据目录首启：看到的是 S01，不是一个空工作台。**
删掉 `~/Library/Application Support/cn.payslipmailer.desktop/` 后起 app，
界面是「欢迎使用薪邮」+ 三步指示（1 创建管理员 / 2 配置发件邮箱 / 3 完成引导），
**侧栏不出现**；DevTools 里 `admin_status` 的返回 `initialized == false`。
**应用要能自己把那个目录建出来** —— 真机首启时它本来就不存在
（ADR-0012 第 1 条实测过），不会有人替它建。
*为什么必须有这条*：`admins` 表无行时 Rust 层会报 `NOT_INITIALIZED`，
TC-100/101/102 三张卡都没有界面承接它。没有这条，首启会渲染出一个
「已解锁但什么都没有」的工作台，用户以为数据丢了。

> **验收中发现 spec 缺陷（2026-11-11，本卡实现期）**：本条原文只说
> 「删掉目录后起 app」，**没要求应用会自己把它建出来**。实测发现：
> 原来的 `open_with` 直接拿目录去连库，全新机器上那个目录根本不存在，
> SQLite 报「unable to open database file」，首启的 `admin_status` 直接失败，
> 使用者看到的是「没能读到本机状态」而不是 S01 向导。
> 已改为 `open_with` 自己 `create_dir_all`（只建目录，不建库文件，
> 钥匙串守卫不受影响），并补了单测
> `db_creates_the_data_directory_on_first_open` 与
> `db_creating_the_directory_does_not_break_the_keychain_guard`。

**2. `create_admin` 有 Command 入口，且库里真的出现管理员行。**
`grep -n 'allow(dead_code)' src-tauri/src/infra/admins.rs` 命中 0 次；
`grep -n 'create_admin' src-tauri/src/lib.rs` 在 `invoke_handler` 列表里命中；
向导填完提交后，用临时工具读 `data.db` 的 `admins` 表：恰好 1 行、`id == 1`、
`pwd_hash` 以 `$argon2id$` 开头。
*为什么必须有这条*：`create_admin` 从 TC-102 起就带着「未接线：入口归 TC-103」的注释。
注释消失 + 注册表里有它，才是真的接上了；只看界面「初始化成功」挡不住
「前端调了一个没注册的 Command，错误被 toast 吞掉」。

**3. 表单实时校验：口令不足 10 位、两次不一致、邮箱格式不合格，三种情况都禁用「下一步」并给出可见提示。**
逐个复现：输 9 个字符 → 提示含「至少 10 位」且「下一步」禁用；补到 10 位 → 解禁；
确认框少打一个字符 → 再次禁用；邮箱停在 `hr@` → 禁用；改成 `hr@company.com` → 解禁。
口令强度条随长度/字符种类变化（设计文档 S01 交互要点原文：「邮箱格式实时校验；密码强度条；
两步密码不一致即禁用『下一步』」）。
*为什么必须有这条*：这是文档写死的交互，也是唯一能在**提交前**拦住弱口令的地方。
后端 `check_password_policy` 已经会拒，但没有这条的话，用户要点了「下一步」才知道
自己少打了一个字符。

**4. 后端兜底：直接把一个没有 `@` 的邮箱喂给 Command，返回 `VALIDATION_ERROR`，且库里不留行。**
绕过界面直接 `invoke("create_admin", { email: "hr", password: <10位>, orgName: "X" })`
→ 返回 JSON 的 `code == "VALIDATION_ERROR"`；随后读 `admins` 表仍是 0 行。
同时 `grep -n 'INVALID_EMAIL' src-tauri/src/commands/auth.rs` 命中 0 次。
*为什么必须有这条*：前端的「实时」只是体验，不是防线。
不用 `INVALID_EMAIL` 是 TC-102 文件头写下的口径（那个码归 TC-201 的成员批量粘贴，
两个场景的文案与「批量」语义不同），挪用会让 TC-201 到时候无从区分。

**5. 单位名称落 `app_meta.org_name`，重启后仍在。**
向导里填「测试单位甲」→ 完成 → ⌘Q → 重开 → 解锁 → S14 显示「测试单位甲」；
读库 `SELECT value FROM app_meta WHERE key = 'org_name'` 得到同一字符串。
*为什么必须有这条*：S01 表单里有这一栏，文档说它是「邮件模板默认值」。
`admins` 表没有这一列，实现时最容易顺手「先做个输入框，回头再存」，
于是 TC-202 的模板引擎读到一个空值，而界面上明明填过。

**6. 「稍后设置」真的能跳过 SMTP：进工作台、不报 SMTP 错、Keychain 里只有 `db-key`。**
在第 1 步点「稍后设置」→ 直接进工作台；DevTools 网络/控制台无 SMTP 相关报错；
`security find-generic-password -s cn.payslipmailer.db-key -g` 有条目，
按 `smtp-credential` 查则查不到（不预置空凭据）。
*为什么必须有这条*：ADR-0012 §2 把「测试连接」后置是有代价的决定，
代价必须钉在验收里：如果实现时顺手加了「必须填 SMTP」的门槛，
真实账号到位之前整个首启流程在这台机器上跑不通。

**7. 初始化后重启：出现的是 S02 而不是 S01，解锁后进工作台。**
承上：⌘Q 后重开 → 界面是「薪邮 · 解锁」+「已锁定」徽标；
输对口令 → 进工作台；`admin_status` 返回 `initialized == true`、`unlocked == true`。
*为什么必须有这条*：设计文档 ch.13 P1 验收标准原文有「重启后数据完整」。
这条同时钉住「DB key 在 Keychain 里活过重启」与「首启判定读的是库不是内存标记」。

**8. S02 与设计文档逐字对齐，且「看一眼状态」不会把人解锁。**
逐项比对：徽标「已锁定」、标题「欢迎回来」、显示本机管理员邮箱、字段标签「登录密码」、
开关默认 **ON** 且文案「记住本机 10 分钟」、链接「忘记密码？」、
主按钮「解锁并进入工作台」、琥珀色提示原文
「密码连续错误 5 次将锁定 60 秒。本机数据已加密，无法通过重装应用绕过。」、
页脚「数据仅存本机 · 无遥测」字样。
另外在锁定态连续调两次 `admin_status`，两次都必须返回 `unlocked == false`。
*为什么必须有这条*：后半句是 ADR-0012 §7 的坑——`probe` 为了读邮箱会自己临时开库，
`unlocked` 若照 `db.is_open()` 取会恒为 `true`，锁屏永远进不去，
而且「锁定态下库是关的」这条不变量会被一个只读操作悄悄破坏。

**9. 回车即提交；失败次数与倒计时可见。**
在密码框按回车 → 触发解锁（不用点按钮）；输错一次 → 界面出现剩余次数（与
`admin_status.remaining_attempts` 一致）；连续错到第 5 次 → 出现 60 秒倒计时，
肉眼可见每秒递减，且倒计时内再提交仍返回 `LOCKED`、库里 `failed_attempts` 不变。
*为什么必须有这条*：设计文档 S02 交互要点原文「回车即提交；失败次数与倒计时可见」。
Rust 层（TC-102 标准 6/7）已经把秒数算好了，界面不透出等于白算。

**10. ⌘L 立刻锁定。**
解锁态按 ⌘L → 界面立刻回 S02，`admin_status` 返回 `unlocked == false`；
再输口令能进。
*为什么必须有这条*：设计文档 ch.11 快捷键原文「⌘L 立即锁定」。
`lock_now` 这个 Command 从 TC-102 起就在，但没有键绑定等于 HR 手边没有锁。

**11. 🙋 真人合盖 → 唤醒必现锁屏。**
解锁状态 → 合上盖子 ≥2 分钟 → 打开 → 界面是 S02（不是原样的工作台）。
由使用者做，验收记录写观察结果与时间。
*为什么必须有这条*：TC-102 只有跨进程模拟的投递证据（ADR-0011 §8「自发不投递」+ §10 四组对照），
结案遗留里明确写着「不想擅自睡掉使用者的机器」，所以这条一直悬着。
设计文档 ch.13 P1 必测边界原文含「系统休眠唤醒」。

**12. 空闲到点后，界面自己变锁屏，不需要点一下也不需要刷新。**
用 Command 把阈值设成 1 分钟（`set_idle_lock_minutes`，界面下拉没有 1 分钟这一档），
放着不动 ≥70 秒 → 界面**无人操作**的情况下变成 S02；期间不点鼠标不按键。
*为什么必须有这条*：这是 ADR-0012 §6 那条事件通道的唯一可观察证据。
没有它，锁定只发生在 Rust 层（库关了），前端仍显示「已解锁」的样子让人继续点，
每个操作都失败——正是「静默失败」那种最难查的形态。

**13. 设置页 5/10/30 分钟下拉，改完当前会话立刻生效。**
S14「安全与锁定」的下拉恰好三项 5 / 10 / 30；选 5 → `app_meta.idle_lock_minutes == 5`，
**不重启**、放着不动 6 分钟 → 锁屏（默认 10 分钟时这 6 分钟不会锁，所以能归因于改动生效）。
*为什么必须有这条*：TC-102 的 `set_idle_lock_minutes` 是「先落库后改计时器」，
落库那半有单测，**计时器那半没有端到端证据**——「改完要重启才生效」这种实现
能骗过所有单元测试。

**14. 「记住本机 10 分钟」= 本次解锁阈值取 `max(库里阈值, 10 分钟)`，不写库、重启失效。**
机制（秒级，单元测试）：库里阈值 5 分钟时，勾选解锁后 `LockWatch` 的空闲阈值是 10 分钟；
不勾是 5 分钟；两种情况下 `app_meta.idle_lock_minutes` 都仍是 5。
真人（与标准 13 共用观察）：库里 5 分钟 + 勾选 → 不动 6 分钟**不锁**；
库里 5 分钟 + 不勾 → 不动 6 分钟**锁**（即标准 13 那次）。
重启失效：重启后不勾，6 分钟 → 锁。
另外确认它**不影响**唤醒锁定与 ⌘L：勾选状态下按 ⌘L 仍立刻锁。
*为什么必须有这条*：设计文档只有那个开关的字面，语义一个字没写（ADR-0012 §8）。
最自然的错实现是「把 10 分钟写进 `app_meta`」——一个看起来只作用于本次的开关
永久改掉全局设置。界面文案还必须诚实：库里是默认 10 分钟时这条是恒等操作。

**15. `KEYCHAIN_MISSING` 给两条分支，且不覆盖旧库文件。**
删掉 Keychain 里的 `db-key`（`data.db` 留着）→ 起 app → 界面是专属引导，
**不是**通用文案「本机加密数据打不开」，且有两个可点的动作：「重试」「重新初始化」。
点「重试」→ 仍报 `KEYCHAIN_MISSING`；前后对比 `data.db` 的字节数与 mtime **一字不变**
（没被新密钥的空库盖掉）。
*为什么必须有这条*：TC-100 结案遗留「`KEYCHAIN_MISSING` 在『开机打开库』这条路上的引导
还没有界面承接」。`load_or_create_key` 的守卫（`infra/db.rs:219-234`）是库层保证，
但界面若把它显示成「初始化向导」并让用户直接建档，就等于用 UI 绕过了那个守卫。

**16. 只读态有常驻横幅：解锁后仍在，写被拒时文案与横幅一致。**
制造只读（见标准 17 的 checksum 漂移即可顺带产生）→ 顶部出现横幅，
文案含三要素（发生了什么 / 影响范围 / 下一步），**没有关闭按钮**；
解锁进工作台后横幅**仍在**；此时任何写操作被拒，返回文案
「数据库处于只读状态（迁移未完成），本次修改未写入」与横幅说的是同一件事。
*为什么必须有这条*：TC-100 结案遗留原文「用户看到的是通用 DATABASE 文案
『本机加密数据打不开』，但实际状态是『已解锁、能读、不能写』——文案与状态不符」。
用 toast 也不行：`overlay.tsx` 的成功提示 3 秒自动消失、失败提示可手动关，
而只读是整个会话的持续状态（ADR-0012 §5）。

**17. 迁移 checksum 漂移有专属码 `MIGRATION_DRIFT`，文案点出是哪一版。**
把 `migrations/0002_admins.sql` 里加一个空格后重编、起 app：
**写路径与日志**里出现 `code == "MIGRATION_DRIFT"`（不再是 `DATABASE`）；

> **验收中发现 spec 缺陷（2026-11-11，本卡实现期）**：本条原文写的是

> 前端要显示的是「发生了什么 + 影响范围 + 下一步」，不是给排障人看的码。

## 评审记录

验收日期：2026-11-11 · 验收方式：Rust 验收测试（15 条，新增 `src-tauri/src/acceptance.rs`）
+ 浏览器实测 + 真机应用实测 + 门禁九项。

**先说验收中发现的东西**（按 docs/README.md §4：未过项当场修，spec 写错了先改 spec）：

### 一、修掉一个真 bug（标准 1 那一半）

**现象**：全新机器首启时，`admin_status` 直接失败，界面是「没能读到本机状态」而不是 S01 向导。
**根因**：`infra::db::open_with` 直接拿数据目录去连库，但**生产代码里没有任何地方创建那个目录**
（`create_dir_all` 只出现在测试基座里，所以几百条测试一条都没碰到它）。
真机首启时 `~/Library/Application Support/cn.payslipmailer.desktop/` 原本不存在（ADR-0012 第 1 条实测过），
SQLite 打不开不存在目录里的文件。
**修法**：`open_with` 自己 `create_dir_all`（**只建目录，不建库文件** ——
钥匙串守卫靠 `db_path.exists()` 判断，目录被建出来不影响它）。
**钉住**：`db_creates_the_data_directory_on_first_open`（目录不存在时能开库）
+ `db_creating_the_directory_does_not_break_the_keychain_guard`（守卫没被破坏）。
**spec 同步修订**：标准 1 补上「应用要能自己把那个目录建出来」，并注明这是验收中发现的 spec 缺陷。

### 二、spec 缺陷修订（标准 17）

原文写「`admin_status` / 启动路径返回的 `code == "MIGRATION_DRIFT"`」——**与实现不符，已改写**。
实测 `open_with` 遇漂移走的是 `Ok(OpenOutcome::ReadOnly { error, .. })`，错误**不外传**，
所以 `admin_status` 返回 `Ok` + `read_only: true`，拿不到那个码。
该码真正可观察的是三处：单元测试、启动时的 `tracing::warn!` 日志行（带两个校验和）、
以及横幅文案里点出的版本号。改的是 spec，不是代码去迁就 spec。详见该条正文。

### 三、改了一条已结案 TC-100 的断言

`infra::db` 里 `db_failed_migration_rolls_back_and_signals_read_only` 原本断言
只读写被拒的错误码是 `DATABASE`。TC-103 按 ADR-0012 第 4/5 条把它换成专属码 `READ_ONLY`
（旧实现下 `user_message()` 会把「已解锁、能读、只差写入」说成「本机加密数据打不开」，
与状态矛盾）。**这是对已结案 TC-100 标准 6/7 断言的变更**，依据写在这里，不是偷偷改。
