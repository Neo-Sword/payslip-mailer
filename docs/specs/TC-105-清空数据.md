# TC-105 · 清空数据（销毁）

状态：accepted · 依赖：TC-100（SQLCipher 库）、TC-101（Keychain）、TC-104（备份导出/恢复） · 最后更新：2026-11-11

（「清空数据：二次确认 + 输入管理员密码，安全删除 data.db 与 Keychain 条目」）
与「原则：一份库、全库加密、凭据分离、可迁移、**可销毁**」；**ch.10 合规要点**
（「用户可随时导出全部个人数据 / 彻底清空数据（可携带权与删除权）」）；
**ch.12 界面原型** 的 S14「清空数据需输入管理员密码并二次确认，不可撤销」
与 S15「危险操作二次确认」（确认框文案逐字照抄）；
**ch.6 磁盘布局**（`exports/` 与 `logs/` 两个目录的位置）。

> **引用口径**：本卡引用设计文档一律用**章号 + 屏号 / 章标题**，不写行号。

决策依据：ADR-0014（本卡六条口径：**先删库后删钥匙串条目**、备份一起删且在确认框里点名、

销毁后回到 S01）；ADR-0013 §9（本卡从备份那张卡里拆出来的理由）；
ADR-0009（钥匙串条目的删除走既有实现）；ADR-0011 §5（口令验证复用既有 Argon2id 校验）。

## 目标

做完之后使用者能干什么：

- **一句话删干净**：在设置页点「清空数据」，输入管理员口令，确认，
  这台电脑上关于薪邮的一切（库、备份、密钥）就没了 —— 不可撤销，但**真的没了**。
- **不会删到一半**：中途出错也不会把用户锁在门外（钥匙串条目最后删，
  崩在中间也停在「能重新初始化」的那一侧）。
- **删之前看得见**：确认框逐项列出会被删掉什么，包括「备份文件也会一起删除」，
  以及「日志会保留（已脱敏）」。

## 范围

**做**：

1. `infra/wipe.rs`（或 `infra/admins.rs` 内的一个函数）：销毁的核心逻辑 ——
   校验口令 → 删库 → 删暂存文件 → 删 `exports/` → 删钥匙串条目。
2. `admins::verify_password`：**无副作用**的口令校验（不写回锁定计数）。
3. `commands/auth.rs`（或新文件）加 `wipe_data` Command：
   入参是管理员口令；返回「删了什么」的清单。
4. S14「数据备份」段加「清空数据」按钮 → 危险确认框（**红色 + 要求输入管理员口令**）。
5. 销毁完成后前端自动回到 S01 首启向导。
6. 确认框文案逐字对齐设计文档 S15 的原型：
   标题「确认清空全部本地数据？」+「将永久删除……操作不可撤销。」+「请输入管理员密码以继续：」。

**不做**（范围膨胀是本项目最大的风险，逐条写清归属）：

- **「撤销销毁」/ 回收站** → 不做。设计文档写明「不可撤销」。
- **只删成员、只删某个月份、只删某个批次** → 不做。
  「数据最小化」与「可销毁」是产品级操作，做细了就会有人误删一部分。
- **删除 `logs/`** → 不做（ADR-0014 决策 3：日志脱敏、不含个人数据，
  且合规上「保存 2 年以上备查」指的是发送记录）。
- **把备份上传到别处以备恢复** → 不做（红线：数据不出本机）。
- **销毁前的自动备份** → **不做**。TC-104 的恢复流程里有「恢复前自动备份当前库」，
  销毁**刻意没有**：自动备份一份马上要删的数据，是把「删干净」这件事变成
  「删干净但留了一份副本」—— 那不叫清空。
- **多机/共享库下的删除语义** → 不做（本项目是单机单管理员；
  设计文档 ch.10 明说「多机共享需另行评估」）。

## 验收标准

每条都要在验收时给出**实际观察到的输出**，不接受「已验证」。

**1. 口令不对：一个字节都不删。**
在设置页点「清空数据」，输入**错误的**管理员口令 → 报错，且
`data.db` 还在（md5 不变）、钥匙串条目还在（`security find-generic-password` 查得到）、
`exports/` 里的备份一个不少。
*为什么必须有这条*：销毁是不可撤销的。「口令打错就把数据删了」是不可接受的；
验证与删除必须分成两步，验证失败直接返回。

**2. 口令正确：库、备份、密钥三样都不留。**
输入正确的管理员口令并确认 → `data.db` 不存在；`exports/` 目录不存在（或为空）；
`security find-generic-password -s cn.payslipmailer.db-key` 查不到。
*为什么必须有这条*：「彻底清空」的核心。少删一样，用户就会在别处发现自己的工资数据
—— 那是合规问题，不是体验问题。

**3. 删除顺序是「先库后密钥」，崩在中间也停在可恢复的那一侧。**
把钥匙串条目的删除这一步人为做成失败 → 库已被删、条目还在 → 下次启动
应用回到 S01 首启向导（而不是卡在 KEYCHAIN_MISSING 引导页循环）。
*为什么必须有这条*：ADR-0014 决策 1。这两个半成品状态的代价完全不对称：
「条目没了库还在」会把用户**锁在门外**。这条要把顺序钉成可观察的行为。

**4. 确认框要求输入管理员口令，且是红色危险操作。**
点「清空数据」→ 弹框标题「确认清空全部本地数据？」；**不输口令时「确认清空」是禁用的**；
按钮是危险色（红）。
*为什么必须有这条*：设计文档 S14/S15 两处都写明「二次确认 + 输入管理员密码」，
且 S15 的交互要点写「危险操作红色 + 密码确认」。

**5. 确认框逐项列出会删什么，包括备份。**
框里能看到：数据库（成员名单、工资数据、批次记录）、**本机的备份文件**、
钥匙串里的密钥、以及「不可撤销」；还能看到「日志会保留（已脱敏）」。
*为什么必须有这条*：备份一起删是不可逆的那部分（ADR-0014 决策 2）。
不点名的话，用户点完才发现唯一的备份没了 —— 那是产品事故。
日志留着也要说清楚，不说就是隐瞒。

**6. 销毁完成后应用回到 S01 首启向导。**
销毁完 → 界面切回「欢迎使用薪邮」的三步向导；`admin_status` 的
`initialized == false`、`unlocked == false`。
*为什么必须有这条*：销毁完不能停在「已解锁但什么都没有」的工作台 ——
那会让人以为数据还在，或者以为出了故障。

**7. 钥匙串里那条「neo」旧条目不受影响。**
销毁前记下钥匙串里那条 `account=neo` 的旧条目（2026-10-18）→ 销毁 →
那条**还在**。
*为什么必须有这条*：销毁只清薪邮自己的东西。钥匙串是用户的，
应用没有权力删别人的条目 —— 这一条是「最小必要」原则在钥匙串上的体现。

**8. 口令验证不计入那 5 次失败锁定。**
在解锁态连续输错 3 次口令 → 没有被锁定，也没有任何锁定计数被写回。
*为什么必须有这条*：ADR-0014 决策 5。那 5 次锁定是给锁屏上的登录用的；
销毁入口本来就在解锁态（用户已经拿着全部数据），计数只会让人不敢再试。

**9. 库文件是被删掉的，不是被「清空内容」的。**
销毁后 `data.db` 不存在（不是「存在但 0 行」）。
*为什么必须有这条*：把表清空而留着文件，会在磁盘上留下「曾经有 42 位成员」的痕迹
（free page、journal、WAL 都可能残留）。删文件是唯一干净的做法。

**10. 门禁九项全绿。**
`FAST=0 bash scripts/gate.sh` → 「✓ 门禁全绿」。九项按名字：Rust 格式、
前端类型检查、设计 Token（色值只允许出现在 `tokens.css`）、Token 引用可解析、
敏感数据未进 git、Rust 静态检查（clippy `-D warnings`）、Rust 单测、
加密栈链接（`otool`：链 `Security.framework`、零 `libcrypto`/`libssl`）、前端构建。
*为什么必须有这条*：本卡第一次碰**不可撤销**的删除路径，
门禁与单测是它唯一的自动化护栏。

### 二、实现期的几个决定

- **不覆写擦除**：APFS + SSD 上覆写不可靠（写时复制 + 磨损均衡让物理块不可寻址）。
  真正的安全性质是「钥匙串里那把 key 没了 ⇒ 密文永远解不开」，所以实现只做
  「删文件 + 删密钥」，**不假装**做了物理擦除（ADR-0014 决策 4）。
- **销毁不做「先自动备份」**：TC-104 的恢复流程里会自动备份当前库，销毁**刻意没有** ——
  自动备份一份马上要删的数据，是把「删干净」变成「删干净但留了一份副本」。
- **日志留着**：脱敏、不含个人数据，且合规上「保存 2 年以上备查」指的是发送记录。
  确认框里写明了「保留 日志」，不说就是隐瞒。
- **新增错误码 `WIPE_PASSWORD_WRONG`**：不复用 `BadCredentials` ——
  那一句带「连续失败 5 次将锁定 60 秒」，而销毁口令**不锁定**（ADR-0014 决策 5），
  前端要能给出「口令不对，什么都没删」这个准确的下一步。
