# TC-602 · 概览屏接线 + 常驻备份提醒 + 依赖漏洞扫描

状态：**in_progress** · 依赖：TC-600 · 最后更新：2026-11-12

设计依据：设计文档 **ch.13**（「发布门槛：无高危 clippy / 依赖漏洞」「必测边界用例」）、
**ch.14**（风险表「凭据丢失 / 忘记管理员密码 → 缓解：**首次启动强制引导导出加密备份；设置页常驻备份提醒**」）、
**ch.3**（S03 概览屏）、「必测边界用例」。

决策依据：**ADR-0031**（依赖漏洞的处理口径：**不可达即记录并豁免，不为看不见的漏洞升级存储引擎**）、
**ADR-0010** §5（`journal_mode = delete`，不用 WAL）、**ADR-0013**（备份口令与管理员口令两回事）。

## 目标

- **概览屏不再有一处假数据**：四个统计块、最近批次表、本月进度、日期，全部来自后端。
- **备份这件事不再只靠"想得起来"**：设置页常驻提醒「上次备份是什么时候」，
  首次建档后给一次导出备份的引导。
- **发布门槛里的「无高危依赖漏洞」变成真的检查**：门禁里有一项，CI 里跑同一条，
  豁免只有一条且写明理由。

## 范围

**做**：

1. **概览屏接真实数据**（六处）：
   在册成员（`member_count`）、邮件组（`list_groups`）、已配置工资项（`list_fields` 里启用中的）、
   上月送达率（最近一个批次的 `success / total`）、最近发送批次表（`list_send_history`）、
   本月发薪进度（当前账套的状态 + 已导入行数 + 整月合计）、顶部日期（真实今天）。
2. **常驻备份提醒**：
   `app_meta` 记 `last_backup_at`（键值表，**不需要迁移**）；
   `export_backup` 成功后写该键；设置页显示「上次备份：<时刻>（N 天前）」，
   从没备份过 → 常驻提醒条；超过 30 天 → 提醒。
3. **首次建档后的备份引导**：S01 走完之后给一次「导一份加密备份」的引导（可跳过；
   跳过后记下来，不反复打扰）。
4. **依赖漏洞扫描进门禁与 CI**：
   `scripts/audit.sh`（拉不动数据库时回退本机库并**明确标注**「可能不是最新」）；
   门禁新增第 10 项；CI 装 `cargo-audit` 并跑同一条；
   `.cargo/audit.toml` 里**窄豁免**（只有一条，理由写在注释里）。

**不做**：

- **升级 rusqlite** → 见 [ADR-0031](adr/0031-依赖漏洞的豁免口径.md)：升级到最新也修不掉
  SQLCipher 这一支，而那条漏洞在我们这里的**前提不成立**（不用 WAL ⇒ 没有 `-wal` 兄弟文件）。
- 送达率的趋势图 / 多月份对比 → v1 只算最近一个批次。
- 定时自动备份、备份保留策略 → 手工备份。
- 依赖**许可**检查（`cargo deny`）与重复依赖 → v1 只做漏洞。
- 上月送达率的"上月"跨年口径 → v1 取最近一个批次，不按自然月回溯。

## 验收标准

**1. 概览屏四个统计块来自后端。**
在册成员 = `member_count`；邮件组 = `list_groups` 的条数；已配置工资项 = 启用字段数；
上月送达率 = 最近批次的 `success / total`（**没有批次时显示「—」，不显示 100%**）。
*为什么必须有这条*：概览屏是使用者每天第一眼看到的屏幕，写死的数字比没有数字更糟。

**2. 「最近发送批次」表是真数据。**
表内容 = `list_send_history()`；**没有批次时显示空状态**，不显示任何假行。
*为什么必须有这条*：同上 —— 一行假的「2026-10 工资条 全部成功」会让人以为账已经发过了。

**3. 「本月发薪进度」反映真实账套。**
有账套 → 显示月份、状态、已导入行数、整月合计（`list_records` / `get_period_totals`）；
没有账套 → 引导去建，而不是显示 66% 的假进度条。

**4. 概览组件里没有写死的统计数字。**
脚本 grep 断言：概览组件的源码里不出现 `42` / `3` / `10` / `100%` 这类字面量（版本号、列宽之类的除外）。
*为什么必须有这条*：「概览屏接线」这件事必须可证伪，否则下一次重构很容易把假数据放回去。

**5. 备份提醒在设置页常驻。**
从没备份过 → 提醒条在；导一次备份 → 「上次备份」变成真实时刻；超过 30 天 → 提醒。
*为什么必须有这条*：ch.14 把「凭据丢失」列为中风险，缓解措施写的就是这条。

**6. 首启后的备份引导只出现一次。**
S01 完成后出现引导；跳过 → 记下来，之后不再出现；点「去导出」→ 打开备份段。
*为什么必须有这条*：ch.14 写的是「强制引导」—— 但**硬拦截会在还没有任何数据时逼人导出一份空库**，
所以本卡按「引导 + 只提醒一次」落地（差异写进评审记录）。

**7. 依赖漏洞扫描有结果。**
`bash scripts/audit.sh` → 无未豁免的漏洞；豁免表里**只有 RUSTSEC-2026-0459 一条**，
理由写在 `.cargo/audit.toml` 的注释里。
*为什么必须有这条*：ch.13 的发布门槛明写「无高危依赖漏洞」——
而**在装上扫描工具之前，这句话是没有执行过的**。

**8. 豁免的前提仍然成立。**
Rust 单测 `db_journal_mode_stays_delete` 仍绿 —— `journal_mode = delete`
⇒ SQLite **不会**创建 `-wal` 兄弟文件 ⇒ CVE-2026-119375 的触发前提不成立。
这条是豁免的**依据**，所以它必须是一条可跑的断言，而不是一句注释。
*为什么必须有这条*：豁免的依据如果会悄悄失效，豁免就变成了漏洞的藏身之处。

**9. 门禁十项全绿。**
`FAST=0 bash scripts/gate.sh` → 「✓ 门禁全绿」（原九项 + 新增「依赖漏洞扫描」）。
CI 跑同一份 `gate.sh`（CI 里另装 cargo-audit）。

**10. 发布记录与安装说明不受影响。**
`scripts/release.sh` 仍能产出 dmg + 校验和 + 发布记录（新增的依赖检查不改变发布链）。

**验收中发现并当场修的缺陷**

1. **预览模式缺三块假数据**（`listSendHistory` / `listRecords` / `getPeriodTotals`）→
   概览屏在浏览器预览里整屏是「—」加一条红色报错。补上与后端同口径的假数据后，
   预览里能看见真实布局（这也是本卡验收手段本身的一部分）。
2. **账套状态显示成了英文 `draft`**（第一版接线时直接把后端的 status 字符串贴上）→
   改成与「月度工资表」同一套中文词（草稿 / 待发送 / 发送中 / 已发送 / 已归档）。

**与设计文档的一处差异（按 spec 的口径落地，不是缺陷）**

ch.14 写的是「**首次启动强制引导**导出加密备份」；本卡落地为「**引导 + 只提醒一次**」。
理由：硬拦截会在「还一条数据都没有」的时候逼人导出一份空库 —— 那时的备份没有意义；
真正兜底的是设置页里**常驻**的那条提醒（标准 5 已验）。差异记在这里。

**要认的账（本卡遗留的边界）**

- **标准 6 的触发时机要真机**（清空数据 → 重新初始化 → 引导出现；跳过后不再出现）。
- **`cargo audit` 的 advisory 数据库在本机拉不动**（github.com 的 git 协议与 codeload 在本网络超时，
  SSH 正常）→ 本机用手动克隆的 `~/.cargo/advisory-db` + `--no-fetch`；
  `scripts/audit.sh` 会**明说**「可能不是最新的」，不装作是最新的。CI 里走正常拉取。
- **性能目标与边界用例不在本卡**（冷启动 <2s / 5000 行导入 <8s / 100 封队列无内存增长 /
  主界面交互 <100ms；「中文全角数字」与「超大 Excel 5000 行」两个必测边界用例）→ 归 **TC-603**。
