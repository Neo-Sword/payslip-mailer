# TC-300 · 月份账套（状态机 + 字段快照冻结）

状态：accepted · 依赖：TC-100（SQLCipher 库）、TC-200（工资条项目）、TC-203（公式求值器） · 最后更新：2026-11-12

设计依据：设计文档 **ch.5 状态机**（月份账套 `salary_periods.status`：
草稿 draft → 待发送 ready → 发送中 sending → 已发送 sent → 已归档 archived；
「**发送中/已发送状态禁止编辑工资数值**；如需纠错，走『**解锁 → 生成修订记录 →
仅对未发送者补发**』」）、**ch.6 数据设计**（`salary_periods | id, year_month, status,
field_snapshot, locked_at | UNIQUE(year_month) | field_snapshot 冻结当月字段定义，
防止事后改字段导致历史错位」；`audit_log | id, action, target, detail_masked, at |
记录登录、改配置、导入、发送、**解锁**、导出」；`salary_records` 的归属）、
**ch.12 界面原型** 的 S07「月度工资数据」（月份切换、状态 chip、导出空模板 / 导入 Excel /
前往预览核对、记录数与校验状态、已发送账套默认只读）、**ch.9** 的合规要点
（「电子工资条有效性依赖证据链」）、**ch.4** 红线 8（字段只能停用不能删除）。

> **引用口径**：本卡引用设计文档一律用**章号 + 屏号 / 章标题**，不写行号。

决策依据：ADR-0019（本卡八条口径：**冻结点 = draft → ready**、**draft 用当前配置而
ready 起用快照**、**`is_editable` = draft | ready**（修正 TC-000 时代的旧口径）、
**解锁 = sent → draft 且必留修订记录**、`year_month` 存 TEXT `YYYY-MM`、
**快照存 JSON 数组**、`locked_at` 记进入 sending 的时刻、本卡建 `audit_log` 表）；
ADR-0015（字段是用户数据，所以需要快照把「当时」钉住）；红线 8。

## 目标

做完之后使用者能干什么：

- **开一个月的账套**：选个月份，这个月就是一个独立的账套，有自己的状态。
- **改字段配置不会弄乱历史**：改了「基本工资」的显示名或加了「季度补贴」，
  上个月已发送的工资条表头**一个字都不变**。
- **状态看得见**：草稿 / 待发送 / 发送中 / 已发送 / 已归档，一眼知道这个月走到哪了。
- **发错了能改，但要留痕**：已发送的账套可以「解锁」回到草稿重改，
  而每一次解锁都留下一条修订记录（可举证）。

## 范围

**做**：

1. 迁移 `0006_salary_periods.sql`：`salary_periods` 表
   （id / year_month / status / field_snapshot / locked_at，`UNIQUE(year_month)`）
   + `audit_log` 表（id / action / target / detail_masked / at）。
2. `domain/period.rs` **接线**（删掉 TC-000 时代留下的两处 `#[allow(dead_code)]`）：
   状态 ↔ 字符串的解析与序列化、
   **`is_editable` 修正为 draft | ready**（设计文档只禁 sending/sent）、
   加「解锁」这条特殊迁移（sent → draft）。
3. `infra/periods.rs`：账套的读写 ——
   新建（按年月）、列出、查状态、合法迁移、
   **进入 ready 时冻结字段快照**、读快照、
   **解锁（sent → draft + 写一条修订记录）**。
4. Command：`list_periods` / `create_period` / `get_period` / `transition_period` /
   `unlock_period` / `get_period_snapshot`。
5. S07 的界面骨架：月份切换下拉 + 状态 chip + 「导出空模板 / 导入 Excel /
   前往预览核对」三个按钮（后两个的实现在 TC-301 / TC-302 / TC-401，本卡只给位置与说明）。
6. 界面上能看出「这个月用的是快照还是当前配置」（ready 之后的月份列名来自快照）。

**不做**（范围膨胀是本项目最大的风险，逐条写清归属）：

- **工资记录**（`salary_records`，逐格编辑、合计行）→ TC-303。
- **导出空模板** → TC-301；**Excel 导入与行级校验** → TC-302。
- **发送**（ready → sending → sent 的推进、补发、幂等）→ TC-402（P4）。
  本卡只提供状态与迁移的**能力**，不驱动发送。
- **「仅对未发送者补发」** → TC-402（它才有 `send_jobs` 能判断谁收到了）。
- **锁定月份**（一个年月的账套被别的月份占用）→ 不做。
  `UNIQUE(year_month)` 已经保证一个年月只有一个账套。

## 验收标准

每条都要在验收时给出**实际观察到的输出**，不接受「已验证」。

**1. 账套的状态机就是设计文档那五个状态，迁移不能跳。**
`list_periods` 能看到状态；`draft → sent`（跳级）被拒；`sent → ready`（回退）被拒；
`archived` 是终态。
*为什么必须有这条*：设计文档 ch.5 的状态机是原文。
状态机的作用就是**拦住**「没校验就发了」「发了还能改」这类事故。

**2. 一个年月只有一个账套。**
同一个 `year_month` 建两次 → 第二个被拒。
*为什么必须有这条*：设计文档 ch.6 的 `UNIQUE(year_month)`。
一个月份两个账套 = 同一份工资发两遍。

**3. 草稿期间字段配置可以随便改，界面跟着变。**
建一个 draft 账套 → 加一个字段「季度补贴」→ 该月的列就多一列。
*为什么必须有这条*：HR 配字段与录数据是同时进行的，
快照在创建时就冻结会让新字段进不了这个月（ADR-0019 洞一）。

**4. 进入 ready 的那一刻，字段快照被冻结。**
draft → ready → 之后在 S04 改字段配置（加字段、改显示名、改公式）
→ 该月显示的列**与冻结瞬间完全一致**（字段集合、显示名、公式、顺序）。
*为什么必须有这条*：设计文档 ch.6「field_snapshot 冻结当月字段定义，
防止事后改字段导致历史错位」。这是本卡存在的全部理由。

**5. 快照里存的是「当时的字段定义」，包括公式源码。**
快照里能看到该字段当时的 `key / label / data_type / formula / required / visible / sort_order`，
`formula` 是**源码**不是算出来的值。
*为什么必须有这条*：公式源码属于字段定义（ADR-0018），
值属于工资记录（TC-303）。把源码存成值，就再也无法重算那个月了。

**6. ready 之后仍然可以编辑数值；sending / sent / archived 不能。**
`is_editable`：draft ✓、ready ✓、sending ✗、sent ✗、archived ✗。
*为什么必须有这条*：设计文档 ch.5「**发送中/已发送**状态禁止编辑工资数值」——
没提 ready。TC-000 时代把 ready 也禁了，与设计文档字面不符，本卡修正。

**7. 解锁能把已发送的账套退回草稿，并且必定留下一条修订记录。**
sent → `unlock_period` → 状态回到 draft；`audit_log` 里多一条
`action=unlock` 的记录，含账套 id 与当时的状态。
*为什么必须有这条*：设计文档 ch.5「解锁 → 生成修订记录 → 仅对未发送者补发」。
没有记录的解锁等于偷偷改历史工资条，与 ch.9「可举证」的要求相违。

**8. 非法迁移不产生任何副作用。**
对 sent 账套做 `transition_period(ready)` → 被拒，账套状态**一字不变**，也没有审计记录。
*为什么必须有这条*：被拒的操作不能留下半截状态。
（这与 TC-201 的「口令错一个字节都不删」是同一个原则。）

**9. `locked_at` 记的是进入 sending 的时刻。**
ready → sending → `locked_at` 有值且接近当前时刻；其他状态下是空。
*为什么必须有这条*：设计文档 ch.6 有这一列。它回答「这个月的数据什么时候被锁住的」。

**10. 界面上的状态 chip 与实际状态一致。**
S07 的月份切换下拉旁边显示当前月的状态（草稿 / 待发送 / 发送中 / 已发送 / 已归档）。
*为什么必须有这条*：状态是这套流程里最要紧的一句话
（能不能改、能不能发），它必须一眼看得见。

**11. 门禁九项全绿。**
`FAST=0 bash scripts/gate.sh` → 「✓ 门禁全绿」。九项按名字：Rust 格式、
前端类型检查、设计 Token（色值只允许出现在 `tokens.css`）、Token 引用可解析、
敏感数据未进 git、Rust 静态检查（clippy `-D warnings`）、Rust 单测、
加密栈链接（`otool`：链 `Security.framework`、零 `libcrypto`/`libssl`）、前端构建。
*为什么必须有这条*：本卡第一次在**业务表**上做状态机；
`clippy -D warnings` 会盯住「TC-000 时代留下的 `#[allow(dead_code)]` 有没有被真的删掉」。

**浏览器实测（S07 界面）**：切到「2026 年 9 月」（已发送）→ 状态 chip「已发送」、
提示「已发送的账套只读 —— 要改得先『解锁纠错』」、出现「解锁纠错」按钮；
列区写明「已冻结在进入『待发送』的那一刻 —— 之后改工资条项目配置不影响这个月」，
列名带「（快照）」后缀。切回「2026 年 10 月」（草稿）→ 提示换成
「草稿阶段用当前的工资条项目配置 —— 改了立刻生效」。

### 二、实现期改掉的一处**与设计文档不符的旧口径**

`domain/period.rs` 是 TC-000 时代留下的，写的「`is_editable` 只在 draft 为真」——
但设计文档 ch.5 的原话是「**发送中/已发送**状态禁止编辑工资数值」，**没提 ready**。
ready 是「校验通过、等待发送」，还没发出去，改一个数完全正常（改完 S11 的校验会重跑）。

⇒ 本卡把 `is_editable` 修正为 **draft | ready**，并改掉那条对应的旧测试。
（ADR-0019 洞三记录了这件事。）

### 三、实现期的两个小决定

- **`year_month` 存 TEXT `YYYY-MM`**（设计文档只说 `UNIQUE(year_month)`，没定格式）。
  接受 `2026-10` / `2026/10` / `202610` 三种写法并统一成 `YYYY-MM`；月份不在 1–12 直接拒。
- **库里的状态认不出来时当作只读终态**，不猜：猜错会让界面显示一个假的「可编辑」状态。

### 四、结论

- **11 / 11 条已过**，无豁免项，本卡结案：`状态` 转 accepted、ADR-0019 转 accepted、TASKBOARD 更新。
- **工资记录不在本卡** → TC-303（逐格编辑、合计行、公式列重算）；
  导出空模板 → TC-301；导入与行级校验 → TC-302；发送推进与「仅对未发送者补发」→ TC-402。
  本卡只提供**能力**（状态、迁移、快照、解锁留痕），不驱动发送。
