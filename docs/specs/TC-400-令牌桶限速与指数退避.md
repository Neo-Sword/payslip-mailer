# TC-400 · 令牌桶限速 + 指数退避（发送编排骨架）

状态：**accepted** · 依赖：TC-100（SQLCipher 库）、TC-300（月份账套）、TC-303（记录与 checksum） · 最后更新：2026-11-12

设计依据：设计文档 **ch.7「邮件发送引擎」**
（「20–30 封/分钟（默认 30）」「3 最大重试次数，指数退避 30s/2min/10min」
「每封一个收件人——禁止 CC/BCC」「错误码处置」四类表
「可中断设计：队列每完成一封即持久化」）、
**ch.6**（`send_batches` / `send_jobs` 表、「不存渲染后的正文（脱敏）」、
`UNIQUE(idempotency_key)`）、
**ch.5**（`send_jobs.status` 状态机）。

> **引用口径**：本卡引用设计文档一律用**章号 + 屏号 / 章标题**，不写行号。

决策依据：ADR-0023（本卡七条口径：**令牌桶只判定不等待、时钟注入**、
**降速是批次级的**、**错误分类是一个纯函数**、**job 状态机无 failed 存储态**、
**迁移 0008 建批次与任务表**、**每封完成即持久化**、**批次状态机**）。

## 目标

做完之后系统具备什么：

- **发信不超速**：无论谁点发送，出信的节奏都被令牌桶压在配置的速率内。
- **失败有章法**：临时失败自动退避重试（30s/2min/10min，≤3 次）、
  永久失败不浪费时间、认证失败立刻停整批、断网暂停保留现场。
- **现场不丢**：每封的成败立即落库 —— 进程崩了，TC-402 能从库里恢复。

## 范围

**做**：

1. `domain/ratelimit.rs`：**令牌桶**（纯逻辑，时钟注入）——
   `try_acquire(now)` 判定「现在能不能发、下一封要等多久」。
2. `domain/retry.rs`：**错误分类**（纯函数）与**退避表**
   （30s/2min/10min、≤3 次）。
3. 迁移 `0008_send_jobs.sql`：`send_batches` 与 `send_jobs`（字段照 ch.6，
   加 `status` / `rate_per_min` / `next_attempt_at`）。
4. `infra/batch.rs`：批次与任务的持久化 —— 创建批次（按范围生成 jobs）、
   取下一个该发的 job、记录一封的结果（按分类推进状态机）、
   批次级降速、暂停/恢复/中止。
5. Command：`create_send_batch`（ dry-run 参数，本卡只建不跑）、
   `list_send_batches`、`get_send_batch`（含 jobs 摘要）、
   `pause_send_batch` / `resume_send_batch` / `abort_send_batch`。
6. **模拟发送器**（测试与「假跑」用）：按注入脚本吐 SMTP 码，
   编排循环用它把整条链路跑起来 —— 限速、退避、分类、持久化全部过一遍。

**不做**（范围膨胀是本项目最大的风险，逐条写清归属）：

- **真实 SMTP**（lettre、连接、TLS）→ TC-500。
- **逐人渲染**（模板 → 正文）与**三重核对** → TC-401。
- **幂等键的生成与中断恢复** → TC-402（表的 UNIQUE 约束本卡就位）。
- **发送日志脱敏与 CSV 凭证** → TC-403。
- **「发送前二次确认」的界面** → TC-402（红线 3）。
- **设置页的速率输入框** → TC-500（本卡读 `app_meta.rate_per_min`）。

## 验收标准

每条都要在验收时给出**实际观察到的输出**，不接受「已验证」。

**1. 令牌桶按速率放行。**
速率 30/分（2 秒/封）→ 连续 `try_acquire`：第 1 封立即放行，
紧接着的第 2 封被拒并给出 `retry_after ≈ 2000ms`。
时钟前进 2 秒后再试 → 放行。
*为什么必须有这条*：ch.7 的「20–30 封/分钟」是防限流的硬约束；
桶要是形同虚设，飞书风控当场退信。

**2. 速率从设置读出来，默认 30。**
没设置过 → 桶按 30/分跑；把 `app_meta.rate_per_min` 设为 20 → 按 20/分跑。
*为什么必须有这条*：ch.7「可在设置页调整」——
调了不生效等于没有这个设置。

**3. 错误分类全表。**
535 → Abort；421 → Retry；550 → Dead；无码连接错误 → Pause；
200 → 成功；531（未知 5xx）→ Dead；441（未知 4xx）→ Retry。
*为什么必须有这条*：ch.7 的错误处置表是发送引擎的判断中枢；
分类错了，重试浪费机会或把该重试的判死。

**4. 退避表与次数上限。**
第 1 次失败 → `retrying` 且 `next_attempt_at = now + 30s`；
第 2 次 → +2min；第 3 次 → +10min；第 4 次失败 → `dead`。
*为什么必须有这条*：ch.7「3 最大重试次数；指数退避 30s/2min/10min」。

**5. 认证失败立即中止整批。**
两个 job，第 1 个返回 535 → 批次变 `aborted`，第 2 个**保持 queued**
（不会被发出去）；已成功的不受影响。
*为什么必须有这条*：ch.7「535 → 立即中止整批，不重发」。
凭据坏了还继续发，每封都是一次失败登录计数。

**6. 永久失败不重试。**
返回 550 → 那封直接 `dead`（`attempts = 1`），批次继续发后面的。
*为什么必须有这条*：ch.7「550/553 → 标记 dead，不重试」。

**7. 网络中断暂停批次，恢复后继续。**
第 2 封遇到连接错误 → 批次 `paused`、那封回 `queued`；
恢复（`resume`）→ 从 queued 继续，**已成功的不重发**。
*为什么必须有这条*：ch.7「网络中断 → 暂停队列，保留现场，可『继续』」。

**8. 每封完成即持久化。**
跑到第 3 封时强行中断（不再调用编排循环）→ 读库：
前 2 封已是 `success`（带 smtp_code 与 sent_at），
不是批次收尾时才一次性写。
*为什么必须有这条*：ch.7「队列每完成一封即持久化」——
这是 TC-402「断电恢复、已发的不重发」的基础。

**9. 降速是批次级的。**
批次中遇到 452 → 桶速率减半（30 → 15）；连续再遇 452 **不再减**
（不叠加）；批次结束后新建的批次按配置的 30 跑。
*为什么必须有这条*：ch.7「自动降速 50%」；
ADR-0023 洞二 —— 一次拥塞不该永久改用户配置。

**10. 每封恰好一个收件人（结构性）。**
`send_jobs` 表**没有** cc/bcc 列；创建批次时每个成员一条 job。
*为什么必须有这条*：红线 1「绝不把多个收件人放进同一封邮件」。
表结构上就没有 cc/bcc，比「约定不填」硬得多。

**11. job 不存正文。**
跑完一批 → `send_jobs` 任何一行都没有正文内容；
`checksum` 有值（TC-303 的行级摘要）。
*为什么必须有这条*：ch.6「不存渲染后的正文（脱敏），仅存摘要与结果」——
库里的第二份明文工资数据是要命的。

**12. 门禁九项全绿。**
`FAST=0 bash scripts/gate.sh` → 「✓ 门禁全绿」。九项按名字：Rust 格式、
前端类型检查、设计 Token、Token 引用可解析、敏感数据未进 git、
Rust 静态检查（clippy `-D warnings`）、Rust 单测、加密栈链接、前端构建。
*为什么必须有这条*：发送是外部副作用最重的一层，门禁是回归的底线。

**实现口径的说明**

- **验收中发现并当场修的分类缺陷**：`531`（未知 5xx）最初落在「其余 → Retry」
  —— 但 5xx 是服务器**拒绝**，拒绝的原因不会自己好。已改为
  `500..=599 → Dead`（534/535 先拦为 Abort），测试钉住。
- **「不叠加」是批内只降一次**：`TokenBucket.halved` 标记。
  连续 452 不会一路减到 0（减到 0 就永远发不完了）。
- **驱动循环不 sleep**：`drive_batch` 用**注入的时钟**推进
  （不放行就把 `now_ms` 拨到放行时刻）。真进程的 sleep 由 TC-402/TC-500
  的 async 循环做 —— 策略层与「等多久」的判定完全分离，测试零等待。
- **幂等键现在就按公式生成**：`hash(batch_id + member_id + period_id + content_checksum)`，
  表的 UNIQUE 靠它挡重复；TC-402 消费它做中断恢复。
- **批次只对非草稿账套开放**：草稿还没「标记为待发送」，建批次直接被拒
  （`a_draft_period_cannot_start_a_batch` 钉住）。

**要认的账（本卡遗留的边界，不是缺陷）**

- **本卡发不出真邮件**：编排骨架跑在注入的假发送器上（`Sender` trait）。
  TC-500 接 lettre 后，把真 SMTP 回复映射成 `SendResult` 即可，策略层一行不改。
  `Sender` / `drive_batch` / `record_result` / `take_next` / `maybe_finish`
  按 error.rs 文件头的惯例标了 `#[allow(dead_code)]` 并注明接线卡（TC-402/TC-500）。
- **发送进度的前端界面**（S12）没有在本卡做 —— 批次的 Command 已经就位
  （list/get/pause/resume/abort），界面随 TC-402 的「发送编排」屏一起做。
