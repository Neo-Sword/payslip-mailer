# TC-401 · 三重核对（身份 / checksum / 变量完整）

状态：**accepted** · 依赖：TC-202（模板渲染）、TC-203（公式求值器）、TC-300（月份账套）、TC-303（记录与校验列）、TC-400（send_jobs.checksum） · 最后更新：2026-11-12

设计依据：设计文档 **ch.5「防错机制」**（「本产品最重要的差异化」的三条：
① 身份一致「不匹配的行标红且不允许进入发送范围」、② 内容一致「渲染前计算
checksum(收件人 + 工资条数据)，与预览时校验和比对，不一致即中止」、
③ 变量完整「所有变量必须能解析且非空……绝不发出『{{实发工资}}』字面量」）、
**ch.12 S07**（「有校验警告时『前往预览核对』仍可点，但 S11 会拦截该成员进入发送范围」）、
**ch.12 S11**（预览与核对屏）、**ch.6**（`send_jobs.checksum` 用于防错校验）。

> **引用口径**：本卡引用设计文档一律用**章号 + 屏号 / 章标题**，不写行号。

决策依据：ADR-0024（本卡六条口径：**迁移 0009 补 identity_verified 列**、
**TC-302 的 commit 修正**、**发送范围核对拦三类**、**内容一致发送前比对**、
**变量完整按 required 标记**、**核对报告是一等结果**）。

## 目标

做完之后使用者能干什么：

- **发送前看清「谁会被发、谁被拦了、为什么」**：S11 预览核对屏逐人列出核对结果。
- **逐人预览真邮件**：核对屏看到的 HTML 与发送出去的正文**同一份渲染**。
- **绝发不出错的钱**：身份存疑、必填缺失、变量缺失、内容被改 —— 四类问题全部拦在发送前。

## 范围

**做**：

1. 迁移 `0009_identity_verified.sql`：`salary_records` 加
   `identity_verified INTEGER NOT NULL DEFAULT 1`。
2. `infra/import.rs` 的 commit 修正：`identity_unverified` → 写 0
   （TC-302 的持久化缺口，随本卡修）。
3. `infra/verify.rs`：**逐人渲染上下文**（`context_for`：成员表 + 账套 + 组名 +
   该行 values + 汇总 + 工资条表格）、**逐人核对**（渲染 + 变量完整 +
   内容 checksum）、**范围核对**（拦三类并出报告）。
4. Command：`verify_send_scope`（S11 的数据源）、`render_member_payslip`（单人预览）。
5. S11 界面：核对结果列表（通过 / 被拦 + 原因）、被拦统计、单人预览（HTML）。

**不做**（范围膨胀是本项目最大的风险，逐条写清归属）：

- **发送编排与「点发送」**（二次确认、真正的发送循环、中断恢复）→ TC-402。
- **发送进度的实时屏**（S12）→ TC-402。
- **试发给自己**（SMTP 真连）→ TC-500。
- **PDF 附件** → v2（设计文档的「可选附件」）。

## 验收标准

每条都要在验收时给出**实际观察到的输出**，不接受「已验证」。

**1. 身份未验证的行被拦在发送范围外。**
导入一行姓名与成员表不一致的记录（`identity_verified = 0`）→
`verify_send_scope` 把它列进 blocked，原因写「身份待核对」；其余行通过。
*为什么必须有这条*：ch.5 防错①「不允许进入发送范围」——
TC-302 只做了导入半（警告），发送半在本卡兑现。

**2. 停用成员被拦。**
范围里有个被停用的成员 → blocked 列出，原因写「已停用」。
*为什么必须有这条*：S05「停用成员不进入发送范围」；停用可能发生在导入之后发送之前。

**3. 校验列有问题的行被拦。**
某行必填字段缺失（TC-303 的 has_problem）→ blocked 列出，原因写「<字段名>缺失」。
*为什么必须有这条*：S07「S11 会拦截该成员进入发送范围」。

**4. 变量完整：required 内置变量为空 → 拦。**
模板用默认的（含 `{{公司名称}}`），而单位名称没配置 → 该行 variable_problems
列出「公司名称」，该行被拦。
*为什么必须有这条*：ch.5 防错③「缺失字段直接拦截」。

**5. 变量完整：required 字段缺 → 拦。**
某行没有基本工资 → variable_problems 列出「基本工资」。
*为什么必须有这条*：同上；必填字段缺失的钱是算不出来的钱。

**6. 变量完整：可选变量为空 → 放行。**
某人不属于任何组（`{{组名}}` 空）→ 该行核对通过（渲染成空串）。
*为什么必须有这条*：「组名」空着不构成发错工资 ——
拦所有空值会把没分组的人全都拦死，那是过度拦截。

**7. 模板引用未知变量 → 该行被拦（引擎级兜底）。**
模板里写 `{{不存在的变量}}` → 渲染失败（StrictUndefined），
variable_problems 说清是哪个变量。
*为什么必须有这条*：ch.5 防错③「绝不发出『{{实发工资}}』字面量」。

**8. 内容一致：checksum 不一致可判。**
`row_checksum` 现算的值与给定的期望值比对 —— 相等返回 true、
改一格后旧值比对返回 false。
*为什么必须有这条*：ch.5 防错②「不一致即中止」的判定函数；
TC-402 的编排循环拿它在发送前逐封比对。

**9. 逐人预览与发送同一份渲染。**
`render_member_payslip` 对张三出的 HTML，与 `verify_scope` 里张三行的
预览 HTML **逐字节相同**（同一个 `context_for`）。
*为什么必须有这条*：「核对看到的」与「发出去的」必须同一份 ——
预览用一套渲染、发送用另一套，核对就白做了。

**10. 渲染上下文的口径。**
`context_for` 的内置变量：姓名/工号/邮箱来自成员表、年月/年份/月份来自账套、
公司名称来自 `app_meta.org_name`、组名来自成员的组（逗号连接）、
应发合计/扣款合计/实发工资来自该行汇总（千分位格式化）、
工资条表格是全部启用字段的 HTML 表。
*为什么必须有这条*：渲染口径是核对与发送的共同底座 ——
口径错了，「通过核对」就没有意义。

**11. 门禁九项全绿。**
`FAST=0 bash scripts/gate.sh` → 「✓ 门禁全绿」。九项按名字：Rust 格式、
前端类型检查、设计 Token、Token 引用可解析、敏感数据未进 git、
Rust 静态检查（clippy `-D warnings`）、Rust 单测、加密栈链接、前端构建。
*为什么必须有这条*：核对是发送前的最后一道闸，门禁是它自己的闸。

**验收中发现并当场修的缺陷（三条）**

1. **TC-302 的持久化缺口（真缺陷）**：导入时判出的「身份待核对」标记**没有入库** ——
   commit 只写 values_json，那个事实在入库那一刻就丢了，发送半想拦也无从拦起。
   修复：迁移 0009 给 `salary_records` 加 `identity_verified INTEGER NOT NULL DEFAULT 1`，
   commit 写入真值（DEFAULT 1 = 修正前的历史行放行）。ADR-0024 决策 1、2。
2. **「工资条表格」的空值误报**：它的值不在 `ctx.builtins` 里（render 以 safe string
   单独注入），核对层查 builtins 恒为「空」—— 所有行都被误拦。
   修复：变量核对跳过它，单独查 `salary_table_html` 非空。
3. **临时钥匙串的偶发竞态（flaky，与本卡逻辑无关但被门禁暴露）**：
   `SecKeychainCreate` 偶发报「same name already exists」（名字里有纳秒，撞名不该发生，
   门禁实测出现过一次）。修复：`TempKeychain::new` 失败换名重试（3 次）。

**实现口径的说明**

- **S11 的 v1 范围 = 全部启用成员**：按组 / 多选成员的范围选择是发送编排（TC-402）
  的事，核对屏先把「全部人」跑通 —— 范围选择的入口接上后，`verify_send_scope`
  的 `member_ids` 参数直接换就行（口径不变）。
- **被拦的人也有预览**（身份拦的不拦渲染）：让人看见「这封邮件长什么样、哪里要改」
  —— 标红的前提是看得见。
- **邮件预览用白底 iframe**（`sandbox=""`）：发给收件人的正文就是浅色 HTML，
  深色应用里嵌白底看的是**真实观感**；iframe 沙箱不给任何权限。

**要认的账（本卡遗留的边界，不是缺陷）**

- **identity_verified 默认 1**：修正前导入的行没有标记，一律放行（ADR-0024 已写明）。
- **内容一致的逐封比对在 TC-402**：本卡提供 `row_checksum` / `checksum_matches`
  与判定规则（不一致 → 判死 + 暂停），执行点在发送编排循环。
- **试发给自己**是 SMTP 真连（TC-500）的事，核对屏没有它。
