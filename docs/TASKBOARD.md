## 当前焦点

**TC-600 已发出（in_progress）**：[TC-600 spec](specs/TC-600-发布产物与安装说明.md)
+ [ADR-0028](adr/0028-未签名内部分发的口径.md)。它是 P6 的收口卡，也是第一张**产物面向使用者**
的卡（前面所有卡交付的都是「能跑通的能力」，这张卡交付的是「别人拿到就能用」）。
核心口径（ADR-0028 的七条）：
**v1 不签名不公证**（决策 D8 的延续，`sign.sh`/`notarize.sh` 留着但默认不跑）；
**分发判据是 quarantine 属性而不是介质名称**（U 盘/局域网共享拷贝不带 → 双击直开；
网盘/浏览器下载带 → 每台机首次手动放行）；
**钥匙串弹窗必须点「允许」**（未签名二进制的 ACL 认 cdhash，每次重建都重授权 ——
点「拒绝」会让人锁在门外）；
**`spctl -a -vv` 预期失败是事实不是缺陷**（只有 `--signed` 构建才要求它通过）；
**产物不入 git**（`artifacts/` 由 .gitignore 挡住，产物靠「发布记录 + SHA-256」定位）；
**升级演练归 TC-601**（要在「装过旧版本、库里有数据」的机器上做，本卡造不出那个状态）。

本卡要交的三样东西：**一条可重复的发布命令**（`scripts/release.sh` 跑通并加固）、
**随包附的一页安装说明**（`docs/安装说明.md`，六节齐全，正文汉字数 ≤ 900，dmg 根部也放一份）、
**一条发布记录**（版本、体积、SHA-256、架构证据）。

**进度（2026-11-12）**：实现完成，**12 条里 11 条已过**（剩 S9「移走 app 后数据仍在」等本人在场时一起做）。
新增 `scripts/verify-release.sh` 把 S1~S8、S12 变成可跑的断言（输出即证据）。
产物就绪：未签名 universal dmg 11M（`x86_64 arm64`）+ `.sha256` + `发布记录-0.1.0.md`。
**真机验收又撞出三处真缺陷，已当场修掉**（详见 spec 评审记录）：

1. **开发构建与发布构建共用一个数据目录** → 必然撞「密钥与数据不匹配」，
   发布版一启动就死在错误屏上。修法：开发构建改用 `cn.payslipmailer.desktop-dev/`
   （[ADR-0030](adr/0030-开发构建与发布构建分数据目录.md)）。
2. **错误页是一条死路**（文案承诺「从备份恢复或重新初始化」，屏上只有「重试」）。
   修法：新增 `reinitialize_local_state`（把读不出来的旧库**改名移走**，不删），
   错误页补上「重试 / 从备份恢复 / 重新初始化」三条路
   （[ADR-0029](adr/0029-重新初始化的口径.md)）。
3. **侧边栏三个导航项点进去是占位页**（导出空模板 / 发送队列 / 安全与备份）。
   修法：新增 `ExportScreen` 与 `QueuePanel`，「安全与备份」指向设置页。
   **侧边栏承诺的每一屏都必须存在**。

另外修掉三处：**release 构建专属的未使用 import**（门禁跑 dev profile 看不到）、
**bash 全角括号吞变量名**（`release.sh` 两处 + TC-000 时代 `notarize.sh` 一处潜伏 bug）、
**安装说明漏写「钥匙串弹窗要输 Mac 登录密码」**（真机才暴露）。

P6 验收原文里的「从安装到试发一封 ≤ 10 分钟」在本卡被**切成两半**：

**TC-102 已结案（accepted）**，15 条验收标准全过，无豁免项（逐条实测输出见 spec 评审记录）。
P1 的口令与锁定层就位：

- **供应链**：`argon2 0.6.0` 关默认特征 → 12 个纯 Rust crate，验收时逐个复扫
  `.c/.h/.S/build.rs` 全为 0；门禁的加密栈一项仍是 `Security.framework`、零 `libcrypto`/`libssl`。
  本卡新增的是**两条依赖声明**（`argon2` + 把 `core-foundation-sys` 提成直接依赖），不是两条依赖。
- **参数**：`m=19456,t=2,p=1`（OWASP 2024 下限），实测稳态 hash 10.50 ms；参数与盐写在 PHC 串里，
  库里只有 `pwd_hash` 一列，以后调强走重哈希、不需要迁移。
- **锁定**：`failed_attempts` / `locked_until` 进库（INTEGER epoch 秒），「重装应用绕过」这条路
  第一次有了可测实现。判定口径钉死：第 5 次失败仍返回 `BAD_CREDENTIALS` 且 `remaining = 0`，
  **锁定从第 6 次尝试起生效**；锁定期内不延长，全部边界用注入时钟在毫秒级测完。
- **解锁顺序**：先开库后验口令（哈希在加密库里）；失败与锁定分支立刻 `close()`，
  回到 ch.5 的「释放连接并清内存中的明文密钥」。管理员口令**不是**库密钥。
- **唤醒**：分布式通知中心 + `Hold`。验收中追加 **ADR-0011 §10** 四组对照实验，测出
  「回调只由**主线程的 runloop** 派发，注册在哪个线程无关」，据此把观察线程里的
  `CFRunLoopRunInMode` 换成 `sleep`（留着那次泵一条通知都收不到）。标准 11 因此拆两半：
  「计数变了 → 关库」留在 `#[test]`（`inject_wake`，CI 可跑），
  「另一个进程发 → 收到 → 连接关掉」放进 `tests/wake_delivery.rs`
  （`harness = false`，自带 `main()` 泵主线程）—— libtest 把测试体放在工作线程上，
  `--test-threads=1` 也一样（`pthread_main_np()` 返回 0），单元测试永远泵不到主线程。
  环境不满足时打印 `SKIP` 退出 0，不挂住也不假绿（`PAYSLIP_WAKE_TEST_SKIP=1` 可当场复现）。
- **回归**：`cargo test` → 57 passed / 0 failed，外加集成测试 `PASS`；
  `FAST=0 bash scripts/gate.sh` → 九项全绿。

TC-105 的核心口径（[ADR-0014](adr/0014-清空数据的删除顺序与边界.md)）：
**先删库、后删钥匙串条目** —— 两个半成品状态的代价完全不对称，
「条目没了库还在」会把用户锁在门外，「库没了条目还在」只是回到首启向导。
连 `exports/` 里的备份一起删（「彻底清空」要名副其实），日志留着（脱敏，
且合规上「保存 2 年以上备查」指的是发送记录）。不覆写擦除 —— APFS + SSD 上
那不可靠；真正的安全性质是「密钥没了 ⇒ 密文永远解不开」。

「预览表头」是导出表头的**唯一真相源**，TC-301 直接复用它。

粘贴是便利功能，表单是精确操作）；**成员只有停用没有删除**，而**删组只解除归属**、
成员不动；「邮箱待确认」第三态归 TC-403（它才有 550 退信历史）。
**真实名单的验证**仍待业务方给（只放本机，绝不进 git）—— 机制已验，名单不是代码问题。

**TC-202 已结案（accepted）**：12 条标准全过。核心口径
（[ADR-0017](adr/0017-模板渲染的引擎与变量白名单.md)）：
**渲染用 minijinja，但不开 `loader`** —— 那是「从文件读模板」的开关，
不开它，「从磁盘读模板」这条路在**结构上**就不存在（红线 4 的沙箱不靠约定，
靠没开那个开关）；**字段变量用 key 而不是显示名**（`{{字段.base_salary}}`）——
显示名可改、key 不可改，所以 HR 改个名字不会让所有老模板同时失效；
**空值按「是否必填」判定**（字段看 S04 的 `required`；工号在成员表里本来就是可选的，
照字面「非空」拦的话，没填工号的成员会永远收不到信）。
**「试发给自己」没做** —— 要真实 SMTP（TC-500，现在 blocked）；
预览用**示例数据**（真实工资数据在 TC-303）。

**TC-203 已结案（accepted）**：12 条标准全过。核心口径
（[ADR-0018](adr/0018-公式求值器的语法与沙箱.md)）：
**自己写递归下降的算术表达式求值器**，语法只有
「数字 / 字段 key / 汇总变量 / + − × ÷ ( ) / 一元负号」——
**没有函数、没有属性访问、没有字符串、没有 I/O**，
所以「禁止任意代码执行」是**结构性的**而不是约定（红线 4）。
**求值用原始数值、格式化在求值之后**（`18,000.00` 根本不是合法表达式）；
输出**按分四舍五入**把浮点误差挡在「分」这一层外面；
**除以零 / 循环引用 / 拿文本字段做算术 / 引用不存在的字段**全部报错（不是 0）。
汇总变量（应发合计 / 扣款合计 / 实发工资）是**该行**的合计，不是整张表的。

**TC-300 已结案（accepted）**：11 条标准全过。核心口径
（[ADR-0019](adr/0019-月份账套的快照冻结与解锁留痕.md)）：
**快照在「进入 ready」那一刻冻结**（不是建账套时 —— HR 在草稿阶段还要配字段，
创建就冻结会让新字段进不了这个月）；**draft 用当前配置、ready 起用快照**，
所以「改字段配置」弄不乱已经准备发送的历史月份；
**`is_editable` = draft | ready**（设计文档只禁 sending/sent，TC-000 时代把 ready 也禁了，
本卡按设计文档修正）；**解锁 = sent → draft 且必定在 `audit_log` 留一条修订记录**
（「解锁 → 生成修订记录 → 仅对未发送者补发」的前两步，第三步归 TC-402）。

**TC-301 已结案（accepted）**：12 条标准全过。核心口径
（[ADR-0020](adr/0020-空模板导出的表结构与快照来源.md)）：
**表头 = 3 个固定列（姓名/邮箱/工号）+ 启用字段**，固定列在前 ——
它是导入映射的锚点（S08 的映射规则需要一个确定的起点）；
**表头取账套的快照**（复用 TC-300 的 `display_fields`，不另立口径），
所以「导出 9 月的空模板」导出的正是 9 月当时的列；
**公式列不导出数据**，单元格写「公式自动计算」占位（写数字会让人以为那是算出来的）；
**默认是空模板** —— 说明 Sheet 开、示例数据关、预填名单关
（预填名单会把姓名邮箱带出文件，红线 2）；
**扣款项填负数**写进说明 Sheet（它跟着文件走，财务不会问错方向）。
验收时发现并修了三个问题：`Sheet1`/`Sheet2` 的默认名会让人在两个 Sheet 之间认错、
落盘路径散在 Command 层（收进 `export::target_path`，一处口径）、clippy 三处告警。

**TC-302 已结案（accepted）**：18 条标准全过。核心口径
（[ADR-0021](adr/0021-Excel导入的表头映射与冲突策略.md)）：
**表头映射分三档**（精确 = 与显示名完全相等、模糊 = 双向包含需确认、未匹配 = 跳过）
—— TC-301 导出的表头（含必填列的「 *」）必须**全部精确命中**，自己导出的文件导回去零摩擦；
**校验分三档**（错误 K 阻断入库 / 警告 M 入库但带标记 / 成功 N），判据是
「会不会让发出去的钱是错的」；**身份一致按邮箱找人**（邮箱全局唯一，ADR-0016），
**姓名与成员表不一致只警告并标记「身份待核对」**——那行入库但**不进发送范围**
（TC-401 拦），一个错别字不该毁掉整批导入；**空金额 = 没有这一项**（不是 0）；
**公式列填占位文字静默忽略、填别的报错**；**冲突三选一 + 覆盖前同事务写审计**
（审计只有行数，红线 2）；**入库一个事务、失败整批回滚**；**原文件只读不复制**（ch.9）。
验收撞出并修了两条真缺陷：**TC-203 的 `evaluate_formula_fields` 把 `text_fields` 丢了**
（类型错误在生产路径上报成「未知」，已修并补记 TC-203 评审记录）；
**「这一行没填」的字段曾让整批导入失败**（已定语义：
配置里有但没填 → 按 0 算，配置里没有 → 报错 —— S07 原型赵六行「个税 —」正是这个语义）。
行求值顺势收敛到一份（`domain/record.rs`）：预览、入库、将来发送三处必然同一个数。

**TC-303 已结案（accepted）**：13 条标准全过。核心口径
（[ADR-0022](adr/0022-工资记录的逐格编辑与合计行.md)）：
**单格保存**（改一格 → 整行重算公式列 → 重算 checksum → 返回新行原地替换）；
**公式列只读**（前端禁用 + 后端拒绝两层）；**校验列 = 必填缺失警告**
（**拦发送不拦保存** —— 编辑期 HR 经常先录入后统一补，中途拦保存只会逼人乱填 0；
拦截在 TC-401 兑现）；**表级合计 = 整月且公式列不进合计**
（行级公式列已经是和，再加一遍实发就重复了）；**编辑权在 Command 层再查一次**
（sending/sent/archived 拒写）；**逐格编辑不写 audit**（审计粒度是成批动作，
改 42 行 × 10 列 = 420 条会把审计日志淹没）；**「空 = 没有这一项」贯穿编辑**
（清空一格 = 删键）。

**P3 数据闭环到此完整**：账套（TC-300）→ 导出空模板（TC-301）→ Excel 导入（TC-302）
→ 逐格编辑（TC-303）。一条「配置 → 出表 → 收表 → 入库 → 修数」的月度主链路全部落地。

**TC-400 已结案（accepted）**：12 条标准全过。核心口径
（[ADR-0023](adr/0023-发送编排的限速退避与错误分类.md)）：
**令牌桶只判定不等待**（时钟注入 —— 测试零 sleep、真进程的 sleep 归编排循环）；
**降速是批次级的且批内只降一次**（一次拥塞不该永久改用户配置，减到 0 就发不完了）；
**错误分类是一个纯函数**（535/534→中止整批、4xx→退避重试、5xx 全段→判死
—— 服务器拒绝的原因不会自己好、无码→暂停保留现场）；
**job 状态机没有 failed 存储态**（失败即刻变 retrying 或 dead）；
**每封完成即持久化**（TC-402 断电恢复的基础）；
**`send_jobs` 没有 cc/bcc 列**（红线 1 是表结构级的）且**不存正文**（ch.6 脱敏）。
验收修了一条分类缺陷：未知 5xx（531）曾落在 Retry，已改成全段判死。

**TC-401 已结案（accepted）**：11 条标准全过。核心口径
（[ADR-0024](adr/0024-三重核对的落点与拦截规则.md)）：
**身份一致的发送半拦三类**（identity_verified=0 / 停用成员 / 校验列有问题 ——
从范围**排除**并列进报告，不是报错）；**变量完整按 required 标记**
（required 内置变量空 / required 字段缺 / 渲染失败 → 拦；可选空 → 放行 ——
「组名」空着不构成发错工资）；**内容一致的判定函数就位**
（发送前 row_checksum 与 send_jobs.checksum 比对，执行在 TC-402）；
**预览与核对同一份渲染**（同一个 context_for —— 核对看到的与发出去的必然一致）。
**验收修了 TC-302 的持久化缺口**：「身份待核对」标记曾不入库
（迁移 0009 加 identity_verified 列），发送半曾无从拦起。另修「工资条表格」
空值误报（它的值不在 builtins 里）与临时钥匙串的偶发竞态（重试 3 次）。

**TC-402 已结案（accepted）**：10 条标准全过。核心口径
（[ADR-0025](adr/0025-发送编排的恢复语义.md)）：
**存疑 sending 恢复时回 queued**（发给本人的重复无害、丢发难查；
已成功的**绝不**重发）；**恢复可重复发起**（`find_unfinished` 随时查，
「已发 27/60」从库算 —— 没有第二份进度快照）；**仅重试失败项**
（dead → queued、attempts 保留、error_code 清空；aborted 批次拒绝 ——
凭据坏时重试没有意义）；**点发送两层核对**（S11 先核 + `start_batch` 再核，
不过的错误点名被拦的人）；**SMTP 未配置时报「发信设置还没配置」**——
事实陈述不是假成功，真发送循环的接线点已注明（TC-500 换上真 Sender 后
代码一行不改）。红线 3（二次确认「每封一个收件人，绝不抄送」）与
红线 4（只补未成功）在此兑现。

**TC-403 已结案（accepted）**：11 条标准全过。核心口径
（[ADR-0026](adr/0026-发送凭证的列与脱敏层次.md)）：
**CSV 凭证六列**（姓名/收件地址/状态/SMTP回码/发送时间/内容校验和 ——
ch.9 证据链的原话）且**逐格扫不到任何工资数值**（红线 2）；
**姓名进 CSV 不进日志**（凭证是用户主动导出的，同 TC-301 预填名单的逻辑）；
**脱敏四层各自被测试钉住**（库层无正文列 / 审计层只记行数 / 凭证层无数值 /
日志层只记 id 与处置）；**UTF-8 BOM + RFC 4180**（Windows Excel 双击不乱码、
敌意姓名含逗号引号换行往返一致）；**send_jobs 没有删除入口**
（≥2 年留存靠「不删」，唯一终点是 TC-105）；**导出是纯读操作**。

**TC-500 已结案（accepted）**：9 条标准全过。**发送链路真正打通**：
lettre 0.11 + rustls + ring（otool 复验零 libcrypto —— 门禁第 9 项的真正压测）；
Sender trait 收 `EmailMessage`（渲染归编排、发送只管发出去）；
`drive_batch` 内逐人渲染（与 TC-401 同一 `render_for` —— 核对看到的与发出去的
同一份渲染；渲染失败该封判死、批次继续）；专用密码只进 Keychain
（表里只有 `credential_ref`）；测试连接 = 发自检信给自己（不是空探测）；
自动化验收全部跑在 lettre StubTransport 上（ch.3 纪律）。
验收修了一条真 bug：测试连接的密码分支被残留行遮蔽（改密码后测试仍用旧密码）。
**`recover_and_run_batch` 的接线点兑现**：真发送器接上，编排代码一行没改。

**剩 TC-501（真机验证，blocked —— 需要使用者提供飞书专用密码）**：
真发自检信、真发 5 封、535 引导、lettre 翻译层的真实回码。之后 TC-600/601（发布）。

**TC-104 已结案（accepted）**：16 条标准全过，无豁免项。备份的核心口径是
**密钥来自用户口令、不来自钥匙串的 DB key** —— 设计文档 ch.10 明写
「多机使用时…交接靠『导出加密备份 → 新机恢复』」，用 DB key 加密的备份在新机上永远打不开。
加密层走 SQLCipher 自己的 AES-256（`ATTACH + sqlcipher_export`），**不在 zip 容器上再叠一层**；
恢复走「暂存文件 → 验一遍 → 原子改名」，中途失败不会停在「删了还没写上」。
实现期当场改掉四个问题，其中两个是真 bug：临时目录名只由人可读 stamp 决定（同一秒两次恢复
会互删）、`restore_inner` panic 时清理被跳过（工资数据留在磁盘上）——都修了，细节见
[ADR-0013 的实现期追加](adr/0013-备份的密钥来源与恢复流程.md)。
新增依赖只两个纯 Rust crate（`zip` 不带 AES 特性、`sha2` 零新增闭包），另加一条权限
`dialog:allow-open`（原生文件选择器，见 ADR-0013 追加 A）。
**销毁（清空数据）不在本卡** → TC-105。

**TC-104 的核心口径**（[ADR-0013](adr/0013-备份的密钥来源与恢复流程.md)）：
**备份的密钥来自用户口令，不来自钥匙串的 DB key** —— 设计文档 ch.10 明写
「多机使用时…交接靠『导出加密备份 → 新机恢复』」，用 DB key 加密的备份在新机上永远打不开。
加密层走 SQLCipher 自己的 AES-256（`ATTACH + sqlcipher_export`），**不在 zip 容器上再叠一层**
—— 少一套加密实现，而且口令错时在解密那一步就停，压根碰不到现有库。
恢复六步的顺序（先校验备份能不能开 → 再自动备份当前库 → 最后才替换）是 ADR-0013 §4 的全部意义。
**销毁不进 TC-104**：不可撤销的操作不与「备份能救回来」放进同一张卡。

**另一件事挡在门口**：仓库仍是**零 commit**（等使用者点头才提交）。CI 首跑、以及 TC-101 与
TC-102 各自那条「headless 会话里要 SKIP 而不是挂」的遗留，都要等首次 push 才自动补上。

**开发循环的钥匙串弹窗已解决（2026-11-11）**：验收时撞上「每次启动都要重新授权钥匙串」。
根因是钥匙串条目的 ACL 认的是**二进制的 cdhash**（未签名）或需要 **Apple 锚定签名**才稳定
（自签证书实测不行）—— 买 Developer ID 之前无法从根上避免。
于是开发构建改用**专用钥匙串文件**，并加了一条命令把「编译 → 签名 → 起 app → 自动授权」
串起来：`bash scripts/dev-run.sh`。**发布构建完全不受影响**（仍走登录钥匙串 + 默认 ACL）。
完整实测记录与被排除的三条路见 [ADR-0009 的补充章节](adr/0009-Keychain用security-framework的item层.md)。

## 结案遗留

| 来源 | 遗留事项 | 落到哪张卡 |
|---|---|---|
| TC-000 标准 10 | 原生窗口的像素截图（红绿灯实际位置）未取到：后台 shell 起 app 时 System Events 看不到窗口，属 ADR-0008 记的「依赖 GUI 会话」问题 | 已转成 **TC-103 标准 19**（真人起界面确认红绿灯与窗口标题）。本卡是第一次真的起界面 |

| TC-101 测不到 | 真实 ACL 重置：临时钥匙串里没有「升级后签名变了」这回事，`put` 的 not-found 分支只覆盖了「条目不存在」一侧 | **TC-601**（卡名本身就是这件事）真机演练；ADR-0009 已列为负面 |

## 依赖说明（为什么是这条边）

- **TC-100 ← TC-101**：SQLCipher 的库密钥必须由 Keychain 提供，否则构造不出可测试的「打开已有加密库」路径（标准 3 要靠删 Keychain 条目来触发）。先做 Keychain。
- **TC-102 ← TC-100**：口令哈希与锁定计数要落库，落库要先有迁移机制。
- **TC-104 ← TC-100 + TC-101**：备份是「带密钥的库文件」的复制，两者缺一只能备份出一个打不开的库。
- **TC-300 ← TC-200**：状态机的 `field_snapshot` 冻结的是字段配置，没有字段配置就没有可冻结的东西。
- **TC-402 ← TC-400 + TC-401**：幂等键含 `content_checksum`，重试语义依赖退避后的失败分类。
