# 薪邮 · 开发工作约定

本目录是开发过程的**唯一事实来源**。任何一块工作都以「任务卡」为单位推进，
卡上必须同时有 **spec** 与 **ADR**，做完必须**基于这两份东西验收**，通过才发下一张。

## 0. 总纲与事实来源边界

仓库根的 [`总纲.html`](../总纲.html) 是**导航与看板**：进度指标、P0–P6 分期任务表、全部产出的分类登记、双层检索与维护规范。
它由 [`build-master-index.py`](build-master-index.py) 从 `TASKBOARD.md` 与 `specs/` / `adr/` 目录生成，
**不产生新决策、不改写验收标准**；本目录仍是唯一事实来源，两者冲突时以这里为准。

- 任务卡状态**只改 `TASKBOARD.md`**，改完重跑 `python3 docs/build-master-index.py`；不要手改总纲里的表格或进度数字。
- 新增 spec / ADR 由目录扫描自动登记，同时在生成器的 `SPEC_NOTES` / `ADR_NOTES` 补一句核心口径（没补会显式标注「待补」）。
- ADR 只追加不修改（见 §1）；作废的卡标 `withdrawn` 留在看板上，编号不复用、不重排。

## 1. 三种文档的分工

| 文档 | 回答的问题 | 什么时候写 |
|---|---|---|
| `specs/TC-xxx.md` | 做成**什么样**、边界在哪、**怎么算过** | 动手之前 |
| `adr/0xxx.md` | 为什么**这么选**、放弃了什么、代价是什么 | 出现分叉时 |
| `TASKBOARD.md` | 现在在做什么、谁挡着谁、业务输入缺哪块 | 每张卡状态变化时 |

一句话区分 spec 与 ADR：**spec 会随实现被推翻重写，ADR 只追加不修改**。
后来者若不同意某条 ADR，写一条新的去 supersede 它，不要改旧的 —— 决策时的现场信息只有当时的人知道。

## 2. 任务卡编号

`TC-<阶段><序号>`，阶段号对齐 `../PREP-CHECKLIST.md` §4 的 P0–P6：

```
TC-0xx  P0 工程骨架与设计系统
TC-1xx  P1 身份与存储
TC-2xx  P2 配置模块
TC-3xx  P3 数据闭环
TC-4xx  P4 发送引擎（mock SMTP）
TC-5xx  P5 真实邮箱联调
TC-6xx  P6 发布
```

编号一旦发出就不复用、不重排。作废的卡标 `withdrawn` 留在看板上，
因为「曾经打算做又砍掉」本身是对后来者有用的信息。

## 3. 一张卡必须有的字段

```markdown
# TC-xxx · 标题
状态：draft | in_progress | review | accepted | blocked | withdrawn
依赖：TC-yyy（说明为什么依赖）
设计依据：设计文档 ch.N / 原型 SNN / ADR-0xxx

## 目标
一句话，写「做完之后使用者能干什么」，不写「改哪些文件」。

## 范围
明确列出**不做**什么。范围膨胀是本项目最大的风险：功能越全，HR 越不敢用。

## 验收标准
每条都必须可证伪 —— 能跑一条命令、或能点一次界面看到确定结果。
禁止「性能良好」「体验流畅」「代码健壮」这类无法判定的表述。

## 评审记录
验收日期 / 逐条结论 / 未过项处置。这一节是这张卡的结案证据。
```

## 4. 验收怎么做

1. `bash scripts/gate.sh` 全绿（这是所有卡共用的门禁，见 §5）。
2. 逐条对照「验收标准」执行，**每条记下实际观察到的结果**，不写「已验证」。
3. 未过项二选一：当场修，或写清「为什么可以带着它结案 + 由哪张卡补」。
   没有第二种记录的未过项，等于没验收。
4. 结论写进该卡的「评审记录」，更新 `TASKBOARD.md` 状态，**然后才**发下一张卡。

验收时如果发现 spec 本身写错了（标准定歪了、范围划错了），
先改 spec 并在评审记录里注明「验收中发现 spec 缺陷」，再判这张卡。
不要用改代码去迁就一条错误的标准。

## 5. 门禁 `scripts/gate.sh`

所有卡的验收标准都引用同一组检查，避免每张卡自己发明一套「合格」。
其中两条是本项目的**专属红线**，通用 lint 抓不到：

- **组件层不得硬编码色值**：色值只允许出现在 `src/styles/tokens.css`。
  确需脱离 Token 的颜色（仿 macOS 红绿灯这类）用行尾 `/* no-token: 理由 */` 显式豁免，
  豁免可 grep、可审计，而不是把整条检查关掉。
- **Token 引用必须能解析到声明**：写错一个 Token 名不会报错，只会「没有颜色」，
  在深色背景上表现为一片空白，肉眼极易漏过。

另有「敏感数据未进 git」一条：成员名单与真实工资表只放本机，永不入库。

## 6. 红线（每张卡的范围里都要默认包含，不重复写）

见 `../PREP-CHECKLIST.md` §5。最容易在实现时被无意破坏的三条：

1. 一封邮件只有一个收件人，禁止 CC / BCC。
2. 工资数值不进日志、不进错误上报、不进备份文件名。
3. 前端拿不到工资数值与凭据；所有外部副作用走 Rust Command 层。
